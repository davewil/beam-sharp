Nothing to Dispatch

Ad-hoc polymorphism was measured before it was designed for — and the three capabilities that motivated it turned out to want three different things, none of which is dispatch.

The decision

The language gets no ad-hoc polymorphism construct. A capability is generated when the type determines it, enumerated when the set of types is known, and passed when it is not.

The bucket is chosen by what the capability is, not by preference — which is what stops the generated set growing by taste. And the hole ticket 05 recorded turns out to be half imaginary: extension methods were never an ad-hoc polymorphism mechanism at all.

The starting position was already narrow

Ticket 16 arrived carrying four candidates. Two were dead before this session opened, and the remaining two turned out to be the same one.

Type classes died on ticket 09. Instance resolution keys on the nominal head of a type, and ticket 09 removed nominal identity — so instance Show OrderId and instance Show CustomerId are instances for the same type. Not costly; unresolvable.

Protocols and structural dispatch are one candidate, as the ticket file already recorded: put the name in the term, dispatch on the tag. What had not been pulled on was the consequence of resolving that statically.

A correction to this ticket's own file. An earlier section claimed beam-sharp "would get consolidation by construction". That is true only over a closed union — at which point there is nothing left to consolidate. The line has been corrected in place.

Measure first: the three capabilities split three ways

The ticket asked for a mechanism supporting "anything comparable", "anything with a length", and "anything serialisable". Before designing one, all three were measured against the runtime.

What the platform already supplies — OTP 28 / erts 16.4, observed locally
CapabilityWhat the BEAM gives youMechanism needed
Comparable One total order over every type. 1 < :ok is true; #{a => 1} < [] is true. Nothing declares anything. None
Has a length Five monomorphic functions — length/1, byte_size/1, bit_size/1, map_size/1, tuple_size/1. No universal one (size/1 covers tuple and binary only). All five are guard-safe. Union parameter
Serialisable json:encode/1 fails on tuples at any depth, at runtime, with {unsupported_type, Offender}. Generated

The middle row does more work than it looks. Because every size function is guard-safe, "anything with a length" is already a clause head with a guard — the machinery exists and needs no second dispatch system laid beside it.

Why serialisation is the one that wants generating

The argument is not convenience. It is that the tuple is beam-sharp's workhorse — ticket 09 made a tagged tuple the remedy for the newtype gap, and ticket 15 made result<T, E> a tuple. So a large share of declared types are un-encodable by the platform's own encoder, and the platform only says so in production.

%% measured, 16b §5
#{a => 1}                  => <<"{\"a\":1}">>
ok                         => <<"\"ok\"">>
{a, b}                     => {failed, {unsupported_type, {a,b}}}
#{k => {1, 2}}             => {failed, {unsupported_type, {1,2}}}
#{lines => [{sku, _, 2}]}  => {failed, {unsupported_type, {sku,<<"A">>,2}}}

A generated encoder reads the declared type and refuses at compile time, naming the member that has no encoding. A runtime protocol could never do that — which is the argument for generation over dispatch, measured rather than asserted.

And only the encode direction is new: decoding is already built as ValidateAs<T> after a parse.

The generation rule

Rule

A capability becomes a codegen obligation when the type determines the result uniquely — either inherently, or because the language publishes the mapping that fills the gap.

The four existing obligations qualify inherently. Serialisation qualifies by decree, and the price is that the language now carries an opinion about a wire format. The escape is bucket three: a different shape is a function you write and pass.

Two equalities, and who agrees with which

Erlang ships == (says 1 equals 1.0) and =:= (says it does not). beam-sharp ships one, and it is the exact one — decided on internal agreement rather than on what a C# reader expects.

The coercion runs deep, then stops — and the constructs this language is built on never coerce
ConstructCoerces int against float?
== on {1} vs {1.0}yes
== on map valuesyes
== on map keysno — the coercion stops here
A clause headno — f(1) falls through for 1.0
maps:get/2no — {badkey, 1.0}
< orderingthey tie — neither is less

A coercing == would put the guard in disagreement with the clause head directly above it — two answers to "is this value 1" on adjacent lines, and the clause head is the headline feature. Choosing =:= agrees with two constructs and disagrees with none.

Comparison itself is restricted the other way: < requires operands of the same type, so 1 < :ok does not compile. The platform's universal order is kept, but as a named prelude function rather than an operator — it is genuinely needed for ordered_set tables and mixed-key sorting, and naming it makes reaching for it visible.

Bounds, and the debt ticket 27 left here

Ticket 27 §3 deferred capability constraints to this ticket with four requirements attached, including a cost measurement it called "the serious one" — bounds being the feature that turns instantiation from cheap matching into real constraint solving.

That measurement is retired rather than deferred again. Both routes to discharging a bound are closed by decisions already taken, so a bound you could write is a bound you could never use. The walking skeleton no longer owes the number, and instantiation stays matching — now protected by four refusals rather than three.

What falls out for free is the nicer half. < and == work on two values of the same bare type variable, so Sort<T> and Max<T> need no constraint at all. Ticket 27's opacity rule does not block it: opacity exists so a generic function cannot dispatch on its T, and ordering is not dispatch — it returns a bool, reveals nothing about the shape, and cannot fail, the term order being total.

Ticket 05 miscategorised extension methods

Raised by David: extension methods extend class types in C#, and this is functional, so they do not really make sense here. Correct — and it corrects a closed ticket.

Ticket 05 recorded "dropping extension methods and static abstract interface members leaves no ad-hoc polymorphism story." That is one debt written as two. C# needs extension methods because a type's methods are sealed inside its declaration. beam-sharp has no methods on types at all, so extending a type you do not own is the default, not a feature.

  • not polymorphism

    Call syntax

    xs.Where(f) reading left to right. Ticket 05 itself found this is a static rewrite and is the pipeline — so it has belonged to ticket 17 all along. Nothing new is handed over; the only constraint added is that whatever 17 picks has no dispatch in it.

  • not polymorphism

    Overloading

    Several same-named functions over different types, resolved by static type. Ticket 08 settled it: one arrow per arity, union parameters, no overload signatures.

  • the real hole

    Static abstract interface members

    The T.Parse(string) shape — a type promising a static operation. This was the whole of the genuine debt, and bucket one fills it. A codegen obligation is a static abstract interface member with the compiler writing the implementation: ValidateAs<T> is T.TryParse where no type had to declare it.

One leftover is neither: C# lets you put a function in another namespace so it appears on that type without an import. That is name resolution, it has no beam-sharp answer, and it now sits in the map's imports and cross-module-scope fog.

One dispatch mechanism

The ticket demanded a story about which of two dispatch systems fires when. There is one: the clause head. Generated capabilities resolve at compile time from a ground type argument; passed capabilities were chosen by the caller; union parameters are clause heads. Ticket 09's tag is not promoted into a dispatch registry — it remains how union members stay discriminable.
