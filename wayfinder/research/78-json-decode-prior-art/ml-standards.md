## 1. Elm: `Json.Decode`

Two entry points share one decoder: `decodeString : Decoder a -> String -> Result Error a` parses then walks; `decodeValue` walks an already-parsed JS value (ELM-SRC).

- **A. Unknown keys: ignored, not switchable, capturable only by hand.** The `field` doc: "The object *can* have other fields. Lots of them! The only thing this decoder cares about is if `x` is present and that the value there is an `Int`." Its example: `decodeString (field "x" int) "{ \"x\": 3, \"y\": 4 }" == Ok 3` (ELM-SRC). There is no strict mode. To capture extras you decode the object a second time with `dict` / `keyValuePairs` and subtract (the kernel has a key-enumerating case, ELM-KERNEL line 253–260); no built-in "rest".
- **B. Missing required field.** The kernel reports at the *parent* object, carrying the parent value: `_Json_expecting('an OBJECT with a field named `' + field + '`', value)` where `_Json_expecting` builds `Failure ('Expecting ' + type) value` (ELM-KERNEL lines 230–232, 339–341). So `decodeString (field "x" int) "{ \"y\": 4 }"` gives `Failure "Expecting an OBJECT with a field named `x`" <the object>`. Rendered by `errorToString` (assembled from source, not run): `Problem with the given value:` + the pretty-printed object + `Expecting an OBJECT with a field named `x``. Nested, the prefix becomes `Problem with the value at json.a[0]:`.
- **C. First error only, except inside `oneOf`.** Structure, verbatim: `type Error = Field String Error | Index Int Error | OneOf (List Error) | Failure String Value` (ELM-SRC). The path is the nesting of `Field`/`Index`; the leaf holds a free-text message and the offending *value*; there is no separate machine-readable "expected". Path rendering is JS-style rooted at the word `json`: `.name` for alphanumeric keys, `['odd key']` otherwise, `[3]` for indices. `oneOf` runs every branch and returns all branch errors (ELM-KERNEL lines 292–303). Rendered: `Json.Decode.oneOf failed in the following N ways:` (or `The Json.Decode.oneOf at json.a failed in the following N ways:`) followed by `(1) ...`, `(2) ...`. A one-branch `oneOf` renders as that branch's error; an empty one as `Ran into a Json.Decode.oneOf with no possibilities!`.
- **D. null vs absent: distinguished, and the user must compose them correctly.** `nullable int` accepts `null`; `field` requires presence; `maybe d = oneOf [ map Just d, succeed Nothing ]` swallows *any* failure of `d`. The documented pitfall, verbatim from ELM-SRC with `json = { "name": "tom", "age": 42 }`:
  ```elm
  decodeString (maybe (field "name"   int  )) json == Ok Nothing   -- wrong type silently becomes Nothing
  decodeString (maybe (field "height" float)) json == Ok Nothing
  decodeString (field "name"   (maybe int  )) json == Ok Nothing
  decodeString (field "height" (maybe float)) json == Err ...
  ```
  "Point is, `maybe` will make exactly what it contains conditional." So `maybe (field ...)` hides type errors and `field ... (maybe ...)` rejects absence; neither means "optional, but if present must be valid". `NoRedInk/elm-json-decode-pipeline`'s `optional` exists to mean exactly that: absent → fallback, present-and-null → fallback, present-but-wrong → fail ("If it was present but fails to decode, this should and will fail!", ELM-PIPE). It also shows how to tell null from missing: `optional "name" (oneOf [ string, null "NULL" ]) "MISSING"`.
- **E. Input.** String only (a JS string, so already decoded; invalid UTF-8 is not a decoder concern). Parsing is `JSON.parse` (ELM-KERNEL line 188). Measured in node: trailing data rejected (`Unexpected non-whitespace character after JSON at position 8 (line 1 column 9)`); duplicate keys: last wins silently (`{"a":1,"a":2}` → `{"a":2}`); `9007199254740993` parses to `9007199254740992` silently; `1e400` → `Infinity`. `int` accepts any finite number with no fractional part (`isFinite(value) && !(value % 1)`, ELM-KERNEL lines 45–54), so `1.0` and the silently rounded 2^53+1 both pass as `Int`.
- **F. Same type.** Invalid JSON is `Failure ("This is not valid JSON! " ++ e.message) <the input string as a Value>` (ELM-KERNEL line 193). A caller cannot tell syntax from shape without matching on the message prefix.
- **G. Tagged unions: hand-written.** No built-in notion. The idiom is `field "type" string |> andThen (\t -> case t of ... _ -> fail "...")` (idiom unverified, from memory; the mechanism is in source: `andThen` re-runs on the same value and `fail msg` yields `Failure msg value`, ELM-KERNEL lines 286–290, 305–306). Consequence: an unknown-tag error is reported at the *object*, not at `.type`, unless the author nests the `fail` inside `field "type"`.
- **H. Hand-written, not symmetric.** Encoders (`Json.Encode`) and decoders are separate code. Czaplicki's reasons, from his "vision for data interchange" gist (<https://gist.github.com/evancz/1c5f2cf34939336ecb79b97bb89d9da6>): of JSON, "It is not a great choice on basically every metric that matters to building reliable, efficient, and flexible applications."; "the history of building in support for a particular interchange format is pretty poor."; in a comment there, "explicit decoders are very significantly easier to debug than implicit ones." and "generation of JSON decoders in this style is a siren design." His proposed direction is schema-file code generation: "the success stories of protobuf and GraphQL are all around having a specific `.format` file and generating code in whatever language you need."
- **I. Complaints and edges.** Flags and ports *do* get an implicit, derived check for a fixed set of types (Bool, Int, Float, String, Maybe, List, Array, tuples, records, `Json.Decode.Value`) and on mismatch "you get an error on the JS side!"; the guide adds "Many folks always use a `Json.Decode.Value` because it gives them really precise control." (<https://guide.elm-lang.org/interop/flags.html>). So the one place Elm derives a decoder, the community routes around it to get a recoverable error. The `maybe` pitfall above is documented in the function's own doc comment.

## 2. Haskell: `aeson`

- **A. Unknown keys: ignored by default; switchable; not capturable through deriving.** `defaultOptions` has `rejectUnknownFields = False` (AE-INT lines 850–861). With it on, generic record decoding fails with `"unknown fields: " ++ show unknownFields` (AE-FROM line 1415), i.e. `unknown fields: ["b"]` under a `parsing <Type>(<Con>) failed, ` style context (context wording not measured). The changelog when it was added: "Useful to find errors during development, but enabling this should be considered a breaking change as previously accepted inputs may now be rejected." (AE-LOG, 1.4.7.0). Hand-written `withObject` parsers get the whole `Object` and can keep extras themselves.
- **B. Missing required field.** `explicitParseField`: `Nothing -> fail $ "key " ++ show key ++ " not found"`, while the path element is only appended on the found branch (`Just v -> p v <?> Key key`) (AE-FROM lines 921–924). So the error is located at the **parent**: `Error in $: key "x" not found` (assembled from `formatError path msg = "Error in " ++ formatPath path ++ ": " ++ msg`, AE-INT line 604).
- **C. First error only.** Result type is `Either String a`; internally `IError JSONPath String` with `JSONPathElement = Key Key | Index Int` (AE-INT lines 109–121), so the structured path exists but the public `eitherDecode*` flattens it into the string. Format is Goessner-style JSONPath rooted at `$`: `.key` for identifier-like keys, `['odd key']` otherwise, `[0]` for indices (AE-INT 606–629). Type mismatch text: `"expected " ++ expected ++ ", but encountered " ++ typeOf actual`, with a `parsing <name> failed, ` prefix (AE-FROM 546, 713), giving the shape in the brief: `Error in $.a[0].b: parsing Int failed, expected Number, but encountered String`. Accumulating all errors is open issue #578 (2017, "help wanted"); a maintainer's objections there: "`Validation` isn't a `Monad`. How would you write e.g. tagged sum encoding parser?" and "For untrusted input, one should fail reasonably fast, so the service isn't easily DDOSed." (<https://github.com/haskell/aeson/issues/578>). Alternatives: `mplus a b` runs `b` with the original failure continuation and discards `a`'s error (AE-INT 332–337), so `p <|> q` reports only `q`'s failure; the `UntaggedValue` doc says so: "Only the last error is kept when decoding, so in the case of malformed JSON, only an error for the last constructor will be reported." (AE-INT 794–795).
- **D. null vs absent: three operators.** `.:` "appropriate if the key and value *must* be present"; `.:?` "The result is 'Nothing' if the key is not present or if its value is 'Null'"; `.:!` "differs from '.:?' by attempting to parse 'Null' the same as any other JSON value, instead of interpreting it as 'Nothing'." (AE-FROM 846–871). Defaults: `o .:? "k" .!= def`. Generic deriving: "'Maybe' fields are optional regardless of the value of 'omitNothingFields'", and `allowOmittedFields = True` by default (AE-INT 723–737, 856). So derived decoders collapse null and absent; only hand-written `.:!` separates them. `omitNothingFields` (default `False`) is an *encoding* option: `Nothing` is written as `null` unless set.
- **E. Input.** Bytes by default: `eitherDecode :: FromJSON a => LBS.ByteString -> Either String a`, `eitherDecodeStrict` on strict `ByteString`, and since 2.2.1.0 `eitherDecodeStrictText` on `Text` (AE-DEC; AE-LOG 2.2.1.0). Invalid UTF-8 inside a string fails in the tokenizer via `unescapeText`, whose error description is `Data.Text.Internal.Encoding.decodeUtf8: Invalid UTF-8 stream` (AE-TOK 150–155; <https://github.com/haskell/aeson/blob/master/src/Data/Aeson/Internal/Unescape.hs> line 38). "The parser does not (and will not) support UTF-16, UTF-32, or byte order marks (BOM)." (AE-LOG, 1.1.0.0 notes). Trailing data: `Left "Trailing garbage"` (AE-DEC line 52). Duplicate keys: the current decoder comment reads "the first duplicate key in objects wins" (AE-CONV 82–84); the attoparsec-era parser also warned "If an object contains duplicate keys, only the first one will be kept" and offered `jsonWith`, `jsonLast`, `jsonAccum`, `jsonNoDup` to choose (<https://github.com/haskell/aeson/blob/master/attoparsec-aeson/src/Data/Aeson/Parser/Internal.hs>). Note first-wins is the opposite of `JSON.parse`. Numbers are parsed to arbitrary-precision `Scientific`; `Int` decoding fails rather than rounds: `value is either floating or will cause over or underflow <n>` (AE-FROM 205–209); unbounded integrals: `unexpected floating number <n>` (line 199).
- **F. Same type (`String`), different shape.** Syntax errors are bare tokenizer messages such as `Unexpected end-of-input, expecting JSON value`, `Number literal with leading zero` (AE-TOK); shape errors carry the `Error in $...: ` prefix (AE-DEC 48–53). Distinguishable only by string inspection.
- **G. Tagged unions.** `SumEncoding` = `TaggedObject {tagFieldName, contentsFieldName}` (default `"tag"`/`"contents"`), `UntaggedValue`, `ObjectWithSingleField`, `TwoElemArray` (AE-INT 769–806). TaggedObject reads the tag key first, then dispatches. Unknown tag: `expected tag field to be one of ["Foo","Bar"], but found tag "Baz"`, located at the tag key (`badTag tag <?> Key tagKey`, AE-FROM 1216–1223). Missing tag key: context `expected Object with key "tag"` … over `key "tag" not found` (AE-FROM 994–1001; exact joined text not measured). A missing field inside a known member is the ordinary B error, so it names the field but not which member was selected. `UntaggedValue` tries constructors "in the order of definition. If some encodings overlap, the first one defined will succeed" and reports only the last failure (C).
- **H. Derived (GHC Generics or Template Haskell) or hand-written; one `Options` value feeds both `genericToJSON` and `genericParseJSON`,** but nothing forces the two instances to use the same options, and the decoder is deliberately more lenient than the encoder (Maybe fields, unknown keys).
- **I. Security and regrets.** (1) Hash flooding: aeson objects were `HashMap` from unordered-containers over FNV; FP Complete's write-up: a 5 MB colliding object took about 2 min 18 s against 0.3 s, and "The `aeson` library is not safe to use to consume untrusted input." (<https://cs-syd.eu/posts/2021-09-11-json-vulnerability>). Response: aeson 2.0 made the object map abstract (`KeyMap`), added the `ordered-keymap` flag, and "Make `ordered-keymap` on by default" in 2.0.1.0 (AE-LOG); Tweedale's summary notes `HashMap` itself "remains vulnerable to hash flooding attacks" (<https://frasertweedale.github.io/blog-fp/posts/2021-10-12-aeson-hash-flooding-protection.html>). This was a breaking major release caused by one data-structure choice leaking into the public `Value` type. (2) Big-number DoS: "Fix DoS vulnerabilities caused by parsing large numbers (advisory HSEC-2026-0007)", fixed by rejecting large exponents (AE-LOG 2.3.0.0 / 2.2.5.1); arbitrary-precision numbers are the cost of never rounding. (3) Paths lost by entry point: a 2023 Discourse thread found `eitherDecode` keeps the path while `fromJSON`/`parse` drops it, so Yesod users saw "parsing Int failed, value is either floating or will cause over or underflow 0.24" with, in the poster's words, "no information about which field was not correct" (<https://discourse.haskell.org/t/good-error-messages-when-parsing-json/7247>).

## 3. OCaml: `yojson` + derivers

Two steps, always: `Yojson.Safe.from_string` (text → tree, raises `Json_error`) and then a derived `t_of_yojson` (tree → value).

- **A. Unknown keys: rejected by default in both derivers.** ppx_deriving_yojson: "By default, objects are deserialized strictly; that is, all keys in the object have to correspond to fields of the record. Passing `strict = false` ... changes the behavior to ignore any unknown fields." (PDY README). ppx_yojson_conv: `[@@yojson.allow_extra_fields]` "lets one specify that the yojson-converters should silently ignore extra fields, instead of raising. This applies only to the record to which the annotation is attached, and not to deeper yojson converters" (PYC). Example from PYC: `type t = { a: int } [@@deriving yojson]` with `{"a":1,"b":2} => exception`. No capture of extras in either.
- **B. Missing required field.** ppx_deriving_yojson returns `Error <dotted OCaml path>`: the generator emits `error (path @ [name])` for a field with no `[@default]` (PDY source, `desu_str_of_record`). The test suite shows the form: `Error "Test_ppx_yojson.geo.lat"` (PDY tests line 226). That is a path through the *type declaration* (module.type.field), not through the *data*: no array indices, and the JSON key (`"Latitude"` via `[@key]`) is not what is printed. ppx_yojson_conv raises `Of_yojson_error (Failure msg, json)` with `"%s_of_yojson: the following record elements were undefined: %s"` (PYC errors line 72), naming all missing fields at once and attaching the offending JSON subtree.
- **C. First error; weak structure.** ppx_deriving_yojson: `(t, string) result` where the string is only the type path; an extra key in strict mode returns the *record's* path (`top_error`), so the message does not say which key was unexpected, and a wrong-typed field and a missing field produce the same string. ppx_yojson_conv: message + offending subtree, no path; it does name extras: `"%s_of_yojson: %s: %s"` with `what` = `extra fields` or `duplicate fields` (PYC errors 51–60). Failed variant: `Error "Test_ppx_yojson.pvd"` for an unknown constructor (PDY tests 187); ppx_yojson_conv `..._of_yojson: unexpected variant constructor` / `no matching variant found` (PYC errors 40, 98).
- **D. null vs absent.** ppx_deriving_yojson: `option` ↔ "Null or 'a"; absence is only allowed with `[@default]` ("Fields with default values are not required to be present in inputs and will not be emitted in outputs."), so an `option` field without a default must be present (as `null`) per the generator (PDY). ppx_yojson_conv separates the two per field: `x : int option` encodes `None` as `"x":null`, `y : int option [@yojson.option]` omits it (PYC example: `{ x = None; y = None } => {"x":null}`). Decode behaviour for a missing plain `option` field in ppx_yojson_conv: not found in the README.
- **E. Input.** `Yojson.Safe` reads strings, channels, files, lexbufs. Integer overflow becomes `` `Intlit of string `` in `Safe` and `lexer_error "Int overflow"` in variants without INTLIT (YOJ read.mll 82–85). The lexer accepts non-standard `NaN`, `Infinity`, `-Infinity` and `/* */` comments (read.mll 149–167, 229); Tuple/Variant syntax extensions were removed as "a non-standard extension that was rarely used" (YOJ CHANGES). Objects are `` `Assoc of (string * t) list ``, so duplicates survive parsing; ppx_yojson_conv then rejects them (`duplicate fields`), and its README says "ppx_deriving_yojson support duplicated fields, while our library does not" (in ppx_deriving_yojson's generated loop a later key overwrites the earlier, i.e. last wins). Invalid UTF-8 and trailing-data handling: not found in the files fetched.
- **F. Distinct by construction.** Syntax is the `Yojson.Json_error` exception from the parser; shape is the deriver's `Error string` (or `Of_yojson_error`). The split falls out of the two-step API.
- **G. Tagged unions.** Variants are arrays, constructor name first: `[["A"],["B",42],["C",42,"foo"]]`; record variants `["X",{"v":0}]` (PDY). Selection is by that first string. No object-with-discriminator encoding is derived; that shape needs a hand-written `of_yojson`.
- **H. Derived, symmetric by default** (`[@@deriving yojson]` gives both directions; `of_yojson` / `to_yojson` alone are available). Symmetry is why `[@default]` fields are both optional on input and dropped on output.
- **I.** The strict default plus per-record (non-recursive) opt-out is the notable design choice; the error payload is the weak point (a type path string, or a message without a data path).

### ReScript (brief)

- `sury` (formerly rescript-schema): "By default **Sury** silently strips unrecognized keys when parsing objects. You can change the behaviour to disallow unrecognized keys with the `S.strict` function", message `Unrecognized key  "unknownKey"`; `S.deepStrict` applies it to nested objects; a global default exists (`defaultAdditionalItems: Strict`). Errors carry a path array and render as `Failed at items[0]`, with messages of the form `Expected string, received 123`. Unions: "the first one that fits the value wins." `S.option` models `undefined`; null is a separate schema (`S.nullable`, `S.nullAsOption`). One schema value drives both parse and reverse conversion (SURY).
- `bs-json` / `rescript-json-combinators`: Elm-style hand-written combinators; decoders originally raised a `DecodeError` exception, and the rewrite runs them through `Decode.decode` "in order to ensure that the `DecodeError` exceptions don't leak and returns a `result`" (<https://github.com/glennsl/rescript-json-combinators/blob/master/README.md>). A–I otherwise as Elm; details not fetched.

## 4. Scala: `circe` (brief)

- **A.** Ignored by default; derivation `Configuration(strictDecoding: Boolean = false)`, documented "Whether to fail when superfluous fields are found." (CIRCE-CFG). Strict failure text: `Strict decoding <Type> - unexpected fields: b, c; valid fields: a.` (assembled from CIRCE-CFGDEC lines 47–48, 135). It lists the valid fields, which the other libraries do not.
- **B.** `Reason.MissingField` renders as `Missing required field`; the cursor history includes the failed `DownField`, so the path points at the **missing field itself**: `DecodingFailure at .x: Missing required field` (CIRCE-ERR lines 85–86, 111).
- **C.** Fail-fast by default (`Decoder.Result = Either[DecodingFailure, A]`), with a parallel accumulating mode: `decodeAccumulating[A](input: String): ValidatedNel[Error, A]` (CIRCE-PARSER line 48) built on `Decoder#decodeAccumulating`, whose product instance collects sibling failures (CIRCE-DEC 290–291). Error = reason (`MissingField | WrongTypeExpectation(expected, jsonValue) | CustomReason`) + path. Wrong type: `Got value '"a"' with wrong type, expecting number`. Path is "JS style selections, i.e. \".foo.bar[3]\"" (CIRCE-OP). `a or b`: fail-fast returns only `b`'s error; accumulating returns both (CIRCE-DEC 297–308).
- **D.** `Option[A]`: null → `None`, key absent → `None`, wrong type → failure (`OptionDecoder`, CIRCE-DEC 1014–1028). Collapsed by default; hand-written cursor code can distinguish.
- **E.** `decode` takes a `String` (CIRCE-PARSER). Bytes, invalid UTF-8, duplicate keys and big-number handling live in the jawn parser module: not fetched **(unverified)**.
- **F. Distinct.** `sealed abstract class Error` with `ParsingFailure` and `DecodingFailure` (CIRCE-ERR).
- **G.** `discriminator: Option[String] = None`. Without it, a sum is a single-key wrapper object keyed by constructor name; with it, a field in the object. Unknown: `type <T> has no class/object/case named '<name>'.`; missing: `<T>: could not find discriminator field '<d>' or its null.` (CIRCE-CFGDEC 62, 73).
- **H.** Derived (macros / Scala 3 `derives`) or hand-written; `Codec` pairs both directions under one `Configuration`.
- **I.** Not researched beyond source.

## 5. Cross-cutting: what the JSON RFCs require

Sources: <https://www.rfc-editor.org/rfc/rfc8259.txt>, <https://www.rfc-editor.org/rfc/rfc7493.txt>.

- **Duplicate names, RFC 8259 §4:** "The names within an object SHOULD be unique." and "When the names within an object are not unique, the behavior of software that receives such an object is unpredictable. Many implementations report the last name/value pair only. Other implementations report an error or fail to parse the object, and some implementations report all of the name/value pairs, including duplicates." All three behaviours appear above: JS/Elm last-wins, aeson first-wins, ppx_yojson_conv error, yojson keeps all.
- **Numbers, RFC 8259 §6:** "This specification allows implementations to set limits on the range and precision of numbers accepted." and "numbers that are integers and are in the range [-(2**53)+1, (2**53)-1] are interoperable in the sense that implementations will agree exactly on their numeric values." JSON has one number type; int vs float is the decoder's decision.
- **Encoding, RFC 8259 §8.1:** "JSON text exchanged between systems that are not part of a closed ecosystem MUST be encoded using UTF-8 [RFC3629]." and "implementations that parse JSON texts MAY ignore the presence of a byte order mark rather than treating it as an error." §8.2 notes the grammar admits unpaired surrogates such as `"\uDEAD"` and that "The behavior of software that receives JSON texts containing such values is unpredictable".
- **Parser latitude, RFC 8259 §9:** "A JSON parser MUST accept all texts that conform to the JSON grammar. A JSON parser MAY accept non-JSON forms or extensions." It also permits limits on text size, nesting depth, number range, string length.
- **I-JSON, RFC 7493**, is the strict profile: §2.1 "I-JSON messages MUST be encoded using UTF-8" and strings "MUST NOT include code points that identify Surrogates or Noncharacters"; §2.2 a sender "cannot expect a receiver to treat an integer whose absolute value is greater than 9007199254740991 ... as an exact value" and "it is RECOMMENDED to encode them in JSON string values"; §2.3 "Objects in I-JSON messages MUST NOT have members with duplicate names."; §3 lets receivers "reject or otherwise disregard messages that do not conform". The same RFC is on the *open* side for unknown members (§4.2, below).

## 6. Cross-cutting: error-path notation

- **JSON Pointer, RFC 6901** (<https://www.rfc-editor.org/rfc/rfc6901.txt>): §3 "a sequence of zero or more reference tokens, each prefixed by a '/'"; "'~' needs to be encoded as '~0' and '/' needs to be encoded as '~1'". Root is the empty string. A token does not say whether it is a key or an index (`/a/0`).
- **JSONPath, RFC 9535** (<https://www.rfc-editor.org/rfc/rfc9535.txt>) is a query language; its §2.7 *Normalized Path* is the single-location form: "a unique representation of the location of a node", "Normalized Paths use the canonical bracket notation, rather than dot notation", e.g. `$['book'][3]`. Keys and indices are syntactically distinct.
- **Who uses what** (from the sources above): aeson: Goessner-style JSONPath with dots, `$.a[0].b` (predates and is not RFC 9535 normalized form). Elm: `json.a[0]`. circe: `.foo.bar[3]`. sury: `items[0]` plus a segment array. ppx_deriving_yojson: OCaml type path, not a data path. RFC 9457's example and JSON:API: JSON Pointer. FastAPI/Pydantic: a segment array `["body","size"]`. None of the ML-family libraries emits JSON Pointer.
- **Where a missing field points** differs: aeson and Elm report at the parent with the key in the message; circe reports at the missing key. JSON:API takes a side: `source.pointer` "MUST point to a value in the request document that exists; if it doesn't, the client SHOULD simply ignore the pointer." (<https://jsonapi.org/format/#error-objects>), which implies parent-pointing for a missing member.

## 7. Cross-cutting: reporting a validation error to an HTTP client

- **RFC 9457 §3** (<https://www.rfc-editor.org/rfc/rfc9457.txt>) shows a 422 `application/problem+json` body with an `errors` extension: `{"detail": "must be a positive integer", "pointer": "#/age"}` and `{"detail": "must be 'green', 'red' or 'blue'", "pointer": "#/profile/color"}`; "Each member is an object containing \"detail\" to describe the issue and \"pointer\" to locate the problem within the request's content using a JSON Pointer". `errors`/`pointer` belong to a "fictional problem type", so they are an illustration rather than a registered standard. It is a list, so the convention assumes several errors can be returned. §3.2: "Clients consuming problem details MUST ignore any such extensions that they don't recognize".
- **JSON:API**: `source.pointer`, "a JSON Pointer [RFC6901] to the value in the request document that caused the error", e.g. `"/data/attributes/title"` (URL above).
- **FastAPI/Pydantic**: `{"detail":[{"loc":["body","size"],"msg":"value is not a valid integer","type":"type_error.integer"}]}`; first `loc` element is the request part, the rest the path (<https://fastapi.tiangolo.com/tutorial/handling-errors/>). A segment list avoids every escaping question and keeps key-vs-index typed.

## 8. Cross-cutting: open vs closed objects

**The case for rejecting or at least never guessing (closed, strict):**

- Bishop Fox, Jake Miller, "An Exploration & Remediation of JSON Interoperability Vulnerabilities", 2021-02-25 (<https://bishopfox.com/blog/json-interoperability-vulnerabilities>). Five categories: "Inconsistent Duplicate Key Precedence", "Key Collision: Character truncation and Comments", "JSON Serialization Quirks", "Float and Integer Representation", "Permissive Parsing and Other Bugs". The attack needs two services that parse the same bytes differently: a cart validator with last-key precedence and a payment service with first-key precedence, ending "We will be shipped six products of a value of $700, but we were charged only $300". Large numbers "may be decoded as `MAX_INT` or `0`". Recommendations to parser authors: "Generate fatal parse errors on duplicate keys.", "Do not perform character truncation.", "provide a \"strict\" mode that adheres to the RFC 8259 (or relevant) definition", "Produce errors when handling integers or floating-point numbers that cannot be represented faithfully." Note what is absent: the article is about duplicates, numbers and lenient *syntax*; it does not argue for rejecting unknown keys.
- Mass assignment (OWASP cheat sheet, <https://cheatsheetseries.owasp.org/cheatsheets/Mass_Assignment_Cheat_Sheet.html>): frameworks "automatically bind HTTP request parameters into program code variables"; the example appends `isAdmin=true`. Remedy: "Prefer dedicated input objects, such as Data Transfer Objects (DTOs), containing only fields the caller may edit." The harm comes from *binding* unknown input, not from ignoring it; a decoder that validates against a declared type and drops the rest is already the DTO remedy. The sheet does not say whether to reject or ignore extras.
- RFC 9413, "Maintaining Robust Protocols" (IAB, <https://www.rfc-editor.org/rfc/rfc9413.txt>): §2.1 "ignoring faulty or ambiguous input is almost always the incorrect solution to the problem."; §4.2 "Tolerating unexpected input instead conceals problems, making it harder, if not impossible, to fix them later."; §5.1 "Choosing to generate fatal errors for unspecified conditions instead of attempting error recovery can ensure that faults receive attention." It separates this from extensibility, §2.2: "The ability to extend a protocol is sometimes mistaken for an application of the robustness principle." and "A well-designed extensibility mechanism establishes clear rules for the handling of elements like new messages or parameters ... New messages or parameters thereby become entirely expected." So RFC 9413 condemns tolerating *malformed* input and endorses *specified* ignore-unknown.
- Practice: OCaml's two derivers are strict by default; ProtoJSON parsers "should reject unknown fields by default but may provide an option to ignore unknown fields" (<https://protobuf.dev/programming-guides/json/>); aeson's own changelog recommends `rejectUnknownFields` to "find errors during development" (a misspelt optional key is otherwise silently dropped).

**The case for ignoring (open, tolerant):**

- RFC 7493 §4.2, "Must-Ignore Policy": "when an implementation encounters a protocol element that it does not recognize, it should treat the rest of the protocol transaction as if the new element simply did not appear, and in particular, the implementation MUST NOT treat this as an error condition. The converse \"Must-Understand\" policy ... in general it has been found to be overly restrictive and brittle." and "specify that members whose names are unrecognized MUST be ignored."
- Fowler, "TolerantReader", 2011-05-09 (<https://martinfowler.com/bliki/TolerantReader.html>): "be as tolerant as possible when reading data from a service", "only take the elements you need, ignore anything you don't", "Your aim should be to allow the provider to make any change that ought not to break your code."
- Protobuf binary: "Proto3 messages preserve unknown fields and include them during parsing and in the serialized output" (<https://protobuf.dev/programming-guides/proto3/>); preserve-and-forward is a third option beyond ignore/reject, and it is lost on conversion to JSON ("Serialize a proto to JSON.").
- Public API contracts treat added response fields as non-breaking. GitHub lists "Adding a response field" and "Adding enum values" among additive changes and says "Any additive (non-breaking) changes will be available in all supported API versions." (<https://docs.github.com/en/rest/about-the-rest-api/breaking-changes>). Stripe's upgrade guide has the same classification (new properties on responses are backward-compatible) per a search summary; the current page no longer carries the list and the archive copy returned 403, so the wording is **(unverified)**. A strict client of either API breaks on a routine provider deploy.
- Practice: Elm, aeson, circe and sury all ignore by default.

**Reading the two sides together.** The sources mostly do not collide: the security material targets duplicate keys, number fidelity and lenient syntax; the tolerant-reader material targets unknown *members* in data you consume from someone who may evolve it. The direction of the message matters (a server reading a request it defined vs a client reading a provider's response), and "added enum values" is the unknown-member problem for tagged unions.

## What stands out

1. **Unknown keys split by family, not by era:** Elm/aeson/circe/sury ignore; both OCaml derivers and ProtoJSON reject. Every library that has a switch makes it per-type, and ppx_yojson_conv's is explicitly non-recursive. None of the ignoring libraries can hand back the extras through a derived decoder.
2. **No library surveyed rejects duplicate keys by default except ppx_yojson_conv,** and the silent ones disagree (aeson first-wins, JS/Elm last-wins): the exact disagreement Bishop Fox exploits, and the one thing both I-JSON (§2.3) and Bishop Fox say to make fatal.
3. **A missing field is reported in two places:** at the parent with the key in the message (aeson `key "x" not found`, Elm) or at the missing key (circe `.x: Missing required field`). JSON:API's "MUST point to a value ... that exists" favours the parent. A `{Path, Expected}` design has to pick.
4. **"Expected" is free text everywhere except circe,** which has a small reason type (`MissingField | WrongTypeExpectation(expected, value) | CustomReason`). Elm and ppx_yojson_conv attach the offending *value*; aeson keeps a structured path internally and flattens it to a string at the public edge, and loses it on some entry points.
5. **First-error is the norm;** circe is the only one with a parallel accumulating API, and aeson's maintainers resisted it on DoS and monad grounds (#578). The HTTP conventions (RFC 9457 example, JSON:API, FastAPI) all carry a *list*.
6. **Untagged alternatives give the worst errors:** aeson `<|>` and circe fail-fast `or` keep only the last branch's failure; Elm's `OneOf (List Error)` keeps all and is verbose. Tag-first dispatch gives a precise error (`expected tag field to be one of [...], but found tag "Baz"` at the tag key), which a type system with string-literal tags can do without configuration.
7. **null vs absent is conflated by every derived decoder** (aeson `Maybe`, circe `Option`); telling them apart needs a hand-written operator (`.:!`) or a per-field annotation (`[@yojson.option]`). Elm's `maybe` shows the cost of an optional combinator that also swallows type errors.
8. **Syntax vs shape:** distinct types in circe and (by two-step API) OCaml; one type in Elm and aeson, distinguishable only by message text.
9. **Numbers:** aeson and yojson never round silently (`Scientific`, `` `Intlit ``) and aeson paid for it with a 2026 big-number DoS advisory; JS-backed Elm rounds 2^53+1 silently and accepts `1.0` as `Int`. RFC 8259 §6 and I-JSON §2.2 put the exact-integer line at ±(2^53−1).
10. **The only non-derived design (Elm) derives anyway at flags/ports,** and its users bypass that to get a recoverable error value: the demand is for derivation *with* a returned error, not a thrown one.
11. **Path notation:** nobody in the ML family emits JSON Pointer; HTTP conventions do, or use a segment array. A segment list (`["a", 0, "b"]`) converts to either and keeps key vs index typed.
