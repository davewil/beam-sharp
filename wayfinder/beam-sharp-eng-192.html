Who Writes The Tag

A record has to erase to something, and every candidate needs a way to tell two same-shaped records apart. That is a tag — and the whole decision turns out to rest not on which erasure carries one, but on whether the compiler or the author puts the value in it.

The fork — not yet decided

Map or tuple is the visible question. The one that decides it is whether a record’s tag is synthesised from its type name.

If the compiler derives the tag from the name, then type Order and type Invoice over identical fields become different terms and therefore different types — which is nominality, and ticket 09 ruled it out. If the author writes the tag as an ordinary field, nothing is violated: that is ticket 09 §5’s own newtype remedy. The erasure then follows from the answer rather than driving it.

The correction this brief exists to make

My first framing of this question said a tagged map was “nominality in the data, the same objection as the tuple tag”. That was too strong, and it is worth recording that ticket 09 made the identical over-reach — it first wrote “dispatch cannot key on a name”, and amended it on 2026-08-12 after David raised Elixir’s structs. The amendment reads: Elixir puts the name in the term as an atom and dispatches on it, which is §5’s tag remedy at ecosystem scale.

That amendment is now verified at the level of the type representation rather than inferred from behaviour. Reading Module.Types.Descr directly — following ticket 10’s precedent of measuring Elixir’s checker rather than citing it — an Elixir struct type is an open map with the tag as an atom singleton:

%% Module.Types.Descr, Elixir 1.19.5 -- the type of a struct-shaped map
%{map: {:open, %{id: %{bitmap: 4},
                 __struct__: %{atom: {:union, %{Order => []}}}}}}

%% two struct types, same fields, different tags
Descr.empty?(Descr.intersection(order_t, invoice_t))  => true   %% disjoint
%% the same two with the tag removed
Descr.equal?(order_no_tag, invoice_no_tag)            => true   %% identical

So there is no nominal construct anywhere in it. Elixir’s struct “nominality” is structural discrimination on a singleton atom field, and the singleton atom is something beam-sharp already has — ticket 10 made :ok a singleton type and the atom universe open. A tagged map needs no new machinery in this language at all.

What the erasure costs, measured

Ticket 18 measured the tuple discriminator at +13 bytes and asserted — without measuring — that a map’s would be “strictly larger”. It is, but the shape is friendlier than assumed, and the tagged map lands within one byte of the tuple.

Two mechanisms explain the surprises. The exact-set check does not emit a test per field — the BEAM has a single has_map_fields instruction carrying the whole key list, so the +1 B/field is operand growth, not work. And map_get/2 on an absent key fails a guard silently rather than raising (measured, with a runtime-built key so the compiler could not fold it), which is why one test is a complete discriminator for a tagged map: no is_map, no map_size, no per-field presence check.

What Elixir actually enforces

Elixir is the largest shipped instance of “erase a record to a map with a name in it”, which makes its field-set discipline evidence rather than analogy. Measured on 1.19.5, it is weaker than its reputation, and in a direction that matters here.

The finding that cuts against beam-sharp’s current position. Elixir types a struct as an open map and does not enforce exactness on the term at all. Ticket 27 §7 declined row polymorphism, which makes a beam-sharp record an exact field set — and exactness is precisely what costs +29 bytes instead of +14, because a map pattern is open (measured) and only map_size can close it.

So the ecosystem-scale precedent went the other way on the one sub-decision that carries the cost. That is not an argument to follow it — Elixir has no exhaustiveness guarantee to protect — but it means exactness is a beam-sharp-specific cost with no shipped precedent, and it should be paid deliberately rather than inherited.

The three jobs __struct__ does, and their fate here

  • no consumer

    Protocol dispatch

    Dead already, and not on this ticket. Ticket 16 refused every ad-hoc polymorphism construct; open extension needs whole-program consolidation, which fights ticket 13’s aggregate granularity and hot code loading. 16 also found the static-closed variant “not dead, but empty” — consolidation by construction is only available over a closed union, at which point there is nothing left to consolidate.

    So: a beam-sharp tag would carry no dispatch. It is the job that justifies __struct__’s existence in Elixir, and beam-sharp has already declined it.

  • live, and cheap

    Discrimination inside a union

    Ticket 09 requires union members to be discriminable by a synthesised BEAM guard, checked at the declaration. Under a plain map that means value inspection (+44 B measured); under a tagged map it is one map_get (+14 B). This is the job the tag genuinely does here, and it is discrimination, not dispatch — worth keeping the words apart.

  • live, and unowned

    Identity — that an Order is not an Invoice

    This is ticket 09’s named newtype gap. 09 said tags cover it and pointed at refinement types as the alternative; ticket 20 came back and handed it straight back — “a refinement is a set, so Meters and Feet are still one type and 09’s tuple tag stands”.

    Nobody owns the spelling. 09 → 20 → back to 09, and no ticket has ever written down how an opt-in tag is actually spelled. The record surface is the natural home for it, which makes it plausibly this ticket’s — and Elixir’s defstruct is the precedent that it can be blessed syntax rather than hand-written ceremony in every literal.

What is being asked

1. Is the erasure a map — accepting ~+16 bytes per boundary guard and ~1.7 ns per guarded projection over a tuple, in exchange for ticket 09’s aliasing rule holding at the term level, direct json:encode, and Elixir structs arriving without conversion?

2. Is a discriminating tag always the author’s, written as an ordinary field — or does the compiler synthesise one from the type name, which buys +14-byte discrimination and the newtype distinction, at the cost of ticket 09’s rule that two names over one set are one type?

3. If the tag is the author’s: does this ticket also owe it a blessed spelling — the unowned seam between 09 and 20 — or does that graduate as its own ticket?
