Values, Not Coverage

The map assumed a proved exhaustiveness guarantee would mean fewer tests. It means differently-shaped ones. And the ticket’s single strongest hope — generators for free, out of the type declarations — was resting on a word in an error message that does not mean what it says.

The decision

Exhaustiveness converts coverage tests into value tests. It does not delete them.

Four categories genuinely retire. But ticket 23 has the compiler synthesise the missing clause head and never the body — so at the same rate coverage questions disappear, guessed bodies appear. The spec must say this out loud, because a codebase that believes the reduction skips the value tests the compiler never had.

Where a test attaches

Ticket 13 made the directory the BEAM module, which quietly dissolved the obvious answer: “test the exported surface” does not discriminate, because the client API and the OTP callbacks are exported from the same .beam — the latter only because OTP requires it.

So the unit is the client API function against a running process. Three beam-sharp facts push harder here than the general heuristic does. The callback is the most compiler-owned function in the language — ticket 14 checks its signature against the GenServer contract, 04 proves its clauses exhaustive, 23 synthesises its missing heads, 18 writes code into code_change/3 — so asserting “an unknown request is rejected” against it tests the compiler. Hand-building a state to pass it constructs an aggregate no production path ever constructed. And moving a guard from HandleCall up into Apply is behaviour-preserving, which only the client-API test survives.

The cost is real and was measured on the other side. Ticket 15 found that reaching a crash path through the process means killing a real process and reading a monitor's exit reason. That is heavier than calling a function, and it is exactly why almost everyone tests the callback directly. Paid anyway.

The retraction

Ticket 24 §3 asked whether CDuce’s sampled counter-value is good enough to be a property-test generator — uniform enough, hits edge cases, terminates on recursive types — and suggested splitting it into a research ticket. It did not need one. Ticket 29 left a cduce:0.6.0 image on this machine, so it was measurable in ten minutes.

51--100, not 51. [ Int ], not [7]. And --help carries no flag that asks for an inhabitant — the only route to a “sample” at all is provoking a type error, and what comes back is the residual formatted into a string. There is no inherited generator. Nobody shipped one.

Two findings outlast the retraction. The recursive case terminates by emitting a binder rather than unrolling to a depth — which makes ticket 09’s contractivity requirement, adopted for subtyping decidability, also the property that would make a generator terminate. And the product case is partial: the true residual of (S,E) \ (`open,`add) is (`closed|`void,E) | (`open,`remove|`ship), and CDuce printed one rectangle, because proving non-subtyping is all its error reporter needs. beam-sharp’s checker computes the full residual, so this is a shortcut it does not inherit.

The last irony is the useful one: CDuce formats its residual into a string at exactly the point a consumer wants it — which is the failure ticket 23 measured in erlc and refused. beam-sharp’s residual is a term by decision, so the language publishes it and generates nothing, and value generation becomes an out-of-scope library standing on an in-scope guarantee. Ticket 27 §8 bounds that library before it exists: a codegen obligation requires a ground type argument, so generation happens at ground instantiations or not at all — which settles the ticket’s own open (a)/(b)/(c) about polymorphic signatures.

What a test can actually observe

Making the client API the boundary makes every test concurrent, which makes determinism the language’s problem rather than a test framework’s. A fire-and-forget cast has no reply to wait on. Two candidates: a following client-API call, or sys:get_state/1 reaching past the API into the state.

sys:get_state/1 buys no determinism whatsoever — rows one and two are identical, because both are messages riding the same ordering guarantee. Its only purchase is visibility into state the client API does not expose, which is the implementation test through the back door, and the read half of the channel ticket 18 already named a limit. A test reaching for it is a defect, and not even a useful one.

Row three is the trap. A cast sent from a process other than the observer passed 200/200 — not because it is ordered, but because gen_server:call sets up its monitor before sending and hands the caster an accidental head start. Twenty milliseconds flips it to 0/200. That is a test that passes two hundred times locally and fails in CI, and nothing in the type system can see it.

The harness caught itself doing the thing it was measuring. The first version of row three had the caster signal the observer before it called — a happens-before chain that removed the race. It reported 200/200 like every other row and could not have recorded a miss if one existed. That is this ticket’s own “erasable precondition” failure, reproduced while measuring it. The positive control exists for that reason and is the only row proving the other three mean anything.

The seven decisions

Numbered because they are ordered, not to look ordered: 2 exists only because 1 named a boundary the compiler could not see, and 5 and 6 are both consequences of 2 having bought the classification already. Read out of sequence they stop justifying each other.

  1. Decided

    1 · The unit is the client API against a live process

    The OTP callback is not a test target by default. Carve-out unchanged: a genuinely complex operation whose edge the client API cannot reach, and only that edge.

    Rejected: “any exported function of the aggregate” — it makes the boundary a matter of taste per test, and under agent authorship the agent picks whichever is easier to write, which is always the callback.
  2. Decided

    2 · The boundary is published, contract as discriminator

    Ticket 14 already has the compiler know the GenServer contract as a type, so it can name every callback and call the remainder the client API — with no visibility feature at all, which is why this does not wait on the deferred ticket 22.

    Left open on purpose: RecomputeTotal is neither, and stays unclassified. Inventing a visibility rule here would answer ticket 22’s question from the wrong ticket.
  3. Decided

    3 · Four categories retire; the count does not fall

    Retired: unknown-case rejection (04); error-channel distinguishability, since option<atom> does not compile (15 §1); per-instantiation tests of a polymorphic function, since opaque type variables make one ground instantiation evidence about all of them (27 §2); and coverage of compiler-generated code, which is the compiler’s to test.

    Not retired: clause ordering among reachable clauses; guards the checker cannot credit, which the skeleton’s own soundness bug was; and everything foreign.

  4. Retracted

    4 · No inherited generator — publish the residual

    Ticket 04’s “sampled counter-value” is withdrawn. The language publishes the residual as a structured term; generation is an out-of-scope library on top of it.

  5. Decided

    5 · Every async operation owes a synchronous observation

    A constraint on the client API, not on a test framework. The manifest advises where one is missing — advisory, not an error, because a genuinely fire-and-forget aggregate (a logger, a metrics sink) has no natural observation and would be nagged forever.

  6. Decided

    6 · The compiler publishes its elisions

    beam-sharp has three erasable preconditions of its own, enumerable by decision: a literal is a string by construction so its UTF-8 check is elided (20 §4); a boundary guard is emitted only where the body would not object (18 §1); compiler-known prelude operations are inlined, so what runs is not what was called (17 §2).

    Decisions 2, 5 and this one consolidate into one boundary manifest — what the boundary is, what it promises, and what the compiler decided not to check. Named as one artefact deliberately: ticket 18 §5 priced a build artefact as something the spec must define, version and keep stable, and that is paid once here rather than three times.

  7. Decided

    7 · Tests are ordinary beam-sharp, no exemption

    The universal BEAM idiom is a partial destructuring bind whose crash is the assertion. It survives — (:error, atom) is an open residual, so ticket 12 permits the catch-all — but the failure arm must be written.

    Rejected: a test construct exempting partial matches. It is a second semantics for the headline guarantee, and ticket 12 already refused a uniform _ for putting that guarantee one character from being switched off invisibly.

What decision 7 costs, stated plainly

Elixir — the crash is the assertion 
# Crashes on :error, with a good report,
# and the crash IS the test failing.
{:ok, order} = Orders.fetch(pid)
beam-sharp — the arm is written 
switch Fetch(pid) {
    Order o => Assert(o.Total == 100),
    _       => Fail("expected an order")
}

Near-free to write under the standing constraint, and it earns its place on the read side, which carries full weight: the arm forces the test to state what it expected. But ticket 12 measured that the compiler’s emitted failure arm gives function_clause with the offending argument — a good crash report, free — and this idiom opts out of it at exactly the moment a test wants it. A hand-written Fail is only as good as what the agent typed.

What this leaves open

The manifest’s concrete format goes to the map’s fog rather than to a ticket, because what a consumer wants of it is exactly what ticket 25’s exemplars would show, and none exist yet. unclassified goes to ticket 22, which gains a concrete job its deferral note doubted it had: an agent writing tests in a loop targets unclassified helpers because they are the easiest thing in the directory to test. And where a test lives under one function per file goes to the module and namespace patch, since ticket 23 made the directory listing part of the API surface — a decision that turns test placement into an API question rather than a tooling one.

Ruled out of scope: the test runner and framework, already on the map’s tooling track — ticket 13 emits ordinary BEAM modules with specs, so any BEAM runner works and beam-sharp needs none of its own. And a mailbox-drain helper for ticket 14’s two-meanings-of-waiting problem, which is standard-library breadth.
