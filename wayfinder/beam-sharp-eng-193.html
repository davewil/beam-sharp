Carry, Don't Examine

The ticket asked whether the language has generics at all. It turned out to be three questions wearing one coat — and the answer to the one that was actually open costs less than the map feared, for reasons the map had already bought.

The decision

A type variable is a slot for values you carry. A union is a slot for values you examine.

Real prenex parametric polymorphism, in its smallest working form: variables are declared, opaque, unbounded, and never annotated for variance. No row polymorphism. The four refusals are not taste — they are what keeps instantiation cheap.

The question was three questions

Read as one binary, “does the language have generics?” is unanswerable: a flat no would have required re-spelling three closed tickets, which already write list<Json>, map<string, Json>, option<T> and ValidateAs<list<int>> on the page. Splitting it made only one branch live.

Why it is affordable here

The literature's frightening results attach to two things: inference, which is undecidable, and intersection-typed functions, where tallying instances get large and no complexity bound exists in any source the research reached. beam-sharp has neither — and not by luck. Both were refused in earlier tickets for entirely unrelated reasons, before this question was asked.

A beam-sharp function type is (A|B) -> (C|D), never (A->C) & (B->D), because ticket 08 settled same-arity dispatch as a union parameter rather than overload signatures. What remains at a call site is matching list<Order> against list<TSource> and reading off TSource = Order: structural, cheap, and the answer is unique.

The four rules

  • Rule 1

    Opaque in clause heads and guards

    A bare type-variable parameter admits exactly one clause: bind it. Structure around a variable matches freely, so nothing about Map is disturbed.

    Legal — structure around the variable 
    list<TResult> Map<TSource, TResult>(
    list<TSource>, fn(TSource) -> TResult);

([], _)       -> [];
([h, ..t], f) -> [f(h), ..Map(t, f)];
// exhaustive at the definition, for every
// instantiation: list<T> is [] | [T, ..list<T>]
    Rejected — inspecting the variable 
    TSource Pick<TSource>(TSource, TSource);

(x, _) when is_integer(x) -> x;   // error
(_, y)                    -> y;

error: guard inspects a value whose type
  is the variable `TSource`

    Two reasons, and the second is the one that generalises. First: TSource Pick<TSource>(TSource, TSource) tells a reviewer the whole story only while the variable is opaque — it returns one of its arguments, and which one cannot depend on the type. Allow the test and Pick(1, 2) returns 2 while Pick("a", "b") returns "a", from a character-for-character identical signature.

    Second: reachability stops being answerable where the function is defined. Given clauses when is_integer(x) then a catch-all, clause 2 is dead under Describe<int> and clause 1 is dead under Describe<string>. The compiler checks once, at the definition, knowing neither — so it must say nothing, warn about both, or defer to call sites in other files. This is ticket 04's distinction biting: exhaustiveness is absolute, redundancy is relative.

    Tier-3 divergence, recorded. C# permits if (x is int i) on a T; TypeScript narrows a generic with typeof. The permissive rule was fully available as a tier-1 borrow and was refused anyway — because beam-sharp checks clauses at the definition, a constraint the map imposed on itself, not one the theory imposed.
  • Rule 2

    Unbounded — capability constraints belong to ticket 16

    No where TSource <: .... A bound is almost always “this type must support some operation” — comparison, arithmetic, printing — which is ad-hoc polymorphism wearing a bracket. Adding it here would pre-decide ticket 16 badly, routing capability constraints through type-variable syntax before 16 has chosen how capabilities are expressed at all.

    The cost is honest: no generic Max or Sum until 16 resolves. Three things remain available — monomorphic functions per type, a union parameter (which is dispatchable, unlike a variable), and passing the capability as an argument: Max<TSource>(TSource, TSource, fn(TSource, TSource) -> bool) needs no bound, because the capability arrives as a value. That third move is the one ticket 14 made when it put the message type on the client API function rather than on the pid.

    Deferred with four requirements captured, the serious one being a cost measurement at showcase clause counts. Bounds are the feature that turns instantiation from matching into solving, so they cannot be adopted on taste.
  • Rule 3

    Declared, and named with C#'s T convention

    Declaration is forced, not chosen, by a fact neither neighbour shares: beam-sharp's builtin type names are lowercase — int, float, string, atom, term, list, map — while user types are PascalCase.

    Lowercase-implicit quantification (Gleam, ML) is therefore ambiguous here: in list<a>, is a a variable or a builtin you have not met? Gleam escapes this only because its builtins are Int and Float. Uppercase-implicit (Erlang's own specs) is worse — Order in a signature would become a fresh variable rather than your type. Naming follows C#'s convention, which is what tickets 10 and 11 already wrote: option<T>, ValidateAs<T>, ParseAtom<T>.

  • Rule 4

    Variance is not a concept in the language

    No in/out, and nothing inferred either — there is nothing to infer. C# needs annotations because its interfaces are nominal: the compiler is told that IEnumerable<Order> is usable as IEnumerable<term>. Ticket 09 abolished nominality, so list<Order> ≤ list<term> holds because every value in the first set is in the second.

    Ticket 11's measured arrow contravariance is the same phenomenon: nobody declared it and nobody could have declared it otherwise. Variance is emergent description, like “integers are ordered”. The one thing it carries is a diagnostic obligation — a failed containment must name the position that went the wrong way, not print two type expressions and leave an agent to diff them.

Two measurements, both with controls

An emitted polymorphic -spec is documentation, not enforcement

Ticket 13 obliges the compiler to emit a -spec for every function whose type is known. Ticket 27 asked to confirm rather than assume what a polymorphic one publishes. Erlang's spec grammar clearly accepts variables — Gleam emits them. Whether anything checks the relation is a different question.

OTP 28.5 · dialyzer against a PLT of erts/kernel/stdlib
Spec under testOffending expressionDialyzer
map([A], fun((A) -> B)) -> [B] hd(Ys) + 1, where B = binary() Silent — passed successfully
map_mono([integer()], ...) -> [binary()] hd(Ys) + 1, identical shape Caught — will never return

The control fires, so the probe is sensitive and the negative result is real: Dialyzer reads A and B as any().

This is a regression, not a neutral gap. A raw Erlang caller of a monomorphic beam-sharp function at least gets a warning if it runs Dialyzer. A caller of a polymorphic one gets nothing. Choosing generics made the boundary strictly weaker — so ticket 18 must not count the emitted spec as a defence for polymorphic functions, and its defence inventory now has to be taken per function kind, not per language.

Syntax recovers an element-type relation with zero polymorphism

roundtrip is Map — input integer(), output binary(), a genuinely different element type — with the relation preserved exactly, by an analysis that has no type variables anywhere in it. The relation survives because a comprehension is syntax the analyser sees through: the typing rule is written by the compiler rather than solved for. Route the same computation through an opaque fun argument and everything degrades to any().

Since the ticket chose real generics, this is not the mechanism the language relies on for Map. It is load-bearing elsewhere: it is why row polymorphism was declined. Record update is with / spread — also syntax, also typed structurally against a concrete record type — so the case that would have demanded a row variable is already covered. That matters, because the research flagged row polymorphism as an acknowledged open problem with completeness only for restricted solutions, under a note reading “every OTP state map wants it”.

What was rejected

  • Rejected

    Monomorphise per call site

    The ticket named this as the middle path. It does not survive contact with ticket 13. A specialisation has to be emitted somewhere, and both homes fail:

    In the caller's aggregate — List no longer owns its own code, a fix to Map requires recompiling every caller, and hot-loading List updates nothing. Ticket 13 chose the aggregate as the consistency unit for hot code loading, deliberately.

    In List's own aggregate — you must know every instantiation when List is compiled, which is whole-program compilation, against ticket 13's standing obligation that the frontend never depend on in-process compiler state.

    Monomorphisation is a whole-program technique — Rust, C++, MLton. The BEAM is separately compiled and hot-swappable per module. It works inside an aggregate and fails at exactly the boundary where a shared List.Map lives.
  • Rejected

    Row polymorphism

    Rules 2 and 1 already close the two doors it could arrive through: it cannot come as a bound, and it cannot come by inspection. It would have to be a second kind of variable — { Total: Money | r } — which is new machinery, not an extension of anything decided.

    Deferred with requirements. What is genuinely not expressible: a shared function over unrelated record types that happen to share a field. That is a capability constraint, so it goes where all the others went — ticket 16.

Consequences that were forced, not chosen

Codegen obligations require a ground type argument. ValidateAs<T> and ParseAtom<T> now look exactly like generic calls and are not — you cannot generate a structural check for a type nobody has chosen yet. So ValidateAs<TSource> inside a polymorphic function is rejected at compile time, joining ticket 11's existing rule that it rejects arrow types. Ticket 11's caution that neither mechanism is evidence of generics survives intact: generics exist, and these are still not it.

Polymorphic recursion is permitted — and Map is not an instance of it. Map calls itself at the same TSource/TResult: ordinary recursion inside a polymorphic function. Polymorphic recursion is calling yourself at different ones. The research records that inferring it is long known undecidable — but ticket 04 already made signatures mandatory, and the undecidability is about inference. A declared signature makes it straightforwardly checkable. The map gets the feature free because it had already paid for something else.

Downstream

Ticket 16 is unblocked, and inherits both a boundary and a debt. The boundary is this brief's title: parametric polymorphism is now the pass-through mechanism and is deliberately incapable of dispatch, so whatever 16 chooses, it cannot be “let a generic function look at its argument”. The debt is bounds, deferred here with four requirements.

Also propagated: 18 loses the emitted spec as a defence for polymorphic functions; 15 learns that option<T> and ValidateAs<T> are now different kinds of thing, and that a polymorphic function cannot perform boundary validation at all; 17 gains a measured lower bound for its comprehension typing rule, and the news that fold is not covered by it; 24 gains the observation that opacity makes testing at one ground instantiation defensible evidence about all of them; 26 now carries the weight of the row-polymorphism argument, since it rests on with/spread being compiler-visible syntax.

The map's borrow heuristic gained an amendment in David's words: resemblance, not reproduction. Tier 3 reads as “diverge deliberately”, not “diverge only as a last resort” — and rule 1 is the worked case, where the tier-1 borrow was fully available and was refused anyway.
