The Bare Pid

The ticket arrived recommending a process identifier parameterised by its message type. The recommendation was declined in one sentence — and the sentence was David's, not the analysis's.

The decision

Process identity is untyped. A pid is a pid.

The message type lives on the client API function's signature, where it was going to be written anyway. Five more decisions follow from refusing to put it anywhere else.

Why Pid[τ] could not be written here

Ticket 03 surveyed prior art and recommended Pid[τ] as “simple and probably necessary in some form”. Three things kill it, and they compound.

It is inexpressible. Ticket 09 settled that types are sets of values, that a name never enters the algebra, and that two names over the same set are the same type. A pid is one runtime value class with the payload erased — so pid<Order.Msg> and pid<Payment.Msg> denote the identical set and are therefore the same type. Gleam carries the phantom parameter only because its type system is nominal: Subject(msg) lowers to {subject, Pid, Ref} with τ gone.

It is unnecessary, which is the part the analysis missed and the question caught. Nobody writes Pid ! {apply, Id, E} in OTP; they call orders:apply(Server, Id, E). The message is constructed inside a client function whose own signature is checked, and the Request union that HandleCall proves exhaustive over is the same union the client API constructs. Both ends typed, at the two places a type was going to be written, with the pid left alone.

And it would not buy soundness. Ticket 21 established that no foreign caller can be ruled out, so a typed handle constrains only this language's senders while raw ! from Erlang goes through regardless.

The worry it was meant to address is mostly not a worry

The objection to a bare pid is that a client function declares a return type for a reply arriving from a process it cannot identify. Measured on OTP 28, five ways that can go wrong:

What actually happens when a client API is handed the wrong pid
CaseOutcomeReading
Right server{ok,<<"an order">>}Declared type holds

Wrong server, no such clause{'EXIT',unhandled}Crash — and the callee dies too

Four of the five are exits, which ticket 12's signature-directed stance already accepts and which no type could have prevented. Only the last returns a wrong value, and it needs two servers to accept the same request shape and reply with different types — ticket 06's silent unsoundness reappearing in the reply channel, and ticket 18's problem rather than this ticket's.

The platform is paying for the design. On a runtime without supervised isolated processes, “wrong recipient” degrades into arbitrary misbehaviour, so the type system has to carry process identity. On the BEAM, four of five failure modes are already crashes with well-formed exit reasons — so the type system can decline to model process identity and lose almost nothing. Same shape as ticket 12's finding that let-it-crash is how you spell partiality.

Gleam, measured rather than characterised

Ticket 03 flagged this as a known evidence gap and refused to fill it from memory. Gleam 1.18.1 with gleam_otp 1.3.0, on OTP 28:

  • Send side only

    Subject(msg) lowers to {subject, Pid, Ref}; send wraps as {Ref, Message}; the type parameter is erased. The receive side is a runtime map lookup keyed on {element(1, Msg), tuple_size(Msg)} — a dispatch table doing at runtime what a beam-sharp clause head does at compile time, keyed on precisely ticket 09's discriminability vocabulary.

  • No exhaustiveness at all

    The actor installs select_other(Unexpected). Unmatched messages are logged and discarded and the process survives. An ill-typed payload on a valid subject is not detected: 12345 entered a List(String) and came back out of a function spec'd -> binary().

  • The ref is real, and Gleam's own remedy removes it

    An anonymous subject's make_ref() tag genuinely is unguessable — sys:get_state returns user state only, so it could not be recovered. But process.new_name/1 + actor.named, Gleam's recommended fix for passing subjects around, replaces it with a registered atom that registered()/0 enumerates. Discovering it by registry diff and forging a well-typed message took four lines.

  • Both mailbox behaviours, neither named

    Low level, process.receive is a filter: three messages queued, the wanted one plucked from the middle, queue length 3 → 2. Actor level, it is dispatch, via the opt-in catch-all. A Gleam user's answer to “does my mailbox keep this message?” depends on which layer they called, and nothing in the type system says.

None of it transplants. beam-sharp cannot use the ref trick even in principle, because ticket 00 makes handle_call/3 the showcase and {'$gen_call', From, Request} is a public shape by construction. Alpaca's whole-call-graph inference is excluded by a decision already made: ticket 04 requires a declared input type, because a type built from the program makes the check vacuous — and inference over send sites cannot see the foreign sender ticket 21 says cannot be ruled out.

The contract is a type, and the user narrows it

[module: GenServer] names a contract the compiler knows as a type; the user writes a narrower callback signature and the compiler checks containment. This is ticket 21's finding cashed in — Roc's requires clause, recorded there as strictly better than Erlang's -callback.

It is not an invention. Dialyzer already does it, and its gap is exactly the half beam-sharp gets free:

Three callback specs through Dialyzer, OTP 28.5
What it declaresDialyzerReading
Return narrowed to {reply, integer(), state()}passedTicket 12's exact signature is already legal
Return outside the contractwarnedNames the gen_server callback in the diagnostic
Argument narrowed to request()passed — silentlyUnsound; function_clause at runtime

beam-sharp catches the third because containment here is function subtyping, which is contravariant in arguments — the relation ticket 11 already leans on when rejecting arrow types in ValidateAs<T>. One relation, both directions, no special case. This corrects prototype 01e, which wrote HandleCall(Request, From, State); the argument must be term.

Why the wide contract lost, in operational terms. OTP's real handle_call return is six alternatives, with Action a further seven-way union. If a callback carried that union, (:noreply, s) would always be available and always type-correct on an unrecognised request — and always a lie, since nobody will call reply/2. The caller then sits for five seconds and exits with {timeout, ...}: the failure reported in the wrong process, at the wrong time, with the wrong reason. The narrow signature turns that into an immediate raise in the server, which the supervisor sees with the offending message intact.

And it is the reversible choice, which is why it is safe to take now. Narrowing strictly contains the alternatives: a user who writes OTP's full union gets the wide behaviour exactly, and a project wanting a fixed narrow subset sets its scaffolding generator. Neither needs a language change. The reverse is a language change — under a fixed contract nobody ever wrote a narrowed signature, so adding narrowing later means adding the check and rewriting every callback.

A hole nothing in the design catches

Working out what handle_info actually looks like turned up a defect class that was not in the ticket. Ticket 11 makes the argument term; ticket 12 makes the catch-all mandatory and legal because that residual is open. Both are right. Together they mean a clause written with the wrong shape for a system message never fires, and the catch-all absorbs the message in silence.

The fix came from the question “prelude being a bit like Elixir Kernel special forms”, and it is better than the mitigation on offer. The prelude is stratified: ordinary aliases a user could have written (bool, option<T>) versus a compiler-known stratum they could not (ParseAtom<T>, ValidateAs<T>, and now Down, Exit, Timeout). Verified on Elixir 1.19.5: a module defining its own receive/1 macro still gets the special form at the call site.

Naming the type turns a mis-shape into a compile error. And because the compiler knows what produces a Down, calling Monitor with no Down handler in the compilation unit is an error — the hole closed rather than mitigated. This is not a second effect system: nothing propagates through signatures, it is a local query over one compilation unit, which ticket 13 made the aggregate.

The other three decisions, briefly

  • No async, no await, no Task

    “The goal is a C#-like language on the BEAM to take advantage of its concurrency model — seems pointless then to bring over C#'s.” The mechanical objection agrees: async colours functions and the colour propagates up the call graph, which is the second effect system ticket 12 already refused for Partial. The spec must state the omission, because a C# reader will go looking and silence reads as an oversight.

  • Closures-as-messages is inadmissible

    purerl/Pinto's generic callback module is not merely off-showcase. Ticket 11 made arrow types unvalidatable at a boundary, so a message carrying a closure is the rejected case exactly: guard-match is_function(F), call it, and unknown code with unknown types has run inside a construct that claims exhaustiveness. MFA-carrying messages are unaffected — {M, F, A} is guard-decidable data, and OTP's own child specs are built from it.

  • receive survives, as a filter

    Clause-headed syntax, exempt from exhaustiveness, because selective receive leaves unmatched messages in place — an unmatched message is not unhandled, it is not yet. Forcing a catch-all would delete the correlate-a-reply idiom gen_server:call itself runs on. Deleting receive was the live alternative and lost on consequences: without it spawn can only make processes that never read their mailbox, so the language would have exactly one way to make a concurrent thing, and it would be OTP or nothing.

What this does to the rest of the map

  • Ticket 27 loses a motivating case

    Pid[τ] was the clearest demand in the map for a genuine type parameter, and it is declined. Parametric polymorphism now rests on option<T>, ParseAtom<T> and ValidateAs<T> — which ticket 11 already flagged as type-directed codegen rather than generics. That materially changes 27's default answer.

  • Ticket 23 gains a policy knob

    Default callback signatures are a generator setting, not language semantics. Which means a project's narrow-versus-wide policy — and per ticket 12, its crash policy — is configuration.

  • Ticket 13's CI corpus gains two obligations

    The language now ships a model of OTP: behaviour contracts and system-message shapes, both tracking the pinned release range. Unmeasured — only OTP 28.5 was installed.
