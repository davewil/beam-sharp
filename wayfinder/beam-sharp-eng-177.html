The Term Boundary

The keystone ticket asked where dynamic is introduced. The answer is that it isn’t — because it doesn’t exist.

The guarantee

Every case your types admit has a clause — and everything from outside is a term until you match it.

beam-sharp checks that your clauses cover every value your signatures admit; it does not check where a value came from, so anything crossing the boundary is a term until proven otherwise.

Why there is no dynamic

The ticket body treated dynamic as a place — where is it introduced, what may you do there. Both shipping BEAM checkers treat it as something else entirely, and they disagree with each other. Measuring both was what dissolved the question.

Elixir makes it a type in the algebra: a field present on every descr, carrying a bound. That forces a second subtyping relation, because a sound one relates dynamic to nothing. Gleam makes it an opaque library type outside the checker: you enter by a free identity cast and leave through a decoder you wrote by hand.

beam-sharp takes neither. External values arrive typed term, and the only thing you can do with one is match it — so the clause head is the decoder. The exhaustiveness residual term \ (Acc(p₁)|…|Acc(pₙ)) stays non-empty until you have written the boundary case, which means the checker hands you the clause you forgot rather than describing it.

The design heuristic — borrow from C# first, the BEAM second, invent last — failed to discriminate here, and that is itself the finding. Tier one supplies a construct for both poles: C# has dynamic, TypeScript has unknown. Neither audience needs teaching either shape, so familiarity could not pick the winner and the eight-channel interop problem had to.

The five decisions

  1. Kept

    1  No dynamic; one relation, not two

    Subtyping stays plain set-theoretic containment, decided coinductively over the equirecursive types ticket 09 settled. Nothing in the algebra bends soundness, so no gradual judgement is needed.

    Rejected: Elixir’s pair model, which needs subtype? and compatible? — two relations to specify, implement and teach, in exchange for deliberate unsoundness that ticket 06 already showed can be silent.
  2. Kept

    2  Patterns over a term are O(1) guard-decidable only

    BEAM guards are the vocabulary — ticket 09’s discriminability rule extended verbatim rather than a new rule. list<term> is writable in a head; list<int> is not, because no O(1) guard decides element types. Deep validation is an explicit call to a compiler-generated ValidateAs<T>, the same type-directed codegen obligation ticket 10 established for ParseAtom<T>.

    // O(1) — is_list, and nothing more
f(list<term> xs) -> ...

// O(n), at a call site you can see
list<int> | :error ys = ValidateAs<list<int>>(xs);
    Rejected: emitting the traversal inside the clause head. The cost is O(n·depth) and the sender chooses n — ticket 06’s channels are mailboxes, ETS reads and decoded external terms, none of them yours. A construct that looks like constant-time dispatch must not become unbounded work chosen by a foreign process. Also rejected: checking is_list and trusting the elements, which is ticket 06’s silent unsoundness reintroduced one decision after dynamic was dropped to avoid exactly that.
  3. Closed

    3  ValidateAs<T> rejects arrow types at compile time

    A fun carries no runtime evidence of its signature. This is not a BEAM wart — a function’s type is absent from its runtime value in every language; it surfaces here only because validation was made first-class. And arrow subtyping is contravariant in the argument, so the top arrow is none() -> term(), whose parameter type is none: there is no value you can legally pass it.

    // measured, OTP 28
subtype?(fn(int)->int, fn(none)->term)  = true   // the top arrow
subtype?(fn(int)->int, fn(term)->term)  = false  // NOT a supertype

    So “narrow it to fn(term)->term and call it” is unsound — that type claims the fun accepts every term. A foreign fun is holdable and returnable to Erlang, never callable. The boundary is MFA, which is {atom, atom, int} and validates with no special case.

    Rejected: higher-order contract wrapping — the literature’s correct answer, and the only sound way to actually call a foreign fun. Turned down on the same hidden-cost grounds as decision 2, plus its need for blame tracking. Chosen partly for reversibility: wrapping is purely additive later and would invalidate no program written under this rule, whereas arity-and-trust is irreversible, since programs come to depend on the unsoundness.
  4. Kept

    4  The top type is spelled term

    A deliberate override of the borrow heuristic, recorded as the heuristic’s own third tier requires. In a set-theoretic system the top type is a set that participates in the algebra — the residual is computed by subtracting from it. unknown names an epistemic state, and you cannot take the complement of your own ignorance. It also keeps source and emitted -spec using one word rather than two.

    Rejected: unknown (TypeScript, tier one, free for half the audience); object, which drags C#’s root-class and boxing connotations into a language with neither; any, which in TypeScript is the unsound top, assignable in both directions.
  5. Kept

    5  The guarantee, stable under ticket 18

    The rejected candidate was the one that sounded most rigorous: “so long as every caller is beam-sharp, no function receives a value outside its declared type.” It fails because it pins the guarantee to who called you — which ticket 09 §5 already established the BEAM cannot enforce. Candidates pinned to shape survive whichever way ticket 18 decides, because guards check shape and never origin.

    Explicitly not decided here: whether the compiler emits defensive guards on a typed parameter against a foreign caller. That is ticket 18, and the sentence above is true either way.

What moved on the map

This was the keystone — seven tickets blocked on it — and it held at least six decisions, so it was split rather than answered thinly. It kept the boundary, the subtyping relation and the guarantee. Inference strength was not reopened: tickets 04 and 08 had already settled that signatures are mandatory.

27 — new—On the frontier. Does the language have generics at all, and are parametric aliases well-formed?

Two cautions carried forward. ParseAtom<T> and ValidateAs<T> both take a type argument, but neither is parametric polymorphism — <T> is a compile-time argument driving codegen, monomorphic at every use, with no type variable surviving into the algebra. Ticket 27 must not read them as evidence that generics already exist.

And a deferred option with its requirement attached: an external fun is recoverable to an MFA at runtime, so a future check could compare it against the target module’s declared -spec. That needs a runtime type registry keyed by module. Not designed — recorded so it is not lost.
