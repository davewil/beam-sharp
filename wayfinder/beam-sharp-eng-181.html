The Declared Channel

The ticket asked how errors are represented. That had already been answered and the ticket did not know it — so the session went looking for what was actually open, and found a hole in the prelude instead.

The decision

Failure is a value where your signature declares one, and a crash where it does not — and which of those you chose is readable in the type.

Six decisions. The load-bearing one is not a preference: the untagged failure channel silently collapses when the success type absorbs the failure atom, and the prelude was already carrying a degenerate type because of it.

The headline question was already closed

“Exceptions, Result values, or the BEAM's throw/error/exit trio?” has no answer at the language level, because ticket 12 made the stance signature-directed: write the honest value your return type admits, raise only where it admits none. There is no global preference to pick. The ticket's body predated that resolution, so it was still asking a settled question — and the genuinely open part was the shape of failure.

Where a failure goes

Four distinct mechanisms, and only one of them was in doubt at the start of the session. The measurements collapsed the other three into things the language already had.

The defect: a channel that normalises away

Ticket 09 fixed the rule that a union is normalised first — :ok | atom is atom, because a singleton absorbed by a cofinite top is not a distinct member. Ticket 10 then put option<T> = T | :nothing in the prelude and ticket 11 gave ValidateAs<T> the return type T | :error. Nobody turned the first rule on the other two.

Ticket 10 had already written the degenerate line. Its worked example reads a := ToExistingAtom(input); // atom | :nothing — honest weak residual. That declared type is atom. The comment was true of the intent and false of the type — a caller cannot write the failure clause, because there is no failure member left to match. That instantiation is now rejected and ToExistingAtom must be respelled.

The last row is the one that changed the design. Giving the failure a payload is what makes it survive, not merely what makes it informative — a member carrying a reason is a tuple, and a tuple is not absorbed by an atom top. So the tag falls out of the payload rather than being a second decision.

The six decisions

  • Decision 1

    The shape stays untagged; the collapse is an error at the declaration

    Ticket 09's own rule, turned on the prelude — rejected where it is written, so the diagnostic lands where the fix is. An error, never a warning: ticket 03 found Caramel shipped output with Warning 8 let through.

    Rejected: tag both channels, as Elixir and Gleam do. It fixes every case and nests correctly — but the cost falls on as T, the showcase narrowing ticket 08 settled, and the untagged union is one of the few things the set-theoretic type system buys over a nominal ADT. Declining to use it where it is most valuable spends the type system's advantage on nothing.
  • Decision 2

    Absence carries nothing; failure carries a reason

    option<T> = T | :nothing bare, result<T, E> = T | (:error, E) named and tagged. Amends ticket 11: ValidateAs<T> returns result<T, ValidationError> — a path into the term plus the expected type, Gleam's decoder shape.

    Rejected: one channel only. Smallest surface and one rule instead of two — but it discards the reason, and the standing constraint says the consumer is an agent in a loop, for which the reason is the whole value of the diagnostic.
  • Decision 3

    raise takes any term, sharing its vocabulary with E

    Exactly :erlang.error/1; nothing invented. Because the two channels share a vocabulary, escalation between them is an ordinary function rather than an operator:

    T Unwrap<T, E>(result<T, E>);
Unwrap((:error, e)) -> raise e;
Unwrap(v)           -> v;
    Rejected: restricting to atom or tagged tuple. It would match what OTP itself does — but it is a tier-3 rule an author meets nowhere else on the platform. The recommendation goes in the spec, not the grammar.
  • Decision 4

    There is no try in the surface

    Measured: monitor+receive converts a callee crash into a value using only ticket 14's receive, and yields a better reason than try does. That leaves foreign in-process throws as the only gap, closed by a wrapper the compiler emits from the declared return type — the fourth codegen obligation, after ParseAtom, ValidateAs and arity generation.

    Rejected: no exception surface at all. Once Gleam was measured this option had no precedent behind it — Gleam has no surface rescue but uses try/catch nine times in its FFI. The question was never whether the try exists, only whether it is checked or a human's unverified assertion. Also rejected: a general try/catch, on ticket 21's escape-hatch grounds — and chosen partly for reversibility, since adding one later is purely additive.
  • Decision 5

    throw and exit have no spelling to produce; the class survives on catch

    Both jobs are already done — clause heads replace non-local return, (:stop, Reason, State) replaces self-termination. The wrapper catches all three classes into a compiler-known foreign_error = (:error, term) | (:throw, term) | (:exit, term).

    Rejected: narrowing the catch to protect supervision. The hazard does not exist — exit signals are uncatchable, so no supervision decision can be swallowed. Narrowing would instead have failed to catch gen_server:call to a dead process, the commonest foreign failure on the platform.
  • Decision 6

    Sequencing is required, and its spelling is ticket 17's

    Pipelines of fallible steps cost a named helper per stage. with is unavailable — it is ticket 26's record update. LINQ query syntax is the leading candidate, free if ticket 17 adopts LINQ for collections anyway and expensive if it chooses |>. That conditional is 17's decision, not this one's.

    Recorded and not chosen: a ? operator. Smallest thing that removes the tax and independent of 17's choice — but it puts a hidden exit in the middle of an expression, in a language otherwise built entirely from total clauses.

One fog patch got sharper without graduating. Ticket 27 proposed that what distinguishes the compiler-known prelude stratum is requiring a ground type argument. foreign_error belongs to that stratum and takes no type argument at all — so the criterion is neither that nor “could a user have written it”. A third candidate now stands: stratum 2 is what the compiler draws inferences from, whether or not it generates it.
