The Valve

Four constructs left the language and one arrived. The ticket asked which chaining syntax to adopt; the answer was that two of the three candidates need a mechanism this map closed twice.

The decision

The pipe is the only chaining form and it carries qualified names. Fallible steps chain through the valve, |?>. There is no comprehension syntax, no if, and no else.

Precision was the thing comprehensions were wanted for, and it turned out to be a lowering decision rather than a surface one — so the syntax could be deleted and the benefit kept. That single measurement removed two of this ticket's four questions.

The dot fell to a mechanism, not to taste

Ticket 05 recorded that xs.Where(f) and xs |> where(f) are "the same rewrite", and ticket 16 handed the call-syntax half of extension methods here. Both were true, and both concealed the same cost.

The rewrite target in xs.Filter(f) is an unqualified name. Something must pick List.Filter, and the only available clue is that xs : list<T>. That is type-directed name resolution — and this map has closed both routes to it, in tickets decided for entirely unrelated reasons.

LINQ query syntax falls to the identical argument, which is what makes the ticket's own stated conditional unanswerable as posed. ECMA-334's translation is a pure syntactic rewrite bound before type binding, exactly as ticket 05 said — and it emits xs.Where(…), unqualified. The cost was never in the type system. It is in name resolution, and LINQ pays precisely what the dot pays.

The borrow heuristic failed on semantics, not syntax. LINQ is cheap in C# because extension methods and overload resolution are already there — the query rewrite is a borrow sitting on top of machinery beam-sharp deleted twice over. The borrow arrives with its foundation missing, which is exactly the failure mode tier 1 exists to catch.

The dot is not abolished, only narrowed: it is never a call. Whether it projects (o.Total) is ticket 26's, and that argument does not carry over — a field name is known from the record's declaration, where a function name is not.

Precision turned out to be a lowering decision

Ticket 27's prototype 27a had established that a comprehension preserves the element-type relation exactly, under an analysis with no type variables at all. Ticket 27 then chose real polymorphism, which left this ticket apparently having to buy comprehension syntax to keep the precision. It does not. The compiler gets the same result by lowering List.Map to an inlined comprehension instead of to a call.

Emitted as an inlined comprehension 
roundtrip(Xs) ->
    [integer_to_binary(X) || X <- Xs].

%% typer, OTP 28
[integer()] -> [binary()]
Emitted as a call to the generic prelude 
roundtrip(Xs) ->
    list_map(fun integer_to_binary/1, Xs).

%% typer, OTP 28
[any()] -> [any()]

Same computation, same surface syntax, one lowering decision apart. So the rule the spec needs is one line: the compiler-known prelude is inlined, user code is called, and precision follows the inlining.

Three findings arrived that nobody went looking for.

The generic call loses more than lists:map/2 does. 27a's inline fun kept the result element type because the fun's body stayed visible through Erlang's own map. Here it does not — beam-sharp's list_map/2 carries a declared spec, ticket 27 §6's widened emission, and a contract overrides the success typing of the body. Emitting our own generic is strictly worse than calling theirs.

The lowering is more precise than the surface signature can be. Filter emits [pos_integer()], narrowed out of the guards, where List.Filter<T>(list<T>, fn(T) -> bool) -> list<T> can only say list<T>. The emitted code knows something the language's own type system throws away.

Fold is not a second tier, which corrects 27a. Its note that the syntax route "covers map and filter cleanly, fold not at all" was about Erlang's available syntax, not about achievable precision. An inlined monomorphic recursion keeps both sides. So the mechanism was never comprehensions at all — it is a monomorphic body the analyser can see through, and one rule covers map, filter and fold alike.

The valve

Ticket 15 settled result<T, E> = T | (:error, E) and found the tax: pipelines of fallible steps cost a named helper per stage. It deliberately left the spelling here. Three candidates were live, and the winner was chosen on cost of mechanism.

// stage signatures stay honest — CheckStock takes a Valid, not a result
result<Valid, Error> Validate(Request r);
result<Stock, Error> CheckStock(Valid v);
result<Order, Error> Charge(Stock s);

result<Order, Error> Place(Request r) =>
    Validate(r) |?> CheckStock() |?> Charge() |?> Confirm();

// failure: Validate yields (:error, :bad_request), nothing downstream runs,
// Place returns that error unchanged. The escape hatch is the operator's
// ABSENCE — write |> and handle (:error, _) in your own clause.
  • rejected

    Result.Then in the ordinary pipe

    Elm's andThen, Gleam's result.try — two BEAM-neighbour precedents, and no new syntax at all. It reads noisily at length, which is why Gleam eventually added use; and it is the only candidate that forces this ticket to spell "the function CheckStock as a value".

  • rejected

    The error-propagating clause, written by hand

    Add CheckStock((:error, _) e) -> e; to every fallible function and the ordinary pipe works unchanged. This reads best of the three at the call site, and ticket 15's untagged result makes it better than it looks — a caller holding a plain Valid still type-checks, since Valid is a member of result<Valid, Error> — while exhaustiveness forces the clause to exist.

    Sunk by review cost. The clause is byte-identical in every fallible function in the program, and a reviewer reads two lines that have nothing to do with the function they are reviewing. Write cost is near-free under the standing constraint; read cost is not.

  • rejected

    Generating that clause from a [Propagates] attribute

    The clause is fully determined by the signature — nothing about the body informs it — so the compiler can synthesise it and the boilerplate disappears. Textbook ticket 16 §1, and C# attribute syntax is a tier-1 borrow this map has used twice already.

    Sunk by cost of mechanism. It would be the language's sixth codegen obligation, each of which owes the walking skeleton an unmeasured cost. It also widens the declared arrow, so the signature describes the function's pipeline position rather than the function — and it moves the short-circuit out of the code the reviewer is reading.

  • kept

    The valve, |?>

    One operator token, zero codegen obligations, signatures untouched, no boilerplate, and the short-circuit visible exactly where someone reads the pipeline.

    The ? is free because ticket 10 already paid for it, accepting the loss of C#'s ternary as the price of :atom — and no BEAM language has one. It is not decoration: C#'s a?.B() and TypeScript's optional chaining carry the same semantics — if the left is the absent case, the rest of the chain does not run and that case is the result — and ticket 15's untagged result makes (:error, E) the exact analogue of null. A tier-1 borrow for both halves of the audience at once, which is rare in this map.

A fully implicit rule was closed by precedent, not by taste. "If a result<T, E> meets a parameter of type T, propagate" is inferred narrowing at a call site, and ticket 08 already settled that narrowing is always written, never inferred — neither audience expects implicit cast insertion. So a marker was mandatory; the only question was where it sits.

Elixir ships |> alongside tap/2 and then/2, so the pipeline being a small family is the neighbourhood's own habit rather than an oddity (David). That also means a tap equivalent costs nothing here — xs |> Debug.Tap(f) is an ordinary prelude function in the ordinary pipe.

There is no if, and the measurement is why

Prototype 01g made if an expression and left the one-armed case open; ticket 10 routed it here. David's question during the grilling — does else exist in Elixir or Gleam? — looked like a vocabulary check and settled the decision instead.

cond: :b                % catch-all is `true ->`

error: unexpected option :else in "cond"
error: unexpected option :else in "case"

Gleam has no if at all, and the error is written for this case specifically, with the replacement supplied. A deliberate refusal carrying a designed diagnostic — not a feature never reached. And since there is no if, there is no else anywhere in the language. In Elixir, else belongs to if and nothing else: both pattern constructs reject it outright, and cond's catch-all is a clause.

The structural reading

else is what a language needs when its conditional is binary and unnamed. A pattern construct never needs one, because its fall-through is just another pattern.

So keeping if/else would not merely have added a keyword. It would have added the only construct in the language whose fall-through case is not expressible as a pattern — in a language whose entire thesis is that patterns and exhaustiveness are the mechanism.

What replaces it is the clause head's own grammar, in expression position. Compound conditions take a tuple subject, which is C#'s native tuple pattern, Gleam's multi-subject case, and the shape beam-sharp's function heads already have — three heritages converging on one construct.

int Discount(Order o) =>
    o switch {
        { Total: > 100, Status: :open } => 10,
        { Status: :frozen }             => 0,
        _                               => 5
    };

// the subject-less ladder: a tuple subject, not an else-if staircase
(user.IsAdmin, o.Total > 100) switch {
    (true, true) => :priority,
    (_,    true) => :large,
    _                => :normal
}

One branching construct, the way Go has one looping construct (David). switch subsumes if, else, else if, cond, case and the ternary the language had already dropped — and it inherits ticket 12's hard-error exhaustiveness and ticket 04's residual for free.

Two questions die with if. The one-armed case has no spelling left to have semantics. And ticket 15's collapse landmine never fires: had a one-armed if yielded option<T>, then if (ready) { :ok } would produce atom | :nothing, which ticket 15 §1 makes an error at the declaration — a compile failure reported against a union the programmer never wrote, under one of the most ordinary shapes in the language.

Ticket 18 gains the repair and its limit, and now argues over a two-tier emitted boundary rather than a uniform one — plus the valve as new undefended surface. Ticket 20 gains a third independent sighting of binaries as where precision dies, this one in beam-sharp's own emitted code. Ticket 23 gains live evidence rather than a citation, and its question narrows from "could a compiler do this" to "should the residual be machine-readable as well as prose". Ticket 25 inherits two jobs: whether a long ladder of unrelated conditions occurs in the six exemplars, and whether the pipe reads well in the three binary-heavy ones. Ticket 26 keeps with free and now owns the whole of the dot.

Two things were deferred rather than refused, with their requirements recorded so they are not rediscovered. Laziness — "defer lazy, we will want it" — needs compiler-known status in the prelude's second stratum with a fused lowering, an answer to how a lazy source meets ticket 14's process model, and a position on early termination, the one case fusion does not cover. It stays cheap to add because the pipe carries qualified names: Stream.Map is a new module and nothing existing changes. cond waits on evidence that a five-condition ladder actually occurs.
