beam-sharp · decision brief ENG-184 · ticket 18 2026-08-13 OTP 28.5 · Gleam 1.18.1 · Elm 0.19.1

Never Silently

The ticket asked which of eight violation channels to defend. Five were already closed, and what remained turned on one question the map had never put plainly: is a declaration a claim, or a promise?

The decision

A foreign term that breaks your types will crash — not always where it entered, but never silently.

Guards are emitted only where the function's own body would not already object, and always where generated code consumes the value. A foreign declaration may promise only what one BEAM guard decides in O(1). No opt-out.

Eight channels were never eight questions

Ticket 06 charted eight ways a value can enter a beam-sharp program badly typed, and the ticket carried them as eight open decisions. Tallied against what the closed tickets had already settled, they sort into two piles on a single test: did the term arrive somewhere beam-sharp had to match it, or somewhere beam-sharp declared a type for it?

Erlang does not guard its own boundary, and measuring that moved the answer

The opening recommendation was to guard every ground parameter of every exported function, partly on the argument that the ecosystem already writes those guards by hand and beam-sharp would merely automate them. That argument is false, and the census that killed it is the most useful number in the ticket. Every exported function in stdlib and kernel, OTP 28, abstract code read from the shipped .beam files — a parameter counts as defended only if every clause constrains it structurally or names it in a guard.

Why the platform gets away with it. Erlang has no static claim to break, and its runtime checks everything eventually — pass a float where a list was meant and length/1 badargs at first touch. Erlang buys ticket 06's outcome 2, the deferred crash, for free from its BIFs and pays nothing at the boundary.

Outcome 3 — silent unsoundness — only happens when a wrong term traverses the entire body without meeting one operation that objects. That is why the numeric tower is the canonical case: + is one of the few operations total over both integers and floats.

So the chosen answer is deliberately the smallest departure that closes outcome 3. It converges with the platform rather than departing from it — Erlang already achieves "crash eventually" for free, and beam-sharp tops it up only where the free check is absent. Which, after tickets 16 and 17, is precisely where generated code has replaced a body you could read.

Four cases, and they are the whole rule

Body objects — nothing emitted 
// beam-sharp
int LineCount(list<Line> ls);
([])       -> 0;
([_, ..t]) -> 1 + LineCount(t);

%% emitted
line_count([])    -> 0;
line_count([_|T]) -> 1 + line_count(T).
%% line_count(42) => function_clause
Body total over the wrong term — guard emitted 
// beam-sharp
int Add(int a, int b);
(a, b) -> a + b;

%% without a guard
add(A, B) -> A + B.
%% add(1.5, 2.5) => 4.0
%% what is emitted
add(A, B) when is_integer(A), is_integer(B) ->

The third case is the one that made the decision. 16 §4's generated encoder is emitted from the declared type, so it walks the shape it was told to expect and has no reason to look. Undefended, it produces well-formed JSON with the wrong type on the wire, from code the author never wrote and cannot read in a diff:

to_json(#{id => <<"7">>, customer => <<"acme">>, lines => []})
  =>  <<"{\"id\":\"7\",\"customer\":\"acme\",\"lines\":[]}">>

So every parameter feeding a codegen obligation — the encoder, ValidateAs<T>, 17 §2's inlined prelude operations — is guarded unconditionally, no analysis. The fourth case is the conservative default: not visible at this compile, so guard. The rule is emit unless the body demonstrably objects, never "emit where it looks risky" — the burden sits on omission, which is what keeps it an analysis rather than a judgement call.

A declaration is a claim until the compiler makes it a promise

Four of the live channels were one question wearing four coats: what is a foreign function's declared return type actually worth? The only language on the platform with that exact construct answers it, and the answer was measured rather than read.

Gleam 1.18.1 — the declaration 
@external(erlang, "probe_ffi", "lookup")
pub fn lookup(id: Int) -> List(Order)

@external(erlang, "probe_ffi", "count")
pub fn count() -> Int
%% Erlang side returns 41.5
What Gleam emitted, and what it returned 
-spec count() -> integer().
count() ->
    probe_ffi:count().  %% entire body

first_id(1) : <<"7">>
add_one()   : 42.5

Gleam trusts the declaration and publishes the false claim as a -spec. A raw Erlang caller running Dialyzer against that module is actively misled, not merely unhelped. And the generated consumer shows why the tempting middle option fails — [{order, Oid, _} | _] -> Oid tested the tag and the arity and bound the payload bare. The match succeeded and handed the binary through.

Erlang and Elixir are not precedents at all, and the reason is precise: neither has a construct that declares a foreign function's type. NIFs and ports return arbitrary terms; -spec and @spec are Dialyzer-only, never runtime. Having no static claim, they cannot break one. Erlang's single built-in boundary check confirms the shape of the gap — binary_to_term/2 with [safe] refuses an unknown atom and passes a wrong-shaped term straight through. It protects a resource, not a claim.

So a foreign declaration may promise only what one guard decides in O(1). Structured types cross in two steps, and the second step's type forces you to have a plan for bad data:

// promises only "it's a list" — checkable, so checked
list<term> EtsLookup(int id) = [Erlang("ets", "lookup")];

// the crossing — one line, and its type says it can fail
result<list<Order>, ValidationError> Lookup(int id) =>
    EtsLookup(id) |> ValidateAs<list<Order>>();

(id) -> Lookup(id) switch {
    [o, ..rest]  => Format(o),
    []           => <<"no such order">>,
    (:error, e)  => Report(e)   // cannot be omitted — ticket 12
};

This is ticket 11 §2's rule applied verbatim at a second site, not a new rule — it refuses to let the FFI declaration be a back door around the cap the clause head already obeys. It also dissolves the FFI -spec sub-question rather than answering it: a declared type that is always O(1)-decidable and guarded on return makes the emitted spec a checked claim like any other.

And the two-step crossing is not new discipline — it is the platform's own idiom, applied at one channel out of eight. Ecto's cast → validate_* → {:ok, struct} | {:error, _} is ValidateAs<T> hand-written, and the whole Phoenix world runs on it. Measured in a local Elixir application: 9 changeset pipelines and 29 validate_* calls, beside 5 ETS reads that every one bind the payload bare — the same shape the Gleam probe produced, arrived at independently, because there is no reason to distrust a table you filled yourself.

Which is exactly what ticket 21 established you cannot prove on this platform.

The state channel was wider than charted

Ticket 14 narrowed a callback's request argument to term by contravariance — but its own example still declares the state, and 14 never justified that position. It is reachable by a documented OTP function any process can call.

sys:replace_state(P, fun(_Old) -> {account, <<"one">>, <<"lots">>} end).

normal                     : 100
after sys:replace_state    : <<"lots">>
  is_integer(that balance) : false

The state is structured and touched on every message, so checking it per callback is ValidateAs<State> at message rates — the unbounded-work-per-message shape ticket 11 §2 refused. Checking at the entrances costs one validate per hot upgrade.

How far the analysis looks

C asks "would the body object?", and that question needs a stopping point. It looks at the exported function's own clause heads and body, and no further.

%% emitted, function-local

    format(Id).
format.bs — edited alone, later

(n) -> Cache.Put(n);

The standing constraint decides it. One function per file exists so an agent's write_scope is a file with bounded blast radius and a reviewable single-file diff. Whole-aggregate analysis reintroduces exactly the blast radius that rule removed. Ticket 12 made the structurally identical call — keeping the failure arm everywhere rather than accepting a saving whose soundness depended on something not locally visible.

Elm defends its boundary, and it does not transplant

Elm was the one candidate for a language whose static guarantees survive its escape hatch, and it does: Optimize/Port.hs toDecoder synthesises a decoder from each port's declared type, _Platform_setupIncomingPort runs it on every incoming value, and Elm code is unreachable unless it succeeded — byte-identical under --optimize. This partially retracts ticket 21, whose conclusion was that no language defends by checking data.

But Elm owns the one door — return { send: send }. beam-sharp's callers arrive by mailbox, ETS, timer, DOWN and code_change, none of which traverse compiler-emitted code. The mechanism transfers; the coverage does not. The sharpened claim, and the one this ticket used: checking data is what you do at a door you own, and the BEAM's problem was never that checking is unusual — it is that there is no door.

Two things from Elm that cut in opposite directions.

Corroboration: Elm's admissible port type set is a closed whitelist rejecting functions, type variables, Dict, Set, Result and every custom union — including a payload-free enum. That is exactly "types with a decidable structural test": ticket 09 §4's rule reached independently on a different runtime.

Caution: outcome 3 survives inside Elm's checking boundary. _Json_decodeInt accepts any finite whole number, so 1e300 crosses an Int port and n + 1 == n. beam-sharp does not inherit this — is_integer/1 is exact and BEAM integers are arbitrary precision — but it is the measured reason a maximal claim is harder to keep than it sounds.

Resolution of the timing method is ±0.09 ns/call, and only the four-guard case clears it — with that figure confounded by body optimisation the guards themselves enabled. The qualitative return is larger than the numbers. A guard turns a silent 4.0 into a function_clause naming the offending argument, and in the tuple case it moves the blame from a compiler-generated literal inside erlang:element/2 to the caller's own term in the caller's own function.

One structural finding killed a design option mid-session. Elision is exported vs local-only, not local-call vs remote-call: a BEAM function has one entry label shared by both call kinds. So "emit a guarded public entry plus an unguarded internal one" — floated as the cost mitigation for the maximal claim — cannot be done with one function. Interior functions already pay nothing, which is the shape the chosen answer wanted anyway.

The decisions

  • kept

    Guards where the body would not object

    Never on type variables — 27 §3 makes them opaque, so there is nothing to test and the shape is the caller's. Always on anything feeding a codegen obligation.

    Rejected: guarding every ground parameter — unprecedented, and the census shows the platform's implicit safety net already covers most of it. Rejected: guarding nothing — 16's encoder and 17's inlined operations would then run on unvalidated data inside code nobody reviewed.
  • kept

    A foreign declaration promises only what one guard checks

    Closes ETS reads, decoded terms, ambient config and the reply channel together, and dissolves the FFI -spec sub-question.

    Rejected: declare anything, check one level deep — that is Gleam's measured failure with one extra layer of tag. Rejected: trust the declaration — the thing the guarantee exists to rule out.
  • kept

    The state is defended at its entrances

    ValidateAs<State> in code_change/3, init trusted, nothing per-message. sys:replace_state is a named limit.

    Rejected: an O(1) tag check per callback — two instructions, but it would claim a defence one level deep, which is what was refused for the FFI. Rejected: a full check per callback — O(n) at message rates.
  • kept

    Function-local analysis, and no opt-out

    A guard can only move when you edit the function it sits on.

    Rejected: whole-aggregate analysis, with or without an emitted manifest — the manifest recovers visibility but adds a build artefact the spec must version, and hands ticket 23 a dependency it did not ask for.
