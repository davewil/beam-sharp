# Decision brief: ticket 62, the outbound ABI (ENG-252), function-name casing

Brief only. The ticket file, Linear and git are untouched. Everything below was run on 2026-10-22; raw output of every probe is in
`/home/user/beam-sharp/artifacts/probes/62/output.txt` (one section per probe, regenerated by the run.sh files listed at the end).

## 1. Ticket summary

B# exports functions PascalCase (`'New'/1`), because a B# function name is `uident = {UPPER}{ALNUM}*`
(`compiler/src/bs_lexer.xrl:150`; ALNUM = `[a-zA-Z0-9_]`, `bs_lexer.xrl:16`). The prefix question and the `Kind`-contract question are
already answered in the ticket (LANGUAGE.md section 12 now publishes the Kind contract). **The one open decision is how an Elixir
caller is meant to reach `New`.** The ticket's three candidates: (1) accept it, Elixir uses `apply/3`; (2) emit snake_case aliases alongside, "a rule
for deriving the name", with Gleam cited as precedent; (3) make B# functions snake_case.

Grep done before writing (`wayfinder/issues/*.md`): ticket 32 (`32-ffi-surface.md:204`, `:344`) says "there is no snake_case/PascalCase rule anywhere in the
language" (written about the *inbound* direction, on the evidence of the 1,920/1,924 name census); ticket 35 (`35-behaviour-callback-names.md:22,240`) lowered
callbacks through a *fixed table* (`compiler/src/bs_otp.erl:40`) and says a lowercase function name "is not a spellable name". Neither covers outbound aliases.
Candidate 3 is therefore closed by the lexer, not by taste (a signature needs a `uident`), and is not costed further.

## 2. Sub-decisions and gating order

1. **Is there already a tolerable way in for Elixir?** (a fact; gates everything). Probe 01 says yes, which the ticket does not know. See section 3.
2. **Given that, does outbound ergonomics justify compiler work at all?** Gates 3 to 5. Ask this one alone.
3. If yes: **derive the alias by a rule, or let the author spell it?** (gates 4 and 5)
4. Aliases **add to** the PascalCase export (Erlang and B# callers keep working) or **replace** it. (Replace would break the working Erlang path the ticket values; not studied further.)
5. Collision policy: what happens when two names map to one alias, or an alias hits `module_info/0,1` or a behaviour callback. Only exists under 3 = derive.

### P3. Gleam 1.5.0 (ticket section 1 Gleam claim and the "Gleam downcases" precedent). `probes/62/03-gleam/run.sh` (dependency-free projects; Hex not needed)
```
A. @external(erlang, "Shop", "New") ... compiles, emits  'Shop':'Which'('Shop':'New'(1)).   erl: a:main() -> order     (the ticket said "call was not run": now run, works)
B. pub fn DoThing() { 1 }  -> error: Syntax error ... "I'm expecting a lowercase name here"
   pub fn do__thing_X()    -> error: Invalid function name ... "Try: do_thing_x"
C. type T { ABTest XMLHttpRequest Foo2Bar Get2D HTMLElement A AB ABc IOError V8Engine MyOrderLine }
   -> -type t() :: ab_test | xml_http_request | foo2_bar | get2_d | html_element | a | ab | a_bc | io_error | v8_engine | my_order_line.
      -export([all/0, do_thing_now/0]).
D. type T { ABC Abc }  -> -type t() :: abc | abc.   x() -> {abc, abc}.      (silent collision, no diagnostic)
   type T { Foo_Bar }  -> error: Invalid type variant name
E. src/deep/nested.gleam -> deep@nested.beam
```
**Shows, and this falsifies the precedent as the ticket states it:** Gleam 1.5.0 does **not** downcase function names when emitting. It *refuses* any non-snake_case function name at the source (B), so a Gleam module never has a PascalCase export and the outbound problem cannot arise.
What Gleam does PascalCase-to-snake_case is **constructor names** (C), which become atoms; that is what ticket 10 section 7 (`10-atoms-in-a-csharp-skin.md:335`) actually measured, and it is a different construct from a function name. The precedent for "derive an alias from a PascalCase function name" does not exist in Gleam.
What Gleam does provide is a data point on the *cost* of a derivation rule: it forbids `_` in constructor names (D, last case) and still collides `ABC`/`Abc` silently. Version flag: 1.5.0 vs the tickets' 1.18.1; the collision may be fixed later and the Gleam stdlib/compiler source is not installed (the compiler is a Rust binary), so no file:line citation for Gleam is possible.

### P4. Would a derivation rule collide in real B#? `probes/62/04-name-rule-corpus/run.sh`
Compiles the repo's examples (22 of 23 modules) and applies two rules to the exported names. S1 = insert `_` before every capital; S2 = acronym-aware (the shape Gleam produced in P3 C).
```
modules=22 exported author functions=78
names where S1 and S2 differ: 0                       (and zero collisions in the corpus under either rule)
corpus names already containing '_': [('Counter','handle_call'), ('Counter','handle_cast')]      (callbacks already lowered by bs_otp)
GetHTTPServer  S1=get_h_t_t_p_server   S2=get_http_server        HTTP S1=h_t_t_p S2=http      Get_Value S1=get__value S2=get_value
S2 synthetic collisions: {'abc': ['ABC','Abc'], 'get_value': ['Get_Value','GetValue'], 'parse_url': ['ParseURL','ParseUrl']}
Elixir 1.14.0 Macro.underscore: ParseURL parse_url | Get_Value get__value | ABc a_bc | ABTest ab_test | XMLHttpRequest xml_http_request | Get2D get2_d | collisions: ABC/Abc, ParseURL/ParseUrl
```
**Shows:** on today's corpus a rule is free of collisions, but B# identifiers admit `_` and acronyms (`ALNUM` includes `_`), so collisions are reachable. The two rules disagree on `HTTP` and on `Get_Value` (S1 and Elixir's `Macro.underscore` give `get__value`; S2 gives `get_value`), so the rule is a spec item that two implementers can
get wrong silently (an alias that is not where the other side expects is an `undef` at run time, not a type error). Elixir's `Macro.underscore` and Gleam agree on every constructor case in P3 C (`a_bc`, `ab_test`, `xml_http_request`, `io_error`, `v8_engine`, `get2_d`), so a de-facto convention exists to copy.
The corpus is the repo's own examples; it is not evidence about what users will write.

## 4. Neighbour survey

- **Erlang.** Quoted atoms are first-class syntax: `/usr/lib/erlang/lib/stdlib-4.3.1.3/src/erl_scan.erl:420` `scan1([$'|Cs], St, Line, Col, Toks) ->` calls `scan_qatom` (`:422`). `'Shop':'New'(1)` needs nothing. `erl_lint.erl:530` lists `[{module_info,0}, {module_info,1}, {record_info,2}]` as predefined, which is why P6's `ModuleInfo` alias is refused.
- **Elixir.** Unquoted `.Capitalized(` is the alias path (`elixir_tokenizer.erl:1370`), but a quoted function name after the dot is a deliberate, supported tokenizer clause (`:911`, P7) and the formatter keeps the quotes when needed (P1). Elixir ships its own PascalCase to snake_case function, `Macro.underscore/1` (measured in P4; source not installed so no file:line; `Code.fetch_docs` not used).
- **Gleam.** 1.5.0: functions must already be snake_case, so there is no outbound casing problem and no function-name derivation (P3 B). It derives snake_case only for constructor atoms (P3 C) and collides `ABC`/`Abc` silently (P3 D). Source not installed (Rust binary); evidence is by measurement only.
- **Elm.** Targets JavaScript; has no BEAM outbound ABI, and the Elm core/package source is not installed (package.elm-lang.org is blocked by the proxy). Not a precedent for this question; no probe run.
- **This repo already has one outbound rename, and it is a table.** `compiler/src/bs_otp.erl:40` `callbacks('GenServer')` maps `'HandleCall'` to `handle_call` etc.; `bs_emit.erl:76` (export list), `:118` (`name/2`) and `:132` (`emitted_name/3`) are the single place a B# function name becomes an Erlang one. A module that declares `behaviour GenServer` is already called as `handle_call` from Erlang/Elixir. Ticket 35 chose a table specifically so it is "not a naming rule by another route".

## 5. Options

### Option A: accept, and document the quoted form (no compiler work)
B# unchanged:
```csharp
module Shop
public Order New(int id)
New(id) -> Order{ Id = id, Total = 0 }
```
Elixir author, compiles and runs today (P1): `:Shop."New"(1)`, `Enum.map(ids, &:Shop."New"/1)`, `ids |> Enum.map(&:Shop."New"/1)`. Under B or C the same B# source additionally accepts `:Shop.new(1)`.
Compiler delta: none. Spec delta: LANGUAGE.md section 12 (`:3315-3328`) and the ticket text say `apply/3` is "the way in"; both should list the quoted form and drop "Elixir cannot call a PascalCase export".
**Strongest counterargument:** the ticket's own concern stands untouched: adopting B# *incrementally inside an existing Elixir codebase* means every call site carries quotes that look foreign next to snake_case Elixir code, and `Shop.New` (the idiomatic alias form) is never available. Nothing in my probes measures adoption friction, only that the call works.

### Option B: compiler derives a snake_case alias for every public function
B# unchanged; Elixir writes `:Shop.new(1)`. Refused by this option but accepted today (P6): a module declaring both `ParseURL` and `ParseUrl`, or `ModuleInfo()`.
Compiler delta (measured by the scratch patch): in `bs_emit:forms/1` an alias export list and forwarder forms (32 lines, P5); a spec'd derivation rule (acronym handling, digits, `_`; P4 shows two reasonable rules disagree, and Elixir and my S2 disagree on `Get_Value`); a new `bs_check` collision diagnostic plus reserved names (P6); `-spec` for the forwarders; `bsc --api` and LANGUAGE.md section 12 changes; and it reverses the stated position of ticket 32 ("no snake_case/PascalCase rule anywhere") which would need a ticket-level exception.
Cost: +8.3% beam bytes, +52% exports, no measurable compile-time change (P5).
**Strongest counterargument (against B):** the rule becomes part of the published ABI that the clean-room fleet must reproduce exactly; the one neighbour that ships such a rule (Gleam, constructors) collides silently on `ABC`/`Abc` (P3 D) and Elixir's own `Macro.underscore` collides the same pair (P4). The case *for* B at its strongest: it is the only option that makes the common case (`:Shop.new(1)`) free for the author, with no new syntax.

### Option C: the author spells the alias (new surface, no rule)
```csharp
module Shop
public Order New(int id) as :new        // proposed syntax; `as` is not a keyword today
New(id) -> Order{ Id = id, Total = 0 }

public int ParseURL(int n) as :parse_url          // compiles under C
public int ParseUrl(int n) as :parse_url_v2       // compiles under C; under B this pair is refused, under A `as` is a syntax error
```
Compiler delta (not built; costed by P5/P6 for the emission half): lexer keyword `as` (reserving a name, as `raise` and `fn` are reserved, `bs_lexer.xrl:77-85`); `signature` production in `bs_parser.yrl:308-312` gains an optional trailing alias (the `signature` tuple's last position is already used by type params, so a new field); `bs_check` validates the alias is a lowercase atom and unique against all emitted names and the reserved list; `bs_emit` reuses the forwarder emission from P5, only for annotated functions. Mirrors ticket 32's "both spellings are written" (a quoted string has no failure case) and ticket 35's "table, not rule".
**Strongest counterargument:** every function an Elixir caller needs gets a second hand-written name; most authors who want Elixir-friendliness will annotate everything, which is Option B with more typing and a new keyword, plus a drift hazard (the alias name is unchecked by any convention). It also needs David to approve new surface syntax for an ABI concern.

(Ticket candidate 3, snake_case B# functions, is excluded: lexer `uident = {UPPER}{ALNUM}*` makes a lowercase signature name unspellable, per ticket 35.)

## 6. Recommendation

**Choose Option A now, and ask David the gating question alone: "is `:Shop."New"(1)` acceptable for Elixir callers?"** My reasons, each with its evidence:
1. The ticket's premise (an Elixir caller can only use `apply/3`) is false; the quoted form works in every call shape I tried and survives the formatter (P1). The friction is a pair of quotes, not an inability.
2. The one precedent offered for B is not one: Gleam 1.5.0 emits no derived function names (P3 B) and its constructor rule collides silently (P3 D).
3. B costs a spec'd rule, a new diagnostic, and a ticket-32 reversal (P4, P6); the clean-room handoff is the project's stated priority and a rule is exactly the kind of unwritten ABI detail it would trip on.
4. A closes nothing: if adoption evidence later shows quoting hurts, C (explicit, rule-free) can be added without breaking any program, because aliases only add exports. B cannot be retracted once programs call `:Shop.new`.
Concretely A means: fix LANGUAGE.md section 12 and the ticket's section 1 headline, nothing else. If David rejects A on ergonomics, ask the second question alone: "may a signature carry `as :new`?" (C) before considering a derivation rule (B).
