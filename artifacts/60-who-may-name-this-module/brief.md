# Decision brief: ticket 60 / ENG-242, which modules may name this one?

Repo HEAD `f528593`. Probes in `probes/`, regenerated by `probes/run.sh` (OTP 25, Elixir 1.14.0; see `probes/versions.out`).
Nothing under `wayfinder/` or `compiler/` was touched. `bsc` was not run (cannot be built here).
Labels: MEASURED (probe, `.out` named), SOURCE (file:line read), RECORDED (a ticket says so, not re-run), UNVERIFIED.

## Question

`public`/`private` (F12) settles **what** a module exposes. Nothing settles **who** may name it: can `Other.Audit`
write `using Shop.Orders` and call `Shop.Orders`'s public functions, when only `Shop.*` should?

## Sub-decisions, and which one gates the rest

(a) unit: subtree / named group / explicit list. (b) direction: callee says who, or caller declares dependencies.
(c) third marker on the signature, or a separate construct. (d) checker cost. (e) consumer: ticket 24's `unclassified`.

**(e) gates everything.** If no real program needs "public to `Shop.*`, refused to everyone else", (a)-(d) are moot. So the
question to David is (e), alone, as a program (see Recommendation). The others then mostly fall out:

- (b) is close to forced. A caller-side list duplicates `using`: every cross-module reference already needs a `using`
  line, "those entries declare the file's dependencies" (SOURCE bs_check.erl:4037-4046), and the emitter/typing tables
  are only reachable through it (SOURCE bs_check.erl:472-486). A caller listing what it may use restates what it uses.
  Only a callee-side (or third-party architecture file) declaration can *refuse* a caller.
- (c) is close to forced. F12 keeps the marker on the signature with two levels and lists "`protected`, `internal`,
  or any third level" out of scope (SOURCE F12 "Out of scope"). A per-function "who" marker would also promise per-function
  enforcement the BEAM cannot give (RECORDED 18 §5, 22): it must be a compile-time caller check. Module-level fits it.
- (a) and (d) are the live design choices if (e) is yes.

## Option 1: callee declares a subtree (`within`), in `index.bs`

The unit is a directory subtree; the direction is callee-says; it is a separate construct, one line beside `using`,
`type`, `record` and `behaviour`, all of which already live in `index.bs` (F15).

```csharp
// Shop/Orders/index.bs
module Shop.Orders
within Shop                    // only Shop and Shop.** may name this module

// Shop/Orders/Total.bs
module Shop.Orders
public int Total(list<int> lines)
Total(lines) -> Sum(lines)

// Shop/Reports/Summary.bs      accepted: Shop.Reports is under Shop
module Shop.Reports
using Shop.Orders
public int Summary(list<int> lines)
Summary(lines) -> Total(lines)

// Other/Audit/Run.bs           refused
module Other.Audit
using Shop.Orders
public int Run(list<int> lines)
Run(lines) -> Total(lines)
```

Diagnostic, in `bs_diag.erl:1233` style (the wording is my draft):

```
Other/Audit/Run.bs:2:1: error: Other.Audit names Shop.Orders, which Shop.Orders declares `within Shop`
  a module outside Shop cannot `using` it. Move the caller under Shop, or widen `within` in Shop.Orders.
```

Under the other answer (no rule) `Other.Audit` compiles, as it does today.

**Compiler delta (concrete):**
1. `bs_lexer.xrl` keyword `within`; `bs_parser.yrl` `within_decl -> 'within' modpath : {within, Line, Root}` (cf. `using_decl`,
   `bs_parser.yrl:180`). F12's own note applies: lexer plus all three editor grammars land in one commit.
2. `bsc.erl:227-239`: world entry gains `within => Root | none`, read from the module's decls, like `behaviours`.
3. `bs_check.erl`: `add_import` passes `Self` and `L` into `add_module_import` (arity 3 becomes 5, coincidentally the
   ticket's "/5"). One test: `Self =:= Root orelse lists:prefix(Root ++ ".", Self)` using the `children/2` technique
   (bs_check.erl:573-575). Refusal raises `{outside_within, M, Root, Self, L}`.
4. `add_namespace_import` (bs_check.erl:510-517): `using Shop` expands to children; decide per child (skip silently vs
   refuse). Needs its own rule; see counterargument.
5. Two new own-module checks: `Root` must be a prefix of the declaring module (else unsatisfiable), and `Root` must have at
   least one module under it (a typo'd root fails *closed*, prefix_rule.out last line, so it needs its own error).
6. `bs_diag.erl`: `built/2` clause (near :338) and `message/1` clause. Both `qualified_module` and unqualified imports
   route through `using`, so no per-call-site work (SOURCE bs_check.erl:4037-4046).
7. Failing test and gate first (CLAUDE.md), with a `--self-test` that builds `Shop.ReportsV2` and requires the refusal.

**Measured cost:** one prefix test per `using` line: 0.12-0.27 us (cost.out), 0.5 us/edge for a 100k-module world sweep,
against 4.7 ms for one tiny compile. The checker cost is not a deciding axis.

**Strongest counterargument.** A subtree is adjacency by *name*, so the rule is only as stable as the tree. Moving
`Shop/Reports` to `Analytics/Reports` silently changes what `Shop.Orders` will tolerate (it becomes a refusal at the `using`
line, which is loud, but the *fix* is to edit the callee, not the mover). And it over-admits: `within Shop` lets `Shop.Billing`
name `Shop.Orders` although nobody meant that. Narrowing to `within Shop.Orders` admits only its own children, which is
almost the same as intra-module and buys little. The unit is coarse in exactly the way the ticket suspected ("cheap answer").
`ibs` and single-file builds have `Self = 'Main'` (SOURCE bs_check.erl:253-257), so `using Shop.Orders` from the REPL would
be refused; whether that is wanted is UNVERIFIED (how `ibs` assigns a module was not read).

## Option 2: callee declares an explicit list (`friends`)

Same site, same direction, different unit: the callee names modules, not a subtree.

```csharp
// Shop/Orders/index.bs
module Shop.Orders
friends Shop.Reports, Shop.Billing

// Shop/Audit/Run.bs
module Shop.Audit
using Shop.Orders              // refused although Shop.Audit is in the same subtree as Option 1 would admit
```

```
Shop/Audit/Run.bs:2:1: error: Shop.Audit names Shop.Orders, which lists friends Shop.Reports, Shop.Billing
  Shop.Audit is not among them. Add it to `friends` in Shop.Orders, or call a module that is.
```

**Compiler delta:** as Option 1 items 1-3 and 6, with the test `lists:member(Self, Friends)` (or a map `is_key` when a
declaration is large) instead of a prefix test; item 5 becomes "every named friend must exist in the world"
(`maps:is_key`, no namespace semantics, so no edge cases from `ReportsV2`). No prefix probe is needed, and the edge cases
of prefix_rule.out do not arise.

**Measured cost:** `is_key` 0.014-0.030 us flat in N. `lists:member` is 0.036 us at N=10, 203 us at N=100k, but a friend list
of 100k names is not a real program; a friend list is 1-10 names.

**Strongest counterargument.** Adding a caller means editing the *callee's* `index.bs`, so a new consumer of `Shop.Orders`
touches a file the consumer's author does not own. That is exactly the blast radius the one-function-per-file layout was
built to avoid (RECORDED in ticket 18 §5: "whole-aggregate analysis would let an edit to one file silently move another file's emitted boundary"). It also has no zero-config case: a test module or a new sibling is refused
until listed, so it pushes an agent to edit the friends line reflexively, which turns it into a rubber stamp.

## Option 3: no new construct; F12's `private` already answers the consumer, revisit on a second occurrence

Leave the "who" half unspecified. Ticket 24's `unclassified: RecomputeTotal/1` is already classified by F12: an unmarked
signature is `private` and a call from another module is refused (RECORDED F12.4). Ticket 24 was written four days before F12
and states the opposite ("every function ... is exported today", 24 lines 218-220). So the consumer that 22 and 60 cite may
already be served, *if* the test module is a different module from the aggregate. Where tests live is UNVERIFIED (ticket 24 does not
name a directory; I found no "Tests/" rule in it).

```csharp
// Shop/Orders/RecomputeTotal.bs
module Shop.Orders
private int RecomputeTotal(list<int> lines)   // unmarked would mean the same
RecomputeTotal(lines) -> Sum(lines)

// Shop/OrdersTests/Total.bs
module Shop.OrdersTests
using Shop.Orders
Test() -> RecomputeTotal([1])     // refused today: "calls RecomputeTotal/1, which Shop.Orders declares `private`" (bs_diag.erl:1233)
```

**Compiler delta:** none. One correction to ticket 24's text (a sentence, per CLAUDE.md: one occurrence gets a sentence,
not a check).

**Strongest counterargument.** It leaves a real hole: a function meant for *sibling modules* only must be `public`, which
makes it callable by everyone (measured: Erlang and Elixir have the same hole, erl_caller_restriction.out 1, ex_probe.out 1),
and the agent's test-drift risk returns for exactly those functions. Also it makes the 22/60 claim "the useful boundary is which
modules may name this one" go unserved on an unexamined assumption that no exemplar needs it. I did not search the 32 `.bs`
files for a public function called by exactly one directory; that search is the missing evidence (below).

## Recommendation

1. **Ask (e) alone, as code**, before anything else: "Is there a `.bs` program in which `Shop.Reports` must be able to call
   `Shop.Orders.Fetch` and `Other.Audit` must be refused?" Show it accepted and refused with the diagnostic above. Before the
   round, run the missing evidence: grep the corpus for public functions whose every caller is in one subtree (a one-off
   shell/erl script, not a gate). If the count is zero, take Option 3.
2. **If yes: Option 1**, `within <root>` in `index.bs`, segment-aware prefix. It is the only option that costs the callee
   author one line rather than a list they must keep current, and (b) and (c) are forced above. Take Option 2 instead only if
   David judges subtree over-admission (siblings) to be the pain; that is a question of taste on real code, not on cost.
3. **Do not** add a marker on the signature, and do not spell it `internal`: the word means assembly in C# (RECORDED 22),
   and here it would mean subtree. Also not `friend` for Option 1 (it means an explicit list in C++; not probed here, so
   treated as a taste point only).
