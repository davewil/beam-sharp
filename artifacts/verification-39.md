## Circularity hunt

1. **How the stripped variant was made.** `erlc -S` the original, `file:consult` the `.S`, replace each `{tr,R,T}` with `R`, drop `{'%',{var_info,...}}` comments, rename the module, and `erlc` the `.S`. I checked the following:
   - I independently normalised `erl_a.S` (my own strip) and compared it with `strip_a.S`. All 129 terms are equal, including non-code terms (exports, labels, attributes). So nothing else changed: no extra call, no identity function, no reordering, no literal-pool change (`StrT` and `ImpT` chunks identical).
   - `beam_disasm` instruction lists: 116 vs 116, identical once `{tr}` is dropped. The Code chunk shrinks 400 to 384 bytes, exactly the 8 extended operands.
   - **A control the brief lacks:** I recompiled the *unstripped* `erl_a.S` from `.S` (module `v_rt`). Code and Type chunks are byte-identical to the original, and its time is 1.000x (0.998-1.004x). So "compile from `.S`" costs nothing, and strip_a vs erl_a is not a source-vs-`.S` artefact.
   - The Line chunk differs in size for strip_a (48 vs 36 bytes) and so does CInf (187 vs 171). That is metadata (a longer module/file name), not executed code.
2. **Negative controls exercise the same path.** `erl_b` is built like `erl_a` (from source), and `strip_b` like `strip_a` (from `.S`). Both copy pairs agree within 1%.
3. **Does the loop hide something dominating?** The opaque-call trick (row 9) is only a parameter on `part_two/2` and does not add a call inside the hot loop. The `b_*` files differ in one line (diffed). `wrap`, `hit` and `spin` are identical across them.
4. **Is the effect an annotation effect and not code layout?** My independent probe below changes *only* the Type chunk. The effect remains.

## Fidelity of the emitter model (a2)

I read `bs_emit.erl` and `bsc.erl` and checked the following.

- `e_foreign_call` produces `{call,{remote,erlang,rem},[..]}`. For a plain non-channelled `int` return, `return_guard` wraps it as `case Call of V when is_integer(V) -> V end`. The model's `guarded/1` is the same shape.
- `-spec` is emitted for every function, private included (`bs_emit.erl:8-11, 32`), widened. The model uses `integer()` specs. The `?A` annotation is `0`, so no line information. The model parses real Erlang with line numbers, and the line difference affects only `{line,..}` instructions outside the loop (a3 addresses `from_abstr`).
- Not modelled: `-type` declarations, `bs@type_atoms/0` exported, and the F24/F37 guards on exported functions (only `PartTwo`, outside the hot loop). I judge this immaterial to `spin`.
- **`bsc` passes no `inline`:** `compile:file(AbstrPath,[from_abstr,debug_info,{outdir,Dir},report_errors,report_warnings])` at `bsc.erl:843-846`. No `inline` anywhere under `compiler/src`. (An `ERL_COMPILER_OPTIONS` environment variable would still be honoured by `compile:file`, which no one has checked, but that is not a default.)
- **Gleam passes `inline`:** the generated `.erl` has `-compile([..., inline])`.

The conclusion "the current emitter's shapes keep the annotations (on OTP 25)" is supported as far as a stand-in can be. It is still unproven for real bsc output and for OTP 28, and the brief says so (Limitations, headline 1, Option A).

## Independent probe (different method)

I patched the **Type table only** of the *existing compiled* `erl_a.beam`. Every 18-byte entry was replaced with `beam_types:encode_ext(any)`; the Code chunk bytes were not touched and nothing was recompiled. A same-length module rename only, with a rename-only control built by the same script. (`mine/patch.escript`, `mine/patch2.escript`, `mine/sdiff.escript`.)

| Variant | min rel | med rel |
|---|---|---|
| plain `.erl` compile (v_plain) | 1.000 | 1.000 |
| identical copy | 1.000 | 0.999 |
| renamed, types kept (control) | 0.992 | 0.994 |
| **Type table neutralised** (erl_p, erl_q) | **1.055-1.075** | 1.061-1.071 |
| `.S` round-trip, unstripped | 1.000-1.004 | 0.998-0.999 |
| `+inline`, types kept | 0.569 | 0.567 |
| `+inline`, types kept (renamed control) | 0.565 | 0.566 |
| `+inline`, Type table neutralised | 0.710 | 0.707 |

Agreement:
- Missing type annotations alone cost about 6-7%, with the same code bytes. The brief's effect, from a different mechanism.
- Inlined: neutralising types costs 0.710/0.565 = **+25.7%**, matching the brief's +25%.
- Inline explains most of the gap regardless: inlined **without** types (0.71x) still beats plain **with** types (1.00x). So Option B's measured benefit does not depend on annotations being kept.

## Defects and caveats (none change the verdict)

1. `probes-39/c/ex/out.txt` as committed is an error trace, not the probe output. Brief row 13 cites it. Re-run output is correct.
2. `run_all.sh` does not regenerate `a2/cmp_fn.out` as committed, nor `b/time2.out`, `e/time_guard_private.out`, `a/run_partial.out`. I re-ran time2 by hand only.
3. Headline 2's "the ticket's 20% is the size you get when the loop is tight" is a stretch. The +25% needs an inlined loop; the ticket's baseline (bsc vs plain Erlang, no inline) corresponds to the +5-7% case here. Treat 20% as unreconciled on OTP 25.
4. The strip/patch proves "no type annotations => slower" but does not show that real bsc output lacks them. The gating question in the brief (run real bsc on OTP 28 and diff `{tr}`) remains the only way to answer that, and the brief correctly puts it first.
5. The brief has no `.S`-roundtrip control; I added one (clean).
6. Synthetic input, answer 6725 (disclosed).
7. Absolute timings are for a slow VM (17.5 ms vs the ticket's 5-6 ms). Only ratios transfer, as the brief says.
