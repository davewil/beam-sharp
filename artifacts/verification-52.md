## 2d characterised (reused `_build`)

- Fresh `_build` every time, as `run.sh` does: stable. Two consecutive full runs produced identical output.
- Reused `_build`: `A then C` still prints the `:ssl` warning although `EXTRA=logger,ssl`, so the author's observation is real. `C then A` prints **no** `:ssl` warning although `ssl` is not declared. So it is stale in both directions.
- The generated `_build/dev/lib/app/ebin/app.app` **is** rewritten correctly with `ssl` in `applications`. The stale thing is therefore not that file. The warning disappears if `mix.exs` is touched between runs (`A`, touch, `C` gives no `:ssl` warning).
- Conclusion: Mix tracks `mix.exs` by mtime, not by its evaluated output. The fixture changes the evaluated output through environment variables without touching the file. The brief's "Is Mix's check stable? No, in this version" is overstated. With edits to `mix.exs` the result is correct, and the brief's inference "Mix reads a cached app spec" is only half right (the cached thing is not `app.app`). The cause of the stale warning stays unexplained. It does not damage the recommendation, but row 2d should say "stale when `mix.exs` is unchanged on disk".

## My independent probe (`mine/v_map.erl`, run in `mine/`)

It uses **real installed trees only**, with no hand-built fixtures: 1669 beams in 42 OTP and Elixir `ebin` dirs. It compares three mappings: path-parse (M1), `.app` `modules` (M2), and `application:get_application` after `application:load` of every app (M3).

- M1 and M2 agree on 1638 of 1669 beams. The other 31 are in **no** `.app` `modules` list (asn1 20, diameter 8, erts 3). No beam is declared by two apps. No single-declared beam disagrees with its directory.
- M3 agrees with M2 on 1638 of 1638 single-declared beams. Row 3b ("useless at compile time") is true only for **unloaded** apps. After `application:load` it works. The brief never tested that, so its dismissal of M3 is untested rather than refuted.
- `.app`-declared modules without a beam: 0.
- Presence check: in the escript VM `code:which(emb)` returns a path. In a plain VM the same module gives `non_existing` / `{error,nofile}`. So **the module-present check is not "sound in every failure case"**. Run inside `bsc` (an escript), it says "present" for any module bundled in `bsc` (`using :bs_check {...}` would pass) that the target program will not have. The brief cites 3c as supporting soundness, when 3c actually shows the presence check can give a false "present" (a check that runs in `bsc`'s VM cannot see the target's code path).

Agreement with the brief: the module->app mapping is genuinely unreliable at the edges (preloaded, escript-embedded, modules unlisted in `.app`, ambiguity under duplicates). Disagreement: on real installed trees the `.app`-scan mapping is correct for 98% of modules and unambiguous everywhere. "Unsound in four measured cases" is true, but three of the four are fixtures I could not find in the wild, and the unmapped real cases (31 beams) are a fifth that the brief missed. "No prefix rule recovers it" holds. The recommendation of "no ownership check" survives on the preloaded and escript cases alone.

In `bs_lexer.xrl:125` an `atom_lit` requires a leading colon, so as specified it must be `in :req`. `in` is already a lexer keyword (`bs_lexer.xrl:54`); `requires` is not. The brief states the spellings are unchecked, but this is checkable and it is wrong as written.

## Verdict

**Mostly reproduces; two claims overstated.** Every measured output reproduces (modulo a timestamp and benchmark noise), the MEASURED-HERE / RECORDED-NOT-RERUN labelling is honest, and the file:line citations are correct to within a line. Overstated: (a) 2d "Mix is unstable" is a `mix.exs`-mtime artefact of the env-var fixture; (b) the module-present check is not "sound in every failure case", because under `bsc`-as-escript it can pass modules the target will not have; and the "unsound in four cases" count rests on three hand-built fixtures that I could not find in 1669 real beams. The recommendation (Option C, name only, warnings, no ownership check) is not refuted, but its Option B/C spellings do not lex as written, and 3b's dismissal of `get_application` is untested after `application:load`. Could not verify: bsc behaviour, Req/Jason, Elm, OTP 28, the cause of the Mix staleness.
