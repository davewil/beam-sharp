# Decision brief: ticket 57 (ENG-239), where does the fold of `-5` belong?

Prepared for David. Nothing under `wayfinder/` or `compiler/` was edited, nothing committed.
Probes: `probes/` (`run.sh` regenerates every `.out`; header comments hold the predictions).

## Question

`type T = int where value >= -5` is refused as `opaque_refinement`; `Sign(<= -1) -> :neg` compiles. Where does the
fold of a negative integer literal belong: the grammar or the checker? And what is the answer to the residual
doctrine (a residual like `-10..-1 | 1..10` must be writable)?

## Three things the ticket does not say (read these first)

1. **The ticket's mechanism is stale, its symptom is not.** It says `-5` reaches the checker as
   `{e_op,'-',{e_int,0},{e_int,5}}`. Since F51 (2026-09-16) it is `{e_neg,L,{e_int,L,5}}`. Refusal is unchanged.
   The stale shape is RECORDED in ticket 57 §"Why it happens"; the current shape is MEASURED `probes/bsc_pieces.out` P1 and SOURCE `bs_parser.yrl:584,907-908`.
2. **The same defect hits guards, silently.** `F(n) when n >= -5` / `F(n) when n < -5` parses and is accepted as a
   guard, but `alternatives/1` returns `unknown`, so it credits no coverage and the two-clause function is reported
   inexhaustive with residual `(int)`: the *whole* type. The same shape with `0` is exhaustive. MEASURED
   `bsc_pieces.out` P7a vs P7b. SOURCE `bs_check.erl:4593-4599` ("An unread guard ... credits no coverage"). There is no diagnostic naming `-5`.
3. **A negative literal in an expression is typed `int`, not a singleton.** `type Neg = int where value <= 0;
   Neg F(int n) / F(n) -> -1` is refused (`return_not_declared`), `-> 0` is accepted. MEASURED
   `fold_prototype.out` F3/F3b. SOURCE `bs_check.erl:2803` (`e_int` types as `range(N,N)`) vs `:2807-2811` (`e_neg` types as `int`).
   So even after refinements can *say* `-5`, the author cannot *return* `-5` into one.

## Sub-decisions

- **(a)** grammar-level literal (mirror `int_lit`), or checker-level fold. (A third place exists, see Option B.)
- **(b)** if checker: how far. `-5` only; `2 + 3`; named constants. Does "refinement and guard share one reading" survive?
- **(c)** must a pattern and a refinement of the same literal share one reader?
- **(d)** residual doctrine: are residuals writable afterwards?

## Option A: grammar-level literal in the refinement (the ticket's first answer)

New nonterminals so that `refinement` comparands are `int_lit` (`bs_parser.yrl:464-465`) instead of `expr_low`.

```csharp
type Delta = int where value >= -100 and value <= 100   // compiles
type Gap   = int where value >= 1 or value <= -1        // compiles (residual of Delta minus 0, now writable)
type Five  = int where value >= 2 + 3                   // parse error: a refinement comparand is a literal
Step(int n) when n >= -5 -> ...                         // STILL unread: credits nothing, residual (int)
Neg F(int n)  /  F(n) -> -1                             // STILL refused: return_not_declared
```

Compiler delta: `bs_parser.yrl:216` `refinement -> expr_low` becomes a small predicate grammar (`pred -> pred 'and' pred | pred 'or' pred | 'value' cmp int_lit | int_lit cmp 'value' | 'value' cmp atom_lit`, plus whatever `alternatives/1` reads at `bs_check.erl:4624-4631`); `bs_check.erl` untouched. Yecc conflict count: UNVERIFIED (baseline recorded as 5 in F53).

- Evidence for: smallest checker change; makes pattern and refinement agree by construction (evidence 4 vs 1). Fixes the reported repro (evidence 13 shows the checker downstream is ready).
- **Strongest counterargument:** it splits the grammar the source comment forbids splitting (`bs_parser.yrl:212-216`: a refinement is an `expr` "so a refinement and a guard cannot disagree"). After A, `value >= -5` in a refinement is read and `n >= -5` in a guard is not, on the same `alternatives/1`: the invariant F2.5 exists to protect is broken *in the one case that mattered*. It also leaves finding 2 (silent guard) and finding 3 (return `-1`) untouched.

## Option B: fold in the parser action `negate/2` (not in the ticket's two options)

One clause beside the float clause that is already there (`bs_parser.yrl:907`):

```erlang
negate(L, {e_int, _, N}) -> {e_int, L, -N};      %% the new clause, before the catch-all
```

Grammar unchanged, `refinement -> expr_low` unchanged, one meaning for refinement, guard, body, emitter.

```csharp
type Delta = int where value >= -100 and value <= 100   // compiles
type Gap   = int where value >= 1 or value <= -1        // compiles
Step(int n) when n >= -5 -> 1 ; Step(int n) when n < -5 -> 2   // now read, exhaustive, no residual (fold_prototype F2)
Neg F(int n)  /  F(n) -> -1                             // compiles (type_of sees range(-1,-1), F3 neg_all)
(-5, _) = p                                          // a bare `=` match: compiles (to_match sees e_int); parse error today (P10)
type Five  = int where value >= 2 + 3                   // still refused (F4): no arithmetic fold
```

Compiler delta: `bs_parser.yrl:907-908` one clause. Nothing in `bs_check.erl` (`comparison/1`, `type_of`, `to_match`, `to_param` already take `e_int`), nothing in `bs_emit.erl` (mirror at `:687-690` already matches `e_int`; `:650` already emits negative `e_int`). The `e_neg` consumers (evidence 10) keep serving `-x`. Error text of `opaque_refinement` is unchanged and its advice becomes true.

- Evidence for: 1 line; both readers (checker, emitter mirror) change with zero edits (evidence 8, 9); guard, refinement, return typing and `to_match` fixed together (13, 14); precedent in this parser for exactly this fold (3); Erlang and Elixir both produce the same *result* by folding literals wherever position demands it (16, 17, 21), and the beam is identical either way (19). Cost is `-5` becoming 7 words instead of 14 (22).
- **Strongest counterargument:** it is a semantic change wider than the ticket, and the ticket says "should not guess". `-1` in *every* body now types as a singleton and `(-5, _) = p` newly parses, so any test that pins today's `int` typing or the `to_match` error is a candidate to move. **UNVERIFIED** here: the 1000+ test suite cannot run. It also folds inside `- (5)` and `- -5` (P4c/d shapes), harmlessly (`- -5` folds to `5`) but not by anyone's decision. And the parser gains a fold while the ticket's design intent says the *checker* owns meaning: Erlang and Elixir both keep the parser dumb and fold later (16, 20), which is the same trade the other way.

## Option C: checker-level fold, scoped to `alternatives/1`

A helper `const_int/1` used by the two `comparison/1` int clauses:

```erlang
comparison({e_op,_,Op,{e_var,_,V},E}) -> case const_int(E) of {ok,K} -> int_cmp(Op,V,K); error -> unknown end;
const_int({e_int,_,K}) -> {ok,K};   const_int({e_neg,_,E}) -> negate(const_int(E));   %% C1
%% C2 adds  {e_op,_,Op,A,B} when Op =:= '+';'-';'*'  over two const_int;  C3 named constants: no form exists (evidence 12)
```

```csharp
type Delta = int where value >= -100 and value <= 100   // compiles (C1)
type Five  = int where value >= 2 + 3                   // refused under C1, compiles under C2 (F4)
Step(int n) when n >= -5 -> 1 ...                       // read by the checker, exhaustive
Neg F(int n)  /  F(n) -> -1                             // STILL refused (F3 neg_pred): type_of is not touched
```

Compiler delta: `bs_check.erl:4624-4625` (two clauses) + a `const_int/1`; **and** `bs_emit.erl:687-690` must learn the same shape, because that mirror is a second reader of the same guard (evidence 8). If only the checker learns it, the checker credits `n >= -5` while the emitter emits no `is_integer` kind test for it (its `kind_expr` falls to the catch-all), which is the "hole" `bs_emit.erl:666-679` describes, in the unsafe direction: an atom compares greater than any integer, so `:ok >= -5` passes. That interaction was derived from source, not run (bsc cannot be built). Optionally `type_of` at `bs_check.erl:2807` for finding 3.

- Evidence for: matches the ticket's stated design intent (one grammar, checker owns meaning); C2 is a strict superset if arithmetic literals are ever wanted (15); Erlang folds arithmetic in patterns too (17, general `partial_eval`).
- **Strongest counterargument:** three readers must be kept in lockstep by hand (`alternatives/1`, `kind_expr`, and `type_of` if finding 3 is to be closed), and the emitter's comment says the *only* thing keeping them safe is that they mirror each other. Option B has one reader by construction. C2 buys `2 + 3` in a refinement, which nothing in the repo asks for and which has no constant to name (12).

## Sub-decisions under each option

| | A | B | C |
|---|---|---|---|
| (b) reach of the fold | `-N` only, by grammar | `-N` only (`negate/2` sees `e_int`) | C1 `-N`, C2 `+ - *`, C3 impossible (no constants) |
| refinement and guard share a reading | **breaks** (evidence 6 vs A's grammar) | yes, by construction | yes, if `bs_emit` mirror updated too |
| (c) pattern and refinement share a reader | yes (`int_lit`) | yes, both are `e_int`/`p_int` of the same value; they still have two grammars | no (pattern is `int_lit`, refinement is `const_int`) but the same value |
| (d) residuals writable | yes (F5 shape) | yes (F5) | yes (F5) |

## Recommendation

**Option B**, with (b) fixed at "`-N` only; no arithmetic, and no constant form". Reasons, each from the evidence:
the invariant the ticket wants to keep (one grammar, one meaning) survives without a second reader to keep in step
(8, 9); it is the only option that also closes the guard hole and the `-> -1` typing hole, which the ticket did not
know about and which A and C1 leave (13, 14); the parser already folds the float twin of this literal (3), so the
bytes of the change are the existing precedent; and it is one clause. Fold arithmetic (C2) only when a program asks
for it. If David judges that meaning must stay in the checker, take C1 and take the `bs_emit.erl:687-690` change in
the *same* commit; do not take A, which reopens the split F2.5 was written against.

Per CLAUDE.md the order is: failing test + gate first. The natural failing tests are the P1/P3 programs, the P7a
guard pair and the F3 return, each currently red (evidence 1, findings 2 and 3). Suite regression risk of B is the
UNVERIFIED point above and should be the first thing run once `bsc` builds.
