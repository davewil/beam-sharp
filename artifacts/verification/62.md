## Circularity / weakness flags (file:line)

- C1. 62-06/run.sh:22 and alias.patch: the "none" baseline is the PATCHED compiler with BS_ALIAS unset, not the unpatched
  bsc. I checked: patched-none and the repo's unpatched bsc output for Shop have every beam chunk byte-identical
  (only CInf, the compile-options chunk, differs). So the baseline is sound, but the probe does not show it.
- C2. 62-06/run.sh:28-29: "min/median" with 9 runs is sorted index [4] = median, correct. But the timings are noisy across
  my re-run: compile median N=50 was 544-589 ms vs the brief's 446-453 (machine load), load 3.3-4.4 ms vs 3.0-3.6. The
  brief's "indistinguishable" and "no trend" still hold in my run, but the quoted absolute figures are not reproducible.
  Brief line 136 "3.0-3.6 ms in every cell": my run gave 3.5-4.4 ms.
- C3. Call-cost claim (brief line 138): "96.7 vs 98.7 ms in one run, 126 vs 92.7 in another". 62-06/out.txt contains only ONE
  run: direct 92.7 ms vs alias 126.0 ms. The 96.7/98.7 pair is in no out.txt. My re-run: direct 90.8 vs alias 105.6.
  Alias was SLOWER in all three runs I can see (126, 105.6, and the author's unrecorded second). The "sign disagrees,
  so no figure is claimed" statement is not supported by recorded evidence; the recorded evidence leans alias +15-35%
  (fine for a tail-calling wrapper; one extra local call). Also the 2M-call loop uses `lists:seq` and a fun, so it
  measures mostly the fun/seq overhead. The brief's final stance (no figure claimed) is safe; the "noise" sentence is not.
- C4. 62-07/corpus.py:17-33: the regex skips every .bs file with no `module` line. I measured the 30 skipped public
  declarations: all are in compiler/examples/exemplars/25a-25g (the realistic multi-file programs), not "scripts" as the
  brief says (lines 146-147). Including them: still 0 derived-name collisions; no acronym/digit names; they add
  HandleInfo, Init, HandleCall, HandleCast (callback-lowering cases) in 25c, 25d, 25g. Conclusion survives; the
  description of what was skipped is wrong, and the skipped files are the most realistic ones. The collision count is
  arity-blind (upper bound), which is conservative. The corpus has no acronym names, as the brief admits, so 0 says little.
- C5. 62-10 collision demo: the "silent collision" is a property of the prototype keeping the first alias. It does print
  `alias-collision` to stderr; the brief says "silently returned 2": it means at run time. Fine, but it is a demonstration
  of the prototype's policy, not evidence about a hypothetical real rule.
- C6. 62-02/out.txt: the only elixirc warning is for the deliberate `Shop."New"` alias-trap line; the "no warning for

## Headline independently confirmed

In a temp dir with bsc-built Shop: from a .exs file, from a mix project (`mix compile`, `mix run`), via `elixir -e`:
`:Shop."New"(1)`, `2 |> :Shop."New"()`, `Enum.map(1..2, &:Shop."New"/1)`, `m = :Shop; m."New"(5)`, `apply(:Shop,:New,[1])` all run
correctly, with no compile warnings under mix. `mix format` rewrites `:Shop.'New'(1)` to `:Shop."New"(1)` and leaves the
quoted form alone. `:Shop.New(1)` fails with the "start with lowercase" error. `Shop."New"(1)` resolves to the Elixir alias,
as the brief says. So the premise "Elixir cannot dot-call a PascalCase export" is false for 1.18.5.
Gleam: `GetById`/`getById`/`HTTPGet` function names rejected, `@external(erlang,"Shop","New")` runs and prints the map
(62-03 re-run). Confirmed.

## Own falsification

- Names with underscores, digits, acronyms (`Get_By_Id`, `Sha256Hash`, `HTTPGet`, zero-arity `Zero`): bsc exports them as
  written and `:Odd."Get_By_Id"(1)` etc. all call fine. The quoted-call story does not break for any identifier B# accepts;
  a quoted atom has no failure case. Lowercase function names are a B# syntax error, so there is no mixed-case exposure.
  Operator names are not valid B# function names. Unquoted `:Odd.Sha256Hash(1)` fails to parse as expected.
- Versions: only Elixir 1.18.5 / OTP 28 available. The tokenizer path is old (quoted function names after `.` have been in
  Elixir since 1.x), but I did not test 1.14-1.17 or 1.19; the brief's version claim is limited to 1.18.5 and says so.
- Ticket 32 line 204: quote accurate (ellipsis-free: "There is no snake_case ⇄ PascalCase rule anywhere in the language."; the
  brief writes <->). Context is question 3 "How does a snake_case Erlang name become a beam-sharp name?" (line 44): INBOUND
  evidence ('PKCS-1' unspellable). The brief itself says this. Ticket 32 line 344 repeats it as a language-wide bold claim.
  The brief's reading (text is language-wide, so Option B would be a carve-out) is fair. The 196-198 "lowercase name would
  have lexed as a field projection" passage is about a foreign module's function binding (`Ets.Lookup`), so the brief's use
  of it against "change convention to snake_case functions" (line 166-168) is an extrapolation, though plausible.
- Stray artifact: untracked /home/user/beam-sharp/a.out (416 B, 23:18) in the repo root, outside artifacts/. Not from my runs.
  Likely produced by the author (erlc/escript step). Brief says "nothing edited except artifacts/": that is slightly untrue.
