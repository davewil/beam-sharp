## Unfiltered calls (the `call()` helper)

`call()` in `p59_scope.sh:44` evaluates `catch Expr` and rewrites an `{'EXIT',{E,[{M,F,A,_}|_]}}` to `{crash,E,M,F}`, dropping the arguments and
the stack. I re-ran the same calls with a try/catch escript that prints class, reason and top frame (not the helper). Results are the same in
every row (e.g. G1 nested tag `7`; G1 no-Credit `error:{badkey,'Credit'}` top frame `erlang:map_get`; G2 `function_clause` top frame
`{'G','Classify',[100.5],...}`; base RunBytes([100.5]) `big`). The helper does not hide or invent anything for these rows; it does collapse a
`function_clause` raised inside a callee and one raised at the entry into the same shape except for the `F` field, which the table does print.
Extra inputs I ran that the script does not: `RunBytes([300])`, `[-5]`, `[a]`: base and G1 answer `big`/`small`/`big` (the atom `a` answers `big`
because atoms sort above numbers in Erlang term order: an out-of-domain value of the wrong KIND, not just range); G2 `function_clause` in
`Classify` for all three. `ClassifyPublic(300)` and `(a)` are `function_clause` in all builds.

## Circularity findings

1. **The first-run edit to `p59_scope.sh` (Kind spelling) was a legitimate fix.** Evidence: the compiled tag is the module-qualified
   `'G.Order'`/`'G.Customer'` (the existing `compiler/examples/Shop` comment writes `:'Shop.Invoice'`). I forged the author's original spelling
   (`'Order'`, `'Customer'`) against the unpatched build: `function_clause` in `RunOrder` (the top-level tag test rejects it), so the control would
   crash in every build exactly as the author reported. The edit changed the control from a wrong-input crash to a valid input; it did not tune any
   row that distinguishes G1/G2 from base. The script's valid-Order row is the proof the corrected forgeries use the real tag. The git history of
   the probes is not available to check the author's earlier version (`artifacts/` is untracked), so this rests on my re-creation, not on a diff.
2. **Threat model: realistic but narrow, and the probe says nothing outside it.** The forged values are produced by Erlang calling an exported
   function (`p59_scope.sh:46-52`). That is the case the boundary guard exists for (CONTEXT.md "Boundary guard": a term supplied by a caller
   outside the checked world). What the probe shows: the exported guard (unpatched) tests only the top-level parameter (tag for `Order`, nothing
   for the elements of `list<Byte>` or the type of a nested field), and a private callee can then receive a value the type does not admit.
   What it does not show: that any B#-only caller can produce such a value (see 5), how common an exported function taking a container of
   refined ints or a record holding a record is, or that a real caller would send these. The probe program was written so that the exported
   function does not look inside (`RunBytes(list<Byte>)`, `RunOrder` with a nested `Customer`); the same wrong value sent to `ClassifyPublic`
   directly is refused (that row is the control for it).
3. **The rows were not shaped to manufacture the G1/G2 difference beyond the program choice.** G1's row differs from base because `Inner` has
   no tag test under G1 and nothing else checks `Customer`; G2's `RunBytes([100.5])` row differs because `Classify` gets `is_integer`. These are
   direct consequences of the one-line patches and I confirmed them with unfiltered calls. The only selection is in the program: `Inner`
   and `Classify` are private functions whose parameters are exactly the types each guard covers, called with a value one level inside an
   exported argument. A program with a private record function reached only from checked call sites would show no difference between
   builds; that is true by construction and is not probed (and is the "dead weight" side of the ticket's argument).
4. **No fixed point between the prototypes and the claims.** The tests that G2 breaks were not edited; they fail exactly because they pin the
   old decision (`boundary_kind_tests.erl:87` and the range test), and G1 breaks none because nothing pins the private tag test; both read
   from the test sources, not from the author's say-so.
5. **Is the nested-forgery route real in B#-only code? I could not find one.** I wrote B# against the unpatched compiler to hand a private
   `Classify(Byte)` a float or out-of-range int without an Erlang forger:
   - `Classify(t)` with `t: term`: refused at compile time ("argument 1 is not covered ... atom | int <= -1 | int >= 256 | float | ...").
   - `Classify(:erlang.float(x))`, `Classify(x + 300)` with `x: int`: refused ("int <= -1 | int >= 256").
   - `Box{ V = n }` and `b with { V = 300 }` for `record Box { V: Byte }`: refused ("assigns V a value Box does not accept").
   - A foreign declaration returning `Byte` (`:erlang.abs(-300)`) or `(int, Byte)` (`:erlang.list_to_tuple([1, 100.5])`): compiles, with a
     warning ("no clause will ever match"), and at run time raises `case_clause` at the foreign-return guard (F42) in both the unpatched and
     G2 builds, before reaching the private function.
   - `list<Byte>` and `map<atom, Byte>` as foreign returns were not accepted as promises (F40: only O(1)-decidable parts), and `number` is not a
     builtin type, so those routes do not exist.
   I did not exhaust B# (receive/mailbox, gen_server `handle_call` state, `code_change`, `ValidateAs` results were not tried: the
   `term`-typed message route needs a validator the author would have to bypass). So: the only route the probes exercise is an external
   caller to an exported function whose guard does not look into containers. In B#-only code I found none that compiled and ran.
6. **Timing probe times what it names, with the answer asserted.** `p59_cost.sh` runs `time_one.escript` (one fresh VM per sample; `min` of
   25 calls to `Day01:PartTwo`), asserts the answer is 6770 in every sample, and compares `base/Day01.beam` with `G2/Day01.beam`, both compiled
   from `aoc/bench/Day01` by the respective builds (I built these myself; G2's has 19 `is_integer` against 2). The variant dirs and the input
   path are arguments, so the script cannot time what it does not name; it does not itself check which build produced the beams. Interleaving
   order is fixed (base then G2 each round), so a slow-start bias would favour base, not G2.

## Unsupported or overstated

- "Beam bytes over 25 example modules" is overstated: 22 compile; 3 "fail" through the script's own `--src-root`/directory handling, not
  through the compiler. The two aoc programs, including `aoc/bench/Day01` (G2: 2328 -> 2584 bytes, +256 on that module alone, from my own
  build), are outside the total. Exemplar directories (`25a`-`25g`) do not compile in any build (README of the handoff says none parses yet) so
  they are not measured; they contain private functions on closed records (e.g. `Row(OrderRow o)`), so the G1 figure (+0 bytes) is
  "zero over modules that have no private closed-record parameter", which the brief states ("the examples contain no private record
  parameter") and which is true of the 22 modules measured (checked by grep), but G1's byte effect on a program with such functions was never
  measured (the +14 bytes per parameter is quoted from ticket 26a, not re-measured here).
- C4's "no cost" is for one function family: six private `int` functions in one benchmark. It says nothing about private record or float
  parameters under G2, nor about guards on a private function called from other builds' call patterns. G2 measured 0.7-1.0% faster, twice;
  I cannot say whether that is noise or an effect of the added type tests on the JIT, and the probe does not separate them. The
  brief's "a 1.2% *gain*" is the author's number (12.95 vs 12.79); mine were 0.7% and 1.0%.
- "The private tag test is the only thing that catches a wrong-kind record arriving as a field" is supported only for a record nested one level
  below an accepted exported record, with a private callee whose body projects a field. It is not a claim the probe measures for other shapes
  (a private function that already matches `Kind` in its clause pattern is not tested, since `constrains_kind` would skip the tag test anyway).
- "This is the defect ticket 58 closed for exported functions, still open one call down" is supported for the container-element route
  from an exported argument. It is not shown for any B#-only path (see finding 5), so "live hole" is true for external callers of an exported
  `list<Refined>` only.
- The brief's alternative (guarding the container at the exported boundary) is explicitly not probed, so nothing here supports a
  comparison with it, nor the claim that it would cost O(n) per call.
- `p59_scope.sh` tests only forged values; it has no row showing that G2 or G1 leaves a *valid* nested value working beyond the one valid
  `Order` (7) and `RunBytes([7])`; `RunBytes([7])` is the only element-valid control for G2, and G1/G2 behaviour on private functions with
  other parameter types (atom, binary, tuple, float) is not probed (the code reading above says they are unchanged; the 1492/1494 eunit
  results back that for the cases the tests cover).
