## Circularity findings

1. patches/v60-P.patch (whole). It does what is described: lexer/parser `internal`, `is_public` and `exports_of` export internals, `internal_of/1`, an `internal` key in the World (bsc.erl), and `restrict/2` called at the top of `import_env` (bs_check.erl hunk "import_env(Decls, Self, World0, Mode)"). Nothing extra. Not circular.
2. Is the refusal produced by the new rule? Yes. Same tree, P compiler, KW=public: Other and Other3 compile (rc=0). KW=private: all refused. KW=internal: Other and Other3 refused, Reports allowed. So the refusal is not from tree layout.
3. Does the rule discriminate on names? Yes. I renamed Other to `Shop.Other` (directory Shop/Other) under P/internal: compiles (rc=0). `Shop.Deep.Er` (nested, qualified call with using): compiles. A module `Reports` (outside Shop): refused. The flip follows the module name.
4. Base compiler with KW=internal (p60_who.sh, base): every module that uses Shop.Pricing is refused with "`using Shop.Pricing` names no module", because `internal` does not parse. This is a different failure, not the private message. The script never runs base+internal in its own README flow, so it manufactures nothing, but anyone reading a base-vs-P refusal count for `internal` must know the base refusal is a parse failure.
5. Other2 (qualified, no `using`) is refused identically in base, P, and all three KW values. It is not evidence about the patch; it supports only C1's "qualified call cannot bypass using".
6. p60_who.sh printf line: `out=$(...); rc=$?` is on one line sequence; rc is captured directly after the command substitution, correctly. Output is `head -3 | tr | sed | cut -c1-200`, which truncates the message. I read full output and found no hidden different failure. The first 3 lines can in principle hide a second error, so rc plus the first message is the only evidence.
7. build_variant.sh filters erlc output with `grep -E 'error|Error' || true` and `set -e` is defeated by `|| true`: a compile failure would be swallowed and only the file count (16 vs 16) would show it. Both builds ran and behaved differently as expected, so the patch built; the risk is latent.
8. p60_neighbours.sh controls: the Gleam section has a positive control only for the same-package import, not a control that proves Gleam's compiler can reject an import. I added one (import of nonexistent `dep/nope`): `gleam build` rc=1 "Unknown module". So a rejection would have been visible; the internal imports genuinely were not rejected. The Elixir section has no negative control for "@doc false would warn", but defp shows the compiler does warn on bad cross-module calls, and the @doc false call printed no warning. Erlang has its own control (hid vs pub).
9. Gleam caveat that the probe cannot settle: the dependency is a path dependency. If Gleam's internal check keyed on dependency source (Hex vs path), the probe would not see it. I found no evidence either way; not tested with a Hex package (README says Hex is blocked).

None of the above manufactured a result.

## Unsupported or overstated

- C4: the scale chain declares only `public` functions and no module has `internal`, so `restrict/2` always takes the `(_, E) -> E` clause. The expensive branch (`within`, `subtree_root`, `maps:without`, `maps:merge`) is never run at scale. The probe shows the map traversal is cheap, not that the full rule is cheap. Each module also `using`s only its predecessor, so tables stay small.
- C4 also covers one machine (x86-64 VM, 4 vCPU); differences under about 5% are noise, and the N=200 point shows +9% while N=50 shows -4%.
- C3/C6: P adds no eunit tests, and the patch tests nothing for `internal` on records, types, protocols or single-segment module names (subtree_root of `Foo` returns `Foo`, so only Foo itself is inside); these are unprobed.
- C3: the usage of `internal` only in the same-name-root sense ("subtree rooted at the declarer's parent namespace") is shown for Shop.* only. Directories and module names coincide in the probe tree; a module whose directory disagrees with its name was not tried.
- C5: "Elixir defp is the enforced form" overstates; it is a warning plus runtime error. The Gleam result is for a path dependency only. The script cuts Gleam output with head -14 and Elixir with head -4.
- C7: the ticket's own citation "add_module_import/5" is wrong in the current tree (it is /3), and the ticket text (measured at 0b761f6) is stale; it is not a probe claim.
