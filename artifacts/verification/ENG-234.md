## Circularity findings

1. `p52_provenance.sh` S4 (about line 46-50): `Apps = [... || A <- [demo], (application:load(A) =:= ok orelse true), ...]`.
   - The candidate list is the literal `[demo]`, and `orelse true` makes the load check unable to fail.
   - Effect: the script cannot show "scan finds the owner". It only shows that, given the right application name, the module is in its `modules` list and `vsn` is readable.
   - Did it manufacture the result? Partly. The answer `{"1.2.3",demo}` is confirmed only by the `code:which` path. `demo-1.2.3` in that path is real compiler-independent evidence, but the "scan" is not a scan.
2. `p52_cost.sh` scan loop: it iterates over the names `app1..appN` it just created and calls `code:lib_dir(A)` on each. That is not discovery over ERL_LIBS. It measures a lookup-by-known-name plus `file:consult`, with a one-module, one-line `.app` per application. Real `.app` files with long `modules` lists and `applications` would cost more per app. The "N apps, ~300 us each" figure is a lower bound for that shape, not a measurement of "which application owns module M". The header also says it measures `code:ensure_loaded`, but only `code:which` is timed.
3. `p52_cost.sh` size measurement: it builds from a pre-saved `fixtures/uses.abstr` via `compile:forms`, with the attribute inserted by hand at line 0. It does not go through bsc, so it shows what an attribute costs in a tiny module. It does not show that bsc could emit it. The 640 B base is tiny, so +60 B is not a percentage that generalises.
4. `p52_provenance.sh` S2 shell handling: the `bsc` function, called with `ERL_LIBS` set as a prefix or unset in a `( unset ERL_LIBS; ... )` subshell. The author's fix is legitimate. I confirmed independently that in that VM `ERL_LIBS` is unset and `code:which` returns `non_existing`. I also confirmed rc=0 on base without the dependency, so S2's failure under Q is caused by the patch and not by a broken invocation. `PIPESTATUS[0]` does capture bsc's exit code (the rc=1 matches my direct runs).
5. `trim` (`head -N | cut -c1-170`) truncates output to 3-4 lines. S1 printing only "42" and S2 printing only three error lines is consistent with my unfiltered runs, so nothing was hidden here. But the filter could hide extra diagnostics. In S1/S2 the `.beam` output is not listed, so "compiles" rests on rc alone. I verified that base S2 writes `Uses.beam`.
6. `patches/v52-Q.patch`: it does exactly what is described. It adds one list comprehension in `check_dir1` that calls `code:ensure_loaded/1` on each `{foreign,Line,Mod,_}` declaration and raises `{unknown_module,Mod,Line}`. It reuses the existing error, which is why the message is misleading. It has no side effects beyond loading the module into the compiler VM. It does not run in the base build. No hard-coded pass condition.
7. `neighbours.sh` uses `sed`/`head`/`tail` and `cut` filters, and `env -u` is applied to external programs only (erlc, erl, elixir), so those are fine. `2>&1 | sed` on the erlc "lacks dep" step shows the real compile errors. No `|| true` hides a result. Control present for most items (has dep / lacks dep for include_lib; present vs absent for the others).
8. The eunit comparison (C8) cannot fail meaningfully for Q. A grep of the tests shows the `using :mod` cases name OTP modules such as `lists` and `erlang`, which always load. So "no new failures" shows only that Q does not break code that already names loadable modules. It says nothing about legitimate uses that name a module not present at compile time. The suite has no case that exercises that.

## Unsupported or overstated

- C3/"derivable without annotation" is supported only for the path form `<app>-<vsn>/ebin/<Mod>.beam`. That is true of rebar3/mix layouts and `_build/*/lib/<app>/ebin` (where the directory carries **no version**, e.g. `_build/default/lib/demo/ebin`). The version would then have to come from the `.app`, and finding the owner requires a scan. The probe covers only a versioned `lib/` directory.
- Stand-in fidelity: `demo` has `{applications,[kernel,stdlib,elixir]}` in the provenance script and `[kernel,stdlib]` in neighbours, with no transitive dependencies. Real Req has an `applications` list (finch, mime, jason, etc.). Req's own modules would live in an app whose transitive closure also has to be present. The probes do not show how provenance would record or check transitives. In the `demo` stand-in the single module sits in a single app. There is no case of a module present in two versions on the path, optional dependencies, or `included_applications`.
- S3 stands for run-time failure only for a missing **whole module**. It would be the same shape for Req, but a version mismatch (the module present with a different function or arity) is never tested.
- The probes show Q refuses at compile time. They do not show a check of **version**: Q only tests presence of the module. Nothing in these probes shows a version comparison.
- `Mix.install` demonstrates in-script declaration but with a path dep. Hex fetching, lock files and version resolution are not covered. Hex and package.elm-lang.org were unreachable, and the README says so.
- The "wrong explanation" in C5 is accurate but depends on the choice of a patch that reused `unknown_module`. A different error would have been equally easy. That is a statement about the prototype, not about the compiler.
- Timings are from a 4-vCPU VM and vary by run (see C7). They support order of magnitude only.
