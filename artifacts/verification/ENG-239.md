## Circularity findings

None manufactured a result. Details, most relevant first.

1. `p57_*.sh` (all) `bsc -o "$W/out"` edit: legitimate. It changes only where artefacts land; the compiler arguments and the checked text are untouched. I ran every probe with it on all four builds and base flips back (C1, C2, C4 all refuse on base).
2. `artifacts/probes/build_variant.sh:9-11`: the build swallows errors (`grep ... || true`, and only prints lines matching `error|Error`). A failed compile would leave a stale or missing beam and the script would still print `built`. Could have manufactured a "variant = base" result; it did not: I checked the beams differ and the variants behave differently from base.
3. `artifacts/probes/57/p57_fold.sh:8`: output is `head -1 | cut -c1-90`. This hides which diagnostic fired past the first 90 characters, so a refusal for a different reason (e.g. a parse error) would read the same as `opaque_refinement`. It did not here: p57_semantics.sh on base prints the full `opaque_refinement` text for the same refinement, and A/B1/B2 reaching rc=0 shows the refusal is the one the patches remove. Residual weakness: the C1 rows only show the first line.
4. `p57_fold.sh:6-7`: a pass is `rc=0` only. Acceptance of `value >= 2 * 3` is not checked for the right set in the shipped probe; the semantics probe covers only `-5`. B2's arithmetic folding being correct is therefore supported only by my own extra run (see C4), not by the author's scripts.
5. `p57_semantics.sh:7-12`: the variable `D` is assigned and never used (dead code, including an undefined `d0()`); it cannot affect output.
6. `p57_semantics.sh:11-17`: `Id -5` passes `-5` as a CLI argument; it is read as an integer (output `-5`), not as an option. A `--` separator is not supported (`bsc: cannot read -- as a value`), so no alternative exists; the result is real.
7. `p57_exprtype.sh:7`, `p57_guard.sh:5`: `head -4` and `head -${3:-6}` truncate output. They show the headline error in every case; nothing hidden changes an rc, and rc is printed from the bsc substitution before the pipeline (`$?` expands before the later `$(...)`).
8. `p57_neighbours.sh:41`: `gleam build | tail -3; echo "gleam rc=$?"` reports the rc of `tail`, not of `gleam`. The success is visible from the `Compiled in` line, so the result was not manufactured, but the printed rc is not evidence.
9. Patch scope: `v57-A.patch` adds exactly one clause in `negate/2`. `v57-B1.patch` and `v57-B2.patch` change `comparison/1` and add `const_int/1`; B2 adds only the `+ - *` clause beyond B1. The new `comparison` heads widen the guard from `e_int` to `e_int | e_neg | e_op` and return `unknown` when `const_int` fails. That `unknown` is the same value the catch-all returned before, so nothing beyond the stated description changed for non-constant operands. Notably the same `comparison/1` serves guards, which is why B1/B2 also fix C2; the probe does show this.
10. A and B differ in `-5` expression typing (C5) because A removes the `e_neg` node and B leaves it. The author did not shape this: the exprtype probe's pass criteria are the compiler's own diagnostics.

## Unsupported or overstated

- C6 shows "no new failures", but the suite has no test that exercises a negative literal in a refinement or guard (`grep` of compiler/test for such cases finds none), and the one test that would compile real programs against variant A, `every_aoc_program_still_compiles_test`, fails identically on base because it asserts `length(Dirs) >= 3` (body_check_tests.erl:297) and the AoC directories are absent here. The other three base failures are `undef` on `bs_check:declarations_pasted/3` and similar. So "A/B change nothing else" is supported only by `every_example_still_compiles` and the rest of the 1494, not by the AoC corpus. The A patch changes the AST for every `-<int>` in any expression, which is the broadest-reaching of the three.
- `eunit_variant.sh:10` writes to `$SCRATCH/tests` but never creates it; a fresh SCRATCH silently runs zero tests (`There were no tests to run`, count printed as `0`) until the directory exists. I created it by hand. A "0 failed" from a script run in that state would be vacuous.
- `p57_neighbours.sh` claims for Gleam "builds a `-5` pattern" but the pattern in the script is `-1`, and the probe shows no AST, so it cannot say where Gleam folds the literal (the script header asks "parser or a later pass?"; only Erlang and Elixir are answered by output).
- `wayfinder/issues/57-negative-literals-in-refinements.md` ("Why it happens") says unary minus desugars to `{e_op,'-',{e_int,0},...}`. The current parser has had a separate `e_neg` node since F51 (`bs_parser.yrl:587-591`, `negate/2`), and the B1 patch is written against `e_neg`. The ticket's mechanism description is stale; the probes do not test it directly (they test behaviour, not the AST). Not a claim in C1-C7, but briefs quoting that mechanism would be wrong.
- C5's Delta result under A shows the literal `-3` is accepted; it does not show how A treats other expression forms (`-x`, `0 - 5` is refused in A per exprtype). The probes cannot support any statement that A makes signed arithmetic generally typed precisely, only literals.
- The base-side rows of `p57_exprtype.sh` and `p57_delta.sh` refuse at the declaration, so they cannot distinguish "the declaration is the only obstacle" from "expression typing also blocks it"; only the patched builds do that.
