## Circularity / gaps
- which-cost depends on code path size: mine 630 us at 32 path entries, 967 us at 38; 855 -> 1455 us at 33 -> 39 (noisy, shared cores). lib_dir is flat (2.0 us at either). m52 adds one Elixir ebin only, so the brief's range is a small-path figure; a real project with a 9-package ERL_LIBS tree widens the gap, favouring the brief's conclusion rather than undermining it.
- Both checks answer only as well as the code path of the machine running bsc: `lib_dir(elixir)` is `{error,bad_name}` on stock `erl` until the Elixir ebins are added (my probe). The brief's own Option B objection ("only works where installed") applies equally to A, which the brief does not say.
- Not circular: the "actual app" column is from code:which paths, independent of the guess.

## Own probes (ERL_LIBS=p/lib with foo-1.0 [.app lists foo_a, foo_gone; only foo_a.beam] and bar-1.0; Elixir module Solo compiled to a bare dir passed with -pa)
```
lib_dir(foo)                         ".../lib/foo-1.0"          app present
which(foo_a)                         ".../foo-1.0/ebin/foo_a.beam"
which(foo_gone)                      non_existing               <- A passes, call is undef (brief concedes in prose, not measured)
which('Elixir.Solo') (-pa)           ".../pa_only/Elixir.Solo.beam"  module present, runs
lib_dir(solo) / lib_dir('Elixir.Solo')  {error,bad_name}        <- FALSE NEGATIVE: A rejects a working program
lib_dir(pa_only)                     ".../pa_only"              <- bare -pa dir answers by DIRECTORY NAME: false positive possible
lib_dir(elixir), Elixir ebin not on path  {error,bad_name}; with ebins added "/usr/lib/elixir/lib/elixir"
```
Consequence: A is sound only for apps laid out as `<name>[-vsn]/ebin` (ERL_LIBS / rebar _build), which is ticket 51's layout; it errs on -pa-style paths and on a bare dir named like the app. State that limit; this does not falsify A for the 51 workflow.
