## 3. Guard false-refusal + extra probe -- PASS (brief's claim holds), with one finding the brief omits
Guard claim reproduced (base: `Sign(n) when n < -1` / `n >= -1` refused; same with 1 accepted).
Extra probe: artifacts/verification/57-extra.sh (9 rows incl. negative controls). Results (fails = rows differing from the correct outcome):
- base 7 fails: GtPair (`n > -1` / `n <= -1`), OverlapLeft (`-1 <= n` / `n < -1`), LeftLit (`-5 <= value`), LeftBoth, BoundIn, NegUpperIn, RefinedExh all refused wrongly.
- v57a 0 fails.
- v57b 2 fails: BoundIn and NegUpperIn. Refinement `value >= -5` now reads, but calling `Id(-5)` is still refused.
- Controls hold in every variant: GapGuard (`n < -1` / `n > -1`, -1 uncovered) stays refused with witness `S(-1)`; BoundOut (`Id(-6)`) and NegUpperOut (`Id(0)`) refused.
Cause of the v57b failures: a call-site `-5` is parsed as `e_neg` and typed as a widened range, not the literal. Observed with `type T = int where value >= 100`, `Id(-5)`: base and v57b say the argument type is `int <= 99`; v57a says `-5`. (`Id(5)` gives `5` in all.) So under B alone a refinement with a negative bound cannot be handed a negative literal argument. This weakens the brief's "B accepts every row" as a usability claim, and strengthens A; the brief's A/B comparison does not mention it. (Pre-existing e_neg typing imprecision, outside ticket 57's stated scope, but it decides whether the fix works end to end.)

None found. Evidence: (a) the probe's expected column states the desired outcome, applied identically to all three variants, and base fails it, so nothing was tuned to pass; (b) patches contain no probe-specific literals and do not touch opaque_refinement/empty_refinement; (c) my independent controls (a genuinely inexhaustive guard pair, out-of-range arguments, wrong-boundary values) stay refused under both patches, so the folds do not simply accept more; (d) base refusals are for the stated reason, not an incidental one.
