## Corrections

1. **Typing change from patch A that the brief omits.** `type_of({e_neg,..})` returns `int` (`bs_check.erl:2889-2899`). `type_of({e_int,N})` returns the singleton range (`:2882`). So after v57a, `-5` has the literal type `-5`; before, and under v57b, it is `int`. My probe E (below) differs between variants:
   - v57a accepts `Neg Mk(int n) -> -5` for `Neg = int where value <= -1`.
   - v57b refuses it with "not covered ... int >= 0".

   This is arguably an improvement, but it is a semantic change to the type of every negative literal. The brief's counterargument says only that the AST changes and that the emitted Erlang "should" be the same. That is incomplete. The brief should also say that A makes `-5` a literal-typed value. It may widen or narrow what the checker accepts across the corpus; I did not test that.
2. The brief's A bullet "(-5) accepted" is right. `value >= - 5` (with a space) is also accepted by both patches; see probe B.
3. B's line count is 18 added, not 21 (minor).

## Circularity findings

- Neither patch touches the probe harness. `probe57.sh` decides ACCEPTED or REFUSED purely by whether bsc prints any first line of output. `run-all.sh` rewrites the diagnostic text to "REFUSED" with `sed`. That only relabels the real `opaque_refinement` message and cannot turn an error into a pass.
- The probe has a weakness. ACCEPTED means no output at all, so any first line that is not the opaque message would be shown as `error: ...`. That is the correct direction, so it cannot manufacture an accept.
- The guard probe prints nothing on success, then "exit-ok". A silent compile and a probe that never ran would look alike. Baseline output, which has the error, shows the probe does run.
- I added a control that the brief lacks: positive guards `n >= 5` / `n < 5` compile at baseline. So the baseline failure is caused by the negative literal, not by the guard shape.
- v57b is not circular. The residual `Sign(-6)` comes from the real checker, since interval arithmetic is untouched. The runtime -101 crash comes from the emitter's boundary guard, which both patches leave unchanged. The runtime check does confirm that the bound is enforced, not merely accepted.
- The baseline row of `57-runtime-and-residual` shows only the compile error for D, so the runtime claim is about the patched compilers only. The brief words it that way.
