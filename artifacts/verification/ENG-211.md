## Circularity findings

1. **Benchmarks like with like (no circularity found).** The four sources in `aoc/bench` (`bench_erl.erl`, `bench_ex.ex`, `gleam/src`, `Day01/bench_bs.bs`) use the same algorithm: same `Wrap` double rem, same `Hit`, same unguarded recursive `Spin` clause, same `Clicks` shape. Gleam's `Hit` and `Spin` use `case` and Erlang uses multiple clauses, but the emitted `Spin` for Erlang and bsc is identical (C2) and Gleam's `Spin` with `inline` stripped equals Erlang within 0.4% (C3), which is the control for the guard-style failure the ticket warns about. The answer is asserted in `bench.erl` and in every probe script (`assert a=="6770"` in `p39_emitter.sh:7`, `p39_ceiling.sh:6`; printed in `p39_inline.sh`). Residual: `Sign`/`Size` use different guard forms across the four sources, outside the hot loop.
2. **Timing instrument.** `39/time_one.escript:3-7` reads and parses the input and loads the module before the timed region, calls `M:F(Ds)` once untimed, then times only `timer:tc(M,F,[Ds])`, 25 times; one fresh VM per sample. Min-of-25 then median over rounds is a reasonable statistic; the README's `p39_four.sh` instead runs all four in one VM in a fixed order (Gleam third), which would not detect an order effect, but `p39_inline.sh` (one VM per sample, interleaved) reproduces the same ratios, so no order effect.
3. **`add_inline` does not give bsc the same inlining as Erlang (`39/make_variant.escript:12-13`, `39/p39_inline.sh`).** The script changes only the compile attribute (`insert_after_module`, `Opts -- [inline]`), and `compile:forms(Forms2, [])` uses no optimisation options different from Gleam's shipped beam (`{options,[debug_info]}` via `beam_lib`), so that part is clean. But the same attribute has a different effect on the two sources. Dumping `Spin/4` from `Day01.abstr` + `inline` (`addinl.escript`): 32 lines, **2 calls** -- `Hit` is inlined, `Wrap` is **not** (a `{call,1,..}` remains); Erlang +inline `Spin/4` is 27 lines with `Wrap` and `Hit` both inlined and the only call being the self tail call; Gleam's `Spin` is the same 27 lines. bsc's `Wrap` AST is `case erlang:rem(..) of ..` (remote-call form, `Day01.abstr:23-27`), not the Erlang `rem` operator, so the inliner's size/shape decision differs even though the optimised bodies are identical. Consequence: bs_inline (-9.0%) and erl_inline (-12.1%) are not the same single factor, the 3-point gap is the missing `Wrap` inlining, and C3's "one factor changed per variant" is not literally true for the bs row. The ticket-level conclusion (inlining accounts for the Gleam lead) still holds because the Erlang and Gleam rows are clean.
4. **I2 inlines the recursive `Spin` into itself (`patches/v39-I2.patch`).** The patch inlines every private function, including recursive ones: `Day01.abstr:4-10` lists `Spin/4` and `Clicks/3` in `{inline,[..]}`. `I2` `Spin` is 46 lines with two copies of the `rem; +; rem` sequence, i.e. the loop is unrolled once. That is probably why I2 (11.30) is 1.5% ahead of Erlang+inline (11.48) and Gleam (11.4-11.5). This is within noise, but the briefing's "faster than Gleam" is attributable to unrolling plus helper inlining, not to a better inline policy. I1's `{inline}` (module-wide, no list) did not do this. The patches do what they say and nothing else (`v39-I1`: one added attribute; `v39-I2`: one added attribute listing `not is_public(F)` functions).
5. **`p39_cost.sh:13-16` mis-reports its own failures.** `mods` is `compiler/examples/*/` (23 directories) plus `aoc/2025/Day01` and `aoc/bench/Day01`; all runs pass `--src-root compiler/examples`. The two aoc paths are refused ("--src-root does not contain ..."), and `compiler/examples/exemplars` is "a namespace, not a module". So the 3 failures are a probe defect, identical in all builds by construction, and the byte totals exclude the benchmarked module. The deltas (+244, +380 bytes) are still real for the 22 compiled modules but are not "25 example modules".
6. **Oracle (`39/oracle/oracle.erl`).** Not smuggling in information outside any compiler's reach: the facts it uses (pos in 0..99, step in -1..1, so `pos+step` in -1..100) are exactly the `{tr,..}` types the BEAM's own compiler prints for `Spin` (`{t_integer,{0,99}}`, `{t_integer,{-1,1}}`, and `{-1,100}` as the input of the first `rem`). What it applies is a transform no existing pass performs (rem strength reduction to a two-way fix-up from a range). The file's header says so. Two cautions: (a) it uses nothing from B# types (`Wrap` is declared `int Wrap(int n)` in B#), so the 4.3x is a bound on a range-driven `rem` pass in the BEAM compiler, not on anything B#'s type system supplies; (b) the oracle is correct only on the domain where the invariant holds, which the real program guarantees by construction (checked over 300 random inputs). 4.3x is believable: the loop runs 2 rem per click (about 1.35 M rem in 673 k clicks); the 8.8 ms difference is about 6.5 ns per `rem`, about 14 cycles at 2.1 GHz, a plausible integer-division cost.
7. **Ticket's original gap not tested.** Nothing here can speak to the Apple Silicon 20%; on x86 the "gap" is 0-1.5% and the 11% Gleam lead is wholly the `inline` attribute. No probe checks that `inline` explains anything on the architecture where the ticket's number came from.

## Unsupported or overstated

- "beam-sharp 20% behind" is not reproduced (1% here). Whether Gleam's `inline` explains the ticket's Apple Silicon numbers is untested; on the ticket's numbers Gleam led Erlang by only 3%, while here the inline gain is 12%, so the same mechanism is not obviously the cause there.
- C5's "25 example modules" and "the same 3 modules fail to compile": 22 modules compiled; the 3 are 2 un-compilable invocations and 1 namespace directory (finding 5).
- "I2 faster than Gleam" (about 1-2%) is inside the noise band, and partly from unrolling a recursive function (finding 4).
- C3's bs row: the claim that only the attribute changed is true of the file, but the compiler's inlining outcome differs from Erlang's (Wrap stays a call); bs_inline is 4% slower than erl_inline, unreported.
- C3's Erlang +inline figure measured -12.1% (claim ~-10%); C4's I2 measured -13.8% (claim -12.2%). Both are 2 points off, in the direction of a larger effect.
- The oracle bound says nothing about what B# types could add (finding 6a).
- Wall-time "unchanged" (C5) is measured over 25 VM boots dominated by startup and type checking; it cannot detect a small change in erlc time.
- I did not run with Elm or Hex-dependent parts (unrelated to ticket 39), and the Gleam project was built without `gleam_stdlib` as the build script states.
