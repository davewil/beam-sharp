## Circularity and holes

- **Escape probe (p59d) is not rigged against v59a/b, but it only exercises two escape shapes**: a private name returned directly as a fn value. Those are exactly what `fnames` records, so v59c passing it is close to tautological. The brief admits only local `fun Name/Arity` was checked. My probes below widen this.
- v59c reads `fnames` via `maps:values` filtered to `{_,_}` pairs (`bs_emit.erl:56` puts `fnames` in Ctx; the notes come from `bs_check.erl:126,3725` `fname_type`, the only producer of `fname` notes, and `bs_emit.erl:1081-1088` is the only consumer that makes a `fun`). Every value use of a bare name goes through `e_fname` (`bs_parser.yrl:712-713`), so tuple, list, record field, argument, lambda body and explicit `Name/Arity` all hit it. The `{q,Mod,...}` imported form is excluded by the pattern, correctly, since a private name cannot be written qualified (see probe H).
- Notes are keyed `{Path, Pos}`. In the shim build `Pos` is `{Line,1}`, so two bare names on one line would collide; this is a shim artifact (and would hit baseline equally), so I put each reference on its own line. Not a finding against the brief but note that the shim could mask or create same-line problems.
- Weak regression evidence for v59c: baseline eunit already fails 583 tests, including five `function_value_tests` (the escape feature's own tests) and `visibility_tests` private-call tests. "Failing set identical" says nothing about those. v59c's regression status is unproven for exactly the area it touches.
- Not probed by anyone: a module of several files (fnames merged across files via `maps:values`; looks fine by code), hot reload, `apply/3` with an atom name, behaviour callback tables, `Show/1` escaping in dead or pruned code (conservative: would just over-guard).

Guard presence in emitted heads (from `dump.escript`): v59c leaves `Show4` (only called via `o |> Show4()`), `NoEscape` and the non-escaping `Show6/1` **unguarded** and guards every escaping one including both `Cls` clauses; so v59c's arity-keyed lookup is precise, and it neither misses nor over-reaches on these cases. v59a unguards all; v59b guards all. Sizes of G.beam: bsc 3528, v59a 3308, v59b 3620, v59c 3556.

Probe H (another module naming a private fn): `G.Show1(t)` is refused by every variant ("calls G.Show1/1, which G declares `private`"); `G.Show1` and `G.Show1/1` as a qualified *value* do not parse. So a private function can only escape from its own module, and the cross-module escape cannot be constructed. I tried to falsify v59c and found no escape path it misses among those expressible in the language today.
