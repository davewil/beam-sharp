# Verification of brief 60 (which modules may name this one)

Toolchain: OTP 28, Gleam 1.19.1, Elixir 1.20.4, own PROBE_HOME=/tmp/verif60. Variants built with mkvariant.sh (base, v60a).
Extra probe: artifacts/verification/60-extra.sh [variant].

## 1. p60_internal.sh base vs v60a: PASS (with one caveat on the control)
v60a: Shop/Orders accepted; Shop/Billing accepted; Other refused (`Sneak calls Shop.Orders.RecomputeTotal/1, which Shop.Orders declares `private``).
Exports of Shop.Orders: [{'Place',1},{'RecomputeTotal',1},{bs@type_atoms,0},{module_info,0},{module_info,1}]. Plain Erlang call -> 300. Matches the brief.
base: Shop/Orders refused with `orders.bs:4:10: error: syntax error before: int` (the `internal` line). Confirmed as the control.
Caveat: under base, Billing and Other are also refused, but for `using Shop names no module and no namespace`, a knock-on of Orders failing. They are not independent controls. The syntax error on Orders is the real control. The erl eval step then crashes under base because nothing was built (expected, writes erl_crash.dump; I deleted it).

## 2. Is the enforcement real, or is Other refused for an unrelated reason: PASS (real)
Read the patch and bs_check. Hidden = every {Module, Key} in World whose recorded `internal` scope differs from scope(Self) (first name segment). Hidden keys are removed from `qual` and from the callee's exports in add_module_import, and added to `privates`, which is why the message says "private" (see 3).
Extra probe, each case compiled in its own world (Shop.Orders as authored plus one caller, same `using` line and body shape as Billing). v60a:
- Shop.Billing (author's text): accepted
- Zed.Billing, identical except module name: REFUSED (4:21, RecomputeTotal/1, Shop.Orders)
- Zed.Billing calling the PUBLIC Orders.Place with the same `using Shop`: accepted. So `using Shop` is not what fails Other; the refusal is the scope check.
- Zed.Billing with `using Shop.Orders` and unqualified RecomputeTotal(q): refused. Shop.Billing, same form: accepted. (Unqualified path is enforced too.)
- Shop.Deep.Inner (3 segments, inside Shop): accepted
- Zed.Deep.Inner (3 segments, outside Shop): refused
- ShopX.Billing (prefix lookalike): refused. The prefix match is on whole segments, not a string prefix.
Under base all of these fail at `using`, because Orders does not parse. That is uninformative, not a counter-example.
Test-design note: my first attempt put all callers in one world. `using Shop` then imports every module under Shop and my Deep.Inner and Billing formed an import cycle. This is a property of namespace `using`, not of the patch. The shipped script isolates each case.
Open observation: scope is the callee's FIRST segment, so a three-segment module cannot restrict to its own parent (Shop.Deep.X can be called from Shop.Anything). This matches the brief's own "arbitrary for trees deeper than two levels".

## 4. Corpus 22 modules, 82 guards: PASS
corpus.escript over compiler/examples, base and v60a: both `TOTAL 53444 bytes, 82 guards across 22 modules`. Per-module rows identical in bytes and guards, so there was no path-length noise in my run. The 23rd directory, `exemplars`, is refused identically in both (not a module directory). `grep -w internal` over *.bs finds only the probe's own Orders file.
Caveat: it shows no regression on programs that never use `internal`. It says nothing about `internal` programs, and guard count is a coarse proxy.

## 5. p60_neighbours.sh: PASS (reproduced) and the "Gleam does not enforce" claim survives
Reproduced: Gleam lib builds exit 0; app (path dependency, imports lib/internal/helper) builds exit 0 with no warning in stdout or stderr (stdout empty; stderr only Resolving/Added/Compiling/Compiled); app:main() -> 42; same-package sibling also builds. Elixir @moduledoc false caller: 42, no warning.
Attempts to find enforcement, all negative on 1.19.1:
- `gleam build`, `gleam check`, `gleam run`: full stderr contains no mention of internal.
- Added a public function returning an internal-module type (`leak() -> helper.Secret`): lib still builds with no warning.
- `@internal` attribute on a pub fn in an ordinary module, called from another package: builds, runs, returns 7.
- DIFFERENCE the brief did not test (it said "may drive docs"): `gleam docs build` in lib omits lib/internal/helper (`find build/dev/docs -name '*helper*'` is empty) and omits `hidden`, and `gleam export package-interface` lists only ['lib'] and not helper. So Gleam treats internal modules differently for docs and the interface, just not at compile time. The brief's sentence "no neighbour enforces a who rule at compile time" holds. The implication that its users "are not asking for a hard rule" is the author's inference and is not measured. Docs/interface hiding is a real use of the marker. LSP completion was not tested by me either.
- Path dependency only. I did not test a Hex-fetched dependency (network). The behaviour could differ there; I found no evidence it does.

## Circularity
Not found. Evidence:
- The control (base) fails at the `internal` token, so the accept is attributable to the patch, and Other's refusal flips with only the module name (Zed.Billing vs Shop.Billing) and not with the call target (public Place accepted). The refusal is the scope check, not `using`.
- The patch does not special-case probe names: scope is derived from the module name. ShopX and Zed.* are refused, Shop.* at depth 2 and 3 accepted, none of which the author's probe contains.
- The run-time claim (300 from plain Erlang) is not manufactured: it is what the emitter's is_public change does, and the patch states so openly.
- The corpus run is a regression check only, and the brief says so. Weak points that are not circularity: the base control for Billing/Other is a knock-on failure (see 1); the "wrong diagnostic" is a shortcut in the prototype, not hidden. The neighbour probe was built by the author but its result (builds, 42) is a plain observation I reproduced with an extra variant (@internal, leaked type).
