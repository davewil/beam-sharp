## 2. Circularity review (file:line)

C1. probes/60/b/run.sh and d/run.sh use the prototype's own keyword `internal` in `index.bs`. The unpatched
compiler would reject that as a syntax error, so "unpatched accepts, patched refuses" cannot be shown by running
b unchanged. I ran the equivalent unpatched case myself (Internal-segment tree, no keyword, base copy of the
compiler): the base compiler accepts every caller (Billing-like, Rogue-like, Tests, OrdersExtras, Shop.Tests.Orders);
the patched one refuses exactly the outsiders. So the claim holds, but the brief should say the baseline is
"same sources without `internal`" and probe k/a is the real before/after. Minor.

C2 (substantive, probes/60/f/who.erl `main/0`, rogue.erl:2). "ROGUE tail call is admitted" is partly an artefact of
the harness: `rogue:tail/1` is called from `who:main/0`, and `who` is the one module the check admits. After the tail
call the callee sees rogue's CALLER, so the admit is the caller of rogue being legitimate. I re-derived with my
own modules (cal/legit/rogue2, in scratchpad v/f): 
 - legit body call -> admitted; rogue non-tail -> refused;
 - rogue tail-calling, called from an unrelated module (`erl -eval`) -> refused (by accident);
 - **legit module tail-calling the checked function -> REFUSED** (false negative for the legitimate case);
 - legit -> rogue (tail) -> checked: ADMITTED. 
 - `Y = f(), Y` is compiled as a tail call: refused when the surrounding caller is not `legit`, admitted when it is.
So "runtime caller identity from stacktrace is unsound" is TRUE, and worse than the brief says (it refuses legitimate
tail callers too), but the brief's sentence "a rogue module tail-calling the checked function is admitted" is
overbroad: it is admitted only if rogue's caller is allowed. Reword. Cost: my own measurement 8.3 ns plain vs 462 ns
(55x); the probe's 37-43x is the same order. "~40-55x" is safer than "~43x".

C3 (substantive, probes/60/d/micro.sh header says "VERBATIM COPY of visible_to/3 + parent/1 + in_subtree/2"). It is
not a copy of the shipped patch: the patch's `visible_to/3` also reads `within`, calls `segment_root/1`
(string:split + splitwith per call), and has a 4-tuple case. I extracted the real functions from the patched
bs_check.erl and timed them (1e6 calls x 9, median): unrestricted **~304 ns/call, not ~10 ns**; restricted **~723 ns,
not ~0.4 us**. x285 edges = 0.09-0.2 ms, so the conclusion "sub-millisecond, negligible" stands, but the brief's
"~10 ns" figure (Option A, probe index row d, recommendation (ii)) is wrong by 30x for the final patch. Correct it or
drop the unrestricted number. (If segment_root were only computed when needed the 10 ns would hold.)

C4 (timing methodology, d/run.sh:24-30). The baseline "repo bsc" is compiler/_build/default/bin/bsc (built 23:05,
1,013,544 B), not an unpatched copy built by the same route as the patched one. My unpatched copy built the same
way is 1,016,121 B; the patched is 1,035,009 B (+1.9%). Order is A,B,C,A,B,C blocks (not interleaved), 9 runs, one
machine state; the brief's honest sentence "I cannot attribute the gap" is correct, but the methodology could not
have isolated it. I re-measured with an unpatched copy, 25 runs, orders rotated per iteration, same 60-module/285-edge
corpus (min/median/max ms): base 623/821/1171, patched-plain 656/833/1236, patched-20-internal 621/784/1035.
Differences are within noise (max-min spread 500+ ms). So the "15-120 ms slower" gap in the brief is not
reproduced; I read it as noise, not table growth. Patched-with-nothing vs patched-with-20 does isolate
"restricted modules cost nothing measurable", not "the patch costs nothing". Suggested wording: no measurable
difference once interleaved against an unpatched copy.

C5. Probe a does not run the thing the gating question names. The gating question speaks of module
`Shop.Orders.Recompute`; probe a's rogue names function `RecomputeTotal` in module `Shop.Orders` (a/src has no
Recompute module directory). It shows the premise (a public function is nameable from anywhere), and the
module-level case is shown by the unpatched base run above and by k. Not a flaw in the finding, but the sentence
"(probe a)" after the module-level question should say "same shape, function-level".

## 4. Falsification of recommendation A (patched copy; scratchpad v/fz, v/fz2, v/proto)

Project with module Shop.Orders.Internal.Calc (Internal segment), Shop.Orders, Shop.Orders.Tests, Shop.OrdersExtras,
Shop.Tests.Orders, Tools.*:
 - Prefix-string vs segment: `Shop.OrdersExtras` (shares the string prefix `Shop.Orders`) REFUSED. Correct (the predicate
   tests `S =:= P orelse prefix(P ++ ".", S)`, segment-wise).
 - `Shop.Orders.Tests` ADMITTED (as the brief says, by design); `Shop.Tests.Orders` (tests in a separate subtree) REFUSED,
   which is a realistic refusal that would force tests next to the code or a widening: the brief's counterargument covers it.
 - Namespace import `using Shop.Orders.Internal` from Tools: REFUSED (all children hidden).
 - Partly visible namespace (Vault: internal Vault.Hidden + public Vault.Pub), `using Vault`: Pub.Go compiles; `Hidden.Open`
   and `Vault.Hidden.Open` are refused with "called but never imported ... add `using Vault.Hidden`" (the hint is
   misleading: adding that line then yields "may not name"). Brief listed this as untested; now tested; only a diagnostic wart.
 - Qualified call after `using Shop.Orders` to `Shop.Orders.Internal.Calc.Sum`: refused, "never imported".
 - Top-level `Internal.Util` module (segment first): `segment_root` returns none, so it is UNRESTRICTED (Tools.Top
   compiles). Go would restrict to the root; edge case worth a line.
 - Escape hatches: `:erlang.apply(:'Shop.Orders.Internal.Calc', :'Sum', [xs,0])` compiles in a Tools module (runtime
   `undef` only because the callee beam was not loaded). A compile-time check cannot see dynamic apply; the brief's "compile-time or nothing"
   should add "and dynamic apply/foreign atoms bypass it". The foreign-declaration form `using :'Shop.Orders...' { int Sum(..) }` is a syntax
   error (foreign function names must be lident), so static foreign naming of PascalCase B# functions is not possible.
 - Transitive/re-export: the check gates only `using` edges, which is what the brief claims. A visible module can wrap a hidden one
   (intended) and its types flow by F44; I did not find a case where a hidden module becomes nameable without a `using` edge.
 No realistic wrong-admit besides the by-design Tests case and the top-level-Internal edge; no wrong-refuse besides Shop.Tests.Orders.
