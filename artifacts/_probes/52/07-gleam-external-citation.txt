APPLICATION, or only the module? Read from real source, /tmp/lang-src/gleam.

    fn parse_external_attribute(...) -> Result<u32, ParseError> {
        let (_, target, _) = self.expect_name(IncorrectNamePosition::Target)?;
        let target = match target.as_str() {
            "erlang" => Target::Erlang,
            "javascript" => Target::JavaScript,
            _ => return parse_error(ParseErrorType::UnknownTarget, ...),
        };
        let _ = self.expect_one(&Token::Comma)?;
        let (_, module, _) = self.expect_string()?;
        let _ = self.expect_one(&Token::Comma)?;
        let (_, function, _) = self.expect_string()?;

        attributes.set_external_for(target, Some((module, function, SrcSpan {..})));
        Ok(end)
    }

   Exactly three arguments are parsed: target ("erlang"/"javascript"), a

3. No cross-check exists either: grepped compiler-core/src for any
   correlation between an @external module name and a declared gleam.toml
   dependency (patterns tried: "external.*application",
   "application.*external", "check.*external.*module") -- zero hits.
   `@external(erlang, "Elixir.Req", "new")` and `@external(erlang, "lists",

VERDICT: Gleam's closest analog to this ticket's candidate syntax never
names the Erlang application, only the module. This is not an omission this
ticket's design would be filling a documented gap in -- Gleam simply never
tried to solve dependency provenance at the @external declaration; its
provenance mechanism (such as it is) lives entirely in gleam.toml's
dependency list, which is the "separate manifest" shape ticket 51 already
measured and rejected for beam-sharp. So Gleam is prior art for the
ATTRIBUTE SYNTAX (ticket 32 already established this) and is NOT prior art
for solving THIS ticket's actual question -- it has the identical gap.
