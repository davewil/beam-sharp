## Circularity findings

None found. Details:

- Both variants really go through the visibility predicate. The refusal is not caused by fixture layout or a missing module. Same-layout controls (allowed importers in deeper positions, two-level Internal, open modules) compile, and refused importers fail only where the predicate says so.
- HEAD accepts every refused case, so the refusals are not baseline behaviour.
- The reused `unknown_module` text is a stated limitation in the brief. It means the "refused" verdict cannot by itself prove the reason, but the controls establish the reason.
- Mild non-independence: the R2 fixture gives the callee `friend Shop`, which is exactly the subtree R1 computes. The two variants agreeing is therefore expected, not independent confirmation. R2 on its own controls (friend Billing and Reports; Pricing refused) shows it is not R1 in disguise.
- The brief's claim that both are valid "same verdicts" is fair only for that fixture.

## Unsupported or wrong claims in the brief

1. **Type names leak through qualified spelling (a third path the two-site analysis misses).** Lib.Internal.Sec declares `record Secret`. Other.B has only `using Lib.User` and writes `public int Go(Lib.Internal.Sec.Secret s)`. It compiles at HEAD and under R1. R1 only gates `using`, and F44 type names cross `using` transitively. The brief says a qualified spelling is "already gated by `using`"; that holds for calls (Other3, and Shop.Billing then a qualified call: refused) but not for qualified type names. Values of the hidden module's type also flow freely (Other.A uses Make/Id). Not tested for R2, which uses the same two sites, so presumably the same leak.
2. **Lenient mode behaviour differs and is unmentioned.** `import_env` is called with `lenient` from exports_of, polys_of, types_of and implements_of. In HEAD, `bsc --api` on Other/Deep succeeds (`int O(int)`). Under R1 the same command now fails with the unknown_module error, because the hidden-module branch raises in both modes. In the namespace branch a fully filtered import silently returns Acc in lenient mode but errors in strict. The brief's "two sites" never mentions Mode.
3. **`Internal` already means something in ticket 41.** wayfinder/issues/41 (around line 490) lists `Internal/` as "inside a module: SUB-MODULE, source-only (ticket 13)". The brief says `Internal` "appears in no example" and has no migration note about this prior meaning. Under R1 the word would carry two meanings. Whether they collide mechanically was not tested (sub-modules are not separately nameable).
4. **R2 world-entry sites.** bsc.erl line 237 gets `friends`, but the types_world entry at bsc.erl line 294 does not, so on the `--api`/type-world path every module is open. The brief says R2 edits "a `friends` field on the world entry" as if there were one site.
5. **R1 top-level `Internal` is open.** `Parent =:= ""` makes a module named `Internal.X` visible to everyone. Not in the brief.
6. Go internal/ is stated from memory, which the brief admits.
7. "Both variants give the same verdicts" holds only on these fixtures (see circularity note).
