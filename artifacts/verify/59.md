## Item 2: do the variants change only what they claim?

vN adds `orelse not Public` to the existing `constrains_kind(Pat)` test in the tag arm. It therefore skips the tag test only on private functions whose param is a closed record. The `none when Public` int/float arm is untouched.

vW deletes the `when Public` on the `none` arm and removes the `none -> {Pat, []}` fallback. Records still take the first arm. The `_Public` rename only silences the unused-variable error.

I dumped the abstract code of every exported function (line numbers stripped) for P59, B59, N59 and the absdump module under HEAD, vN and vW and diffed them. Exported functions are byte-identical in every case. The only differences are the Code-chunk size line and, for vW, nothing else. So the 666 and 1000 outcomes cannot come from the patch breaking an exported check.

## Item 3: the case where the caller cannot prove the argument (new probe, not in the brief)

Source: /tmp/claude-0/verify59/u59/U59/u59.bs. `SumList(list<Byte>, acc)` calls a private `Bump(Byte b)` for each list element. `One(list<Byte>)` calls `Bump(head)`.

| | HEAD | vW |
|---|---|---|
| Code chunk | 183 B | 201 B (+18) |
| file size | 1256 B | 1360 B (+104) |
| SumList ns per element, 3 runs | 7.49, 10.12, 7.55 | 7.14, 7.46, 8.07 |
| `SumList([7,999],0)` | 1008 (silent) | `function_clause` in Bump |

- **Code size:** the brief's claim that widening costs 0 B does not generalise. Whenever the caller cannot prove the range, the guard stays in the Code chunk. It cost +18 B here and also in nested_int.sh (156→174 B).
- **Per-call time:** I measured no consistent slowdown. The ranges overlap, and HEAD's 10.12 is an outlier on a noisy box.
- **Mechanism:** the brief says `beam_ssa_type` removes the guard. I confirmed only the Code-chunk outcome, not which compiler pass does it.
- **Exported list guard:** the exported `list<Byte>` parameter is not checked element-wise. Forged 999 reached `Bump` under HEAD, which fits the brief's "shallow guards" point.

## Circularity findings

None found.

- Both variants are minimal and are not rigged. Exported code is identical.
- The forged inputs are built to pass the outer guard. That shows the hole exists. It says nothing about how likely it is, and the brief does not claim otherwise.
- The cost measurements use literal or provable arguments (`PrivInt(7)`, `Via(Byte)` into `PrivInt`). That is a favourable setup for "widening is free". The brief states the corpus caveat itself, but its P3 table then reads "measured zero". The unprovable case above shows a small non-zero cost.

## Unsupported or wrong claims in the brief

1. The "zero cost of widening" row, and the sentence "widening it measured zero", hold only for provable callers. For unprovable callers the Code chunk grows (+18 B in two programs). The brief mentions the missing case but never built it. Option 1's "strongest counterargument" is therefore partly answerable: bytes yes, measurable time no.
2. The brief says `Fib` timing is 14.3-15.1 ms. I got 15.4-16.3 ms, probably a machine difference. Fib shows no ordering, so the conclusion is unaffected.
3. The brief cites `boundary_guards/4` as the ticket's mistake. The ticket text uses both `/5` (measurement section) and `/4` (quoted from ticket 46). Trivial.
4. The attribution of the +36 B file-size difference is "untraced". Still untraced here, but the same pattern appears with +18 B code (+104 B file) in U59. This is probably debug and line metadata.
5. run.sh still prints a stale "P3 ... variant-private-unguarded.diff" echo for a file that does not exist.
6. The brief's reading that private-record tag-test cost is "roughly 0.4-0.7 ns per call" reproduces, with 0.6-0.9 ns in my 3 runs.

## Not verified

- The ticket-18 and F24 quotations in the brief, and that 18 §4 says what the brief says it does. I read only the opening of ticket 59.
