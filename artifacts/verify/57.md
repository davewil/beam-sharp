## Variant diffs, read adversarially

**A** adds one `negate/2` clause: `{e_int,IL,I} -> {e_int,IL,-I}`. It disables no check. Three effects follow directly: the refinement reader sees `e_int` and `comparison/1` accepts it. The guard path reads through the same function, so a guard `n <= -1` credits coverage. `type_of({e_int,..})` gives the singleton range, so `Pass(-3)` is accepted. The results are consistent with that.

**B** rewrites only `comparison/1`, with clauses that route `e_neg` and `e_int` operands through `const_int/1`. It disables nothing, and positive-literal cases still reach `int_cmp`. One behavioural change beyond the claim: an `e_neg` of a non-constant operand now returns `unknown` at that clause instead of falling through to the later `comparison/1` clauses. Those clauses match only atoms or other shapes, so there is no observable difference in these probes.

**B2** is B plus a single line in `type_of`: `type_of({e_neg,_,{e_int,_,N}}) -> range(-N,-N)`. I confirmed it is exactly B plus that line.

- B refuses `Pass(-3)`. The residual shown is `int <= -6 | int >= 6`, so the argument is typed `int`.
- B2 accepts `Pass(-3)`. The only difference between the two builds is the `type_of` clause, which sits in `bs_check.erl` directly before the general `e_neg` clause that returns `bs_types:int()`.
- This is a controlled A/B on one added clause. The refusal in B is caused by `type_of` returning `int` for the e_neg node (the source at `bs_check.erl:2891-2899` returns `bs_types:int()`), and I found no other route to it.

## Own falsification probes

All built against HEAD and A, in `/tmp/claude-0/verify57/own`.

1. **Edge forms.** Module with `-0`, `-(-5)`, `x - -5`, `- 5 * 2`, `-x * 3`, `-0.0`, a `var n = -7` binding, `-9223372036854775808`, `-4 - -4 - 1`, and clauses `Mat(-1)`, `Mat(<= -2)`. Under HEAD and A the compiled module's results are identical: `[0,5,15,-10,-6,-0.0,-6,-9223372036854775808,[99,10,0,4],-1]`. `-0.0` stays negative zero, as it already did at HEAD. The abstract code differs only by `{op,'-',{integer,N}}` becoming `{integer,-N}` (and `-(-5)` becoming `5`).
2. **A guard with a negative literal beside the pattern form** (`Mat(n) when n <= -2`) is refused at HEAD ("Mat is not exhaustive, residual `Mat(<= -2)`") and accepted under A.
3. **All 23 shipped examples under `compiler/examples`** (the `exemplars` namespace dir has no modules of its own) compile under HEAD and A with byte-identical `.abstr` files (23 same, 0 differ). Many of them contain negative literals, but none of them changes.
4. **Singleton negative refinements.** `value >= -3 and value <= -3` is refused at HEAD ("not a predicate") and under A gives "bad range type" (the P5 defect). Fixing negative literals does not fix singleton ranges.

No probe broke option A.

## Circularity findings

None found that manufactures the headline result. Specific checks:

- **B vs B2 is not rigged.** B2 is B plus one `type_of` line, so the `Pass(-3)` flip is an isolated change. The variants do not disable any check; the observed outcomes follow from the patched code.
- **A does not disable the guard or the type check.** `Pass(-d)` is still refused under every variant, and `value >= 2 + 3` still hits the diagnostic.
- **P3 is the weakest probe.** The 8-vs-4 words comparison is `flat_size` of two terms written by hand in the script, not of a parse by variant A. It is trivially true and does not test that A produces the 4-word shape. The brief should say so. It does not support any decision on its own.
- **Gleam row.** The probe examines emitted abstract code, so it shows what Gleam hands to the Erlang compiler, not what Gleam's parser keeps. The brief's column header ("what the parser keeps for -5") overstates it. This weakens the 2-1 neighbour split; the brief's own text partly admits this ("output shape").
- **Eunit.** The brief's 1446/1448 result for A is reported with the two failures put down to layout. I did not re-run it (see below), so that is the brief's word only.

## Unsupported or wrong claims in the brief

1. "`value >= -5` (and the other seven negative-literal rows): accepted" under A/B/B2 is wrong for `value == -3`: the compile fails with `bad range type` (the P5 singleton defect). The brief mentions P5 only for the positive `value == 3` case. The brief should list `== -3` as "checker accepts, backend fails".
2. The Gleam row is described as parser behaviour; only emitted code was observed (above).
3. The 8-vs-4 AST words figure is not measured on any variant's parser (above).
4. "A grep for 'bad range type' in the repo finds nothing" is not re-verified here beyond an `-rn` of `compiler/src` that found no hits; I did not grep the whole repo.
5. "Eunit 1446 pass, 2 fail, layout failures": the cause is asserted, not shown (not re-run).
