An experimental language, explained through one small decision

A language that asks:
what did you miss?

Most programs describe what should happen. B# also asks whether you have described every case that could arrive.

B# — working name beam-sharp — brings C#-family notation to functional programming on the BEAM, the runtime used by Erlang and Elixir. It is an experimental language with a working reference compiler, not C# running on .NET. The project's premise

02 /

The rules are the program.

A type names the possibilities

A type describes a set of allowed values. Here, Reading names four possibilities. The vertical bar means “or”; :above is a named value, called an atom.

A clause handles one case

A clause is a rule: match this input, produce this answer. The function's signature declares what it accepts and returns. Its clauses must account for that declared input.

Respond(:above) -> :cool
Respond(:at) -> :hold
Respond(:below) -> :heat

public Action Respond(Reading reading)
“Respond accepts a Reading and returns an Action.” The return type comes first, in the C# tradition.

Respond(:above) -> :cool
“When the report is above target, answer cool.” Clauses are checked and matched in order.

The compiler supplies the missing head, not the action after the arrow. It knows which case is absent; it cannot know what your controller ought to do.

Familiar spelling, a different way of working

B# favours functions and explicit cases, with new values instead of changing a shared object. Pipes make a sequence of calls readable. Its |?> “valve” currently passes successful values onward and stops on an error tuple such as (:error, :bad_request). That is explicit error flow, not an exception disappearing. See the runnable pipeline example.

03 /

The missing case is a remainder.

A compiler checks and translates code before it runs. B#'s distinctive move is to treat coverage as subtraction: start with the allowed inputs, remove what each clause handles, and inspect what remains.

Allowed inputs − handled inputs = missing cases

That remainder is called the residual. An empty residual means exhaustive coverage. Because the remainder is itself a type, the compiler can often express it as the exact clause head you need. The idea extends beyond four labels to integer ranges and structured values. How exhaustiveness and ranges work.

Follow a program through the implementation
  1. 01 · ReadLex and parseTurn .bs text into tokens, then a syntax tree.
  2. 02 · SimplifyLowerExpress constructs such as the valve using simpler branching forms.
  3. 03 · CheckTypes and coverageThe checker uses the type algebra to reason about values and residuals.
  4. 04 · ProduceEmit and compileWrite Erlang Abstract Format (.abstr); OTP compiles it into .beam.

The final step uses OTP's compile:file with from_abstr, in the same Erlang VM. The resulting module runs on the BEAM. This reuses the platform's compiler and runtime rather than introducing a separate virtual machine. Compiler pipeline.

Ordinary type aliases describe shapes and erase: they do not wrap every value in a new runtime object. Records use native BEAM maps with a Kind tag. This keeps the language close to the platform, while making validation at foreign entry points important. Types and representations.

Where does changing state live?

BEAM processes handle messages and carry their own state. A counter can receive an “add” request and return its next state without sharing a mutable object with other processes. B# Counter example; Erlang's process model.

What happens when something fails?

OTP separates workers from supervisors that can restart them according to a policy. This supports recovery; it does not make crashes impossible or automatically restore lost state. OTP design principles.

04 /

The repository is also an experiment.

The language specification describes the rules. The reference compiler makes them executable. Small examples demonstrate current behaviour; larger exemplars test whether the pieces compose into useful applications. Tooling asks whether people can comfortably write those programs.

One unusual design decision is the clean-room handoff: give another implementer the specification, feature record and example corpus, but not the compiler source. Can they build a compatible implementation from the explanation alone? That tests the clarity of the language design as well as its code. What the handoff contains.

05 /

What works, and where the edges are.

A design decision is not the same as an implemented feature. This is the local repository snapshot, not a claim of production readiness.

Working nowExecutable foundations

Exhaustiveness checking, recursive types, pipes and the error valve are implemented. There are runnable examples, a command-line compiler, an interactive REPL, and editor syntax support.

More detail for programmers

The map<K,V> type is built, but the Map.Get lookup operation is not. List.Sum, List.Length and List.Reverse are built. Explicit deep validation through ValidateAs works for supported shapes; dictionary validation is explicitly refused. Structured diagnostics include columns. A native semantic language server is not built; syntax highlighting is a different capability.

Standard environment · Diagnostic columns and remaining editor needs

IncompleteImportant practical gaps

Lambdas, function types and generic function signatures are missing, limiting higher-order operations such as map and fold. Generic aliases already work. The five larger application exemplars still hit compiler blockers; their recorded first errors are not complete lists of everything they need. Function-value gap · Measured exemplar blockers.

Foreign callers can also bypass some declared restrictions. Exported integer guards check “is an integer”, but do not yet add all required range bounds. The settled rule is to add only bounds the clause has not already proved. Explicit validation is separate, not automatically applied. Current entry guards · Decided bound checks.

Decided, but pausedConsequences need review

The valve is intended to stop on :nothing as well as error tuples. F30 is not started, and readiness is deliberately paused for David's review: the change can widen old return types and stop passing :nothing onward as ordinary data. It is not simply another feature to switch on. The valve decision and its consequences.

Still openA language-design question

Whether B# has floating-point numbers remains undecided. There is no float type or literal, and no float partition in the type algebra, despite foreign values raising the question. This needs a design answer, not an invented implementation. The open float question.

Different by designNot missing C# features

The absence of a .NET object model or async/await syntax is intentional. Familiar notation is an entry point, not a promise to reproduce C#. Language scope and exclusions.

06 /

Where I would put the next effort.

These are recommendations, not current features or a replacement for the project's decisions.

  1. Close the settled foreign-entry gap.

    Make runtime range checks match declared bounds. The useful guarantee must survive a call from outside checked B# code.

  2. Take one larger exemplar all the way through.

    A working end-to-end example would teach more about real usability than removing the first error in several unrelated programs.

  3. Build one higher-order function journey.

    Connect function values, lambdas and generic signatures through a useful map or fold. Resolve the remaining union-variable matching question along that path.

  4. Give editors a small semantic surface.

    Expose existing diagnostics and derived missing heads first. Keep the next step focused on helping an author understand and repair a program.

Two narrower implementation follow-ups

Automatic UTF-8 entry scanning and atom/binary kind guards are still owed. Their scope should remain distinct from opt-in deep validation. Separately, the emitter reads the checker's function record by tuple position: introduce a shared, explicit contract when a feature next touches that boundary, rather than starting a speculative rewrite.

The central idea is small.

Say what can arrive. Write what each case does. Let the compiler show what you missed. The rest of this repository explores how far that idea can carry a practical BEAM language.
